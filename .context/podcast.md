# Podcast (weekly two-speaker episode)

The plan, with every phase's decisions and departures: `.plans/completed/2026-10-06_autonomous-two-speaker-podcast.md`.

## Status

Every phase is built (1, 2, 2b, 3 and 4): the admin opens this week's episode and starts it **interactive** (stops for review after the stories are selected and after the script is written) or **fully automated**. The pipeline selects 4-5 stories, writes a two-speaker dialogue, voices it with ElevenLabs, assembles one MP3 with ffmpeg and uploads it and a VTT transcript to Bunny Storage. A person can change the stories, edit the script's turn text, regenerate the script or the audio, then **publish** the ready episode by hand: it appears in our RSS feed (`/podcast.xml`) and on the public `/podcast` page. A persistent toast follows every run from any admin page. Two job rows, both seeded **disabled**, automate it: `generate_podcast` produces the week's episode on Friday, and `publish_podcast` publishes it on Saturday morning, Berlin time (see "Automation").

## Two axes on `Podcast`

- **`stage`** (production, forward-only): `legacy` (rows from before this pipeline; read-only, never advanced), `created` → `selected` (stories chosen: `episodeStories` snapshot, `storyIds`, `storiesSelectedAt`) → `scripted` → `voiced` (every TTS chunk stored in `podcast_audio_chunks`) → `ready` (MP3 and VTT uploaded, URLs, paths, bytes, duration and `readyAt` stored, chunks deleted). A failure never moves the stage: it sets `lastError` and `failedAt`, and the next run resumes from the stage.
- **`status`** (`ContentStatus`, shared with newsletters): publication. `published` means "listed in the feed and on `/podcast`", and only `podcastPublish.ts` changes it; `PUT /api/admin/podcasts/:id` accepts only `title` and `humanEdited` (`.strict()`, so `status` or `script` in the body is a 400). `publishedAt` is the first publication and is never cleared; `unpublishedAt` the last takedown. **Ever published** (`wasPublished()` in `podcastGuards.ts`, mirrored in `client/src/components/admin/podcastPublished.ts`) is a non-legacy row with `publishedAt` set (or `status = published`): such an episode is never regenerated, rewound, re-edited or deleted, even after an unpublish, because its feed GUID and enclosure URL must not change. Only the "edited by a person" flag and publish/unpublish still apply to it.

`weekKey` is the ISO week in **UTC** (`isoWeekKey()` in `podcastWeekly.ts`, not the newsletter job's local-time `getWeekKey`), unique, so a week has one episode and a concurrent create loses on P2002 and reads the winner's row. `weekKey` is null on legacy rows.

No runner moves a stage backwards. The only way down is `rewindEpisode(id, to, opts)` (`podcastPipeline.ts`), an admin action (see "Modes, review stops and a person's changes"). `runWeeklyEpisode` also uses it, back to `created`, to clear a dry-run row left over before running live.

## The lease

`advanceEpisode` claims the row with raw SQL on the database clock (`lease_until < now() AT TIME ZONE 'UTC'`; the column is `timestamp without time zone` holding UTC), renews it before every stage and before every TTS chunk, and writes every stage with `updateMany({ where: { id, leaseOwner: me } })`, aborting with `LeaseLostError` when that matches nothing. A voiced chunk is inserted in a transaction that first locks the row `WHERE lease_owner = me FOR UPDATE`. Release is `WHERE lease_owner = me`, in `finally` and at shutdown. A second claimant gets `{ status: 'busy' }` and returns quietly. Chosen over `pg_try_advisory_lock` because Prisma's pool can run each query on another connection (ADR-0003).

`inProgress` on a row means `leaseUntil > now`. A run whose lease is taken over or expires mid-stage writes nothing further and ends as `skipped`, recording no `lastError` of its own.

**Admin runs claim before they answer** (ADR-0009). `POST /:id/resume` and `POST /:id/rewind` with `advance` call `startAdminRun`, which checks the episode can run, claims the lease (409 "in progress" when it cannot), rewinds if asked, stores the mode and clears a block, all before the 202. The background `resumeEpisode` then runs with `leaseHeld: true` and releases in `finally`, even on an early return. So `inProgress` is true from the first answer on, and a double click gets a 409 instead of a second run. A person's edit takes the lease the same way through `withEpisodeLease` (claim, read, fenced write, release), so an edit can never race a run. The cron path keeps claiming for itself.

## Weekly run and blocks

`runWeeklyEpisode` first runs `assertPodcastRunnable`, then advances. Outcomes: `done`, `skipped` (ready or published, blocked on the cron trigger, lease held elsewhere), `stopped` (cron only: the `generate_podcast` row was disabled mid-run; nothing counted, nothing alerted, the stage and stored chunks stay for the next slot or a Resume), `retry-later`, `blocked`. A `PodcastBlockedError` blocks at once: configuration missing, the monthly cap reached, ElevenLabs credits too low, an ElevenLabs 401/402/403 or quota refusal, or the dialogue still invalid after its one regeneration. Other failures count as `attempts` only on the cron trigger and block at `maxAttemptsPerWeek` (3). An admin run never counts and clears a block and the attempts first (`startAdminRun`).

The cron trigger runs **automated**: it sets `mode = automated` on a row without a mode, and **skips** an interactive episode, blocked or not (outcome `skipped`, reason "interactive: the owner is reviewing it", `waitingForPerson: true`), so the job never overrides a person mid-review.

When a run takes an episode to `ready`, `notifyEvent('Podcast episode ready', …)` posts the title, duration, the episode's and the month's TTS characters and the admin link to `WEBHOOK_URL` (any trigger). A missing Friday notice is itself a signal.

## Automation (ADR-0013)

The schedule (owner, 2026-10-06): episodes are **published on Saturday morning, European time**. The generate job therefore runs on Friday, which leaves the owner Friday evening to listen. Both job rows are seeded **disabled** by migration `20261006230000_podcast_jobs`, with `last_completed_at` set so the scheduler's boot catch-up does not run them for never having completed; migration `20261006235000_podcast_friday_saturday_schedule` moved their cron expressions to the ones below, keeping `enabled` and `last_completed_at` (a row already changed by hand is left alone). Enabling or disabling them in the admin Jobs page is the podcast's only on/off switch; it never gates admin actions, unpublishing, the feed or the page.

- **`generate_podcast`** (`0 2,6,10,14,18 * * 5`; node-cron reads server-local time, which is UTC on Render). The handler does nothing outside the Friday window, computed in UTC: Friday from 00:00 until `config.podcast.generateWindowEndHourUtc` (20:00). So a boot catch-up on another day, or the admin's Run button then, does nothing; "Start this week's episode" is the way to run it then. Friday and the following Saturday share an ISO week, so the episode generated on Friday is the one Saturday's publish job finds; the story pool is the 7 days before selection, as always. Inside the window it calls `runWeeklyEpisode({ trigger: 'cron' })`. `blocked` throws, so the scheduler's `notifyJobFailure` alerts once; later slots skip the blocked episode until an admin Resume. `stopped`, `retry-later` and `skipped` return normally (no alert). The ready notice comes from `runWeeklyEpisode`. Before every TTS call the pipeline re-reads this row's `enabled` flag, so disabling the job stops a running episode at the next chunk.
- **Friday-evening reminder** (owner, 2026-10-06; moved from Sunday with the schedule): a run from `config.podcast.reminderFromHourUtc` (18:00 UTC, the last slot) that finds the week's episode `waitingForPerson` (interactive, not ready) sends one `notifyEvent('Podcast episode waiting for you', …)` with the title, the stage, a block reason if any, and the admin link. It is sent at most once per episode, so once per week: a conditional `UPDATE … SET review_reminder_sent_at = now WHERE review_reminder_sent_at IS NULL` claims it first, whichever slot or process gets there. A notice whose webhook post fails is not retried. While a person's run holds the lease there is no reminder (18:00 is the last slot, so none that week unless a manual Run before 20:00 finds the episode at rest): the person is at work on it. The claim is raw SQL so that it works whether or not the generated Prisma client knows the column yet.
- **`publish_podcast`** (`0 7 * * 6`, Saturday 07:00 **Europe/Berlin**). This one job is scheduled on Berlin's clock: `jobs/jobTimeZones.ts` maps it to `config.podcast.publishTimeZone` and the scheduler passes node-cron's `timezone` option, so it fires at 07:00 local in summer (05:00 UTC) and winter (06:00 UTC) alike; every other job stays on the server's clock. The admin Jobs page shows the zone beside the schedule. On any day that is not a Saturday in Berlin the handler does nothing (`isPublishDay`), so a boot catch-up (the seeded `last_completed_at` goes stale after two weeks, and a fresh dev row has none) or a manual Run never publishes on another day; a restart late on Saturday can still publish that day. On Saturday it runs the configuration check, takes `pickAutoPublishCandidate` (the newest ready, live episode of the current or previous ISO week that was never published or unpublished, ready for at least `autoPublishMinAgeHours`, 8: an episode ready by about 21:00 UTC on Friday goes out), re-reads its own row's `enabled` flag right before `publishEpisode` (disabled → no publish, no failure), and sends `notifyEvent('Podcast episode published', …)`. A refusal fails the run and alerts: an episode marked "Edited by a person" while its AI line is unconfirmed, or one a person's run holds. No candidate → nothing happens.
- **Configuration check**: at every podcast job run (inside `runWeeklyEpisode` for the generate job, first thing in the publish job) and once at boot (`checkPodcastConfigAtBoot`, `index.ts`) when either row is enabled; at boot a missing setting is logged and announced through `notifyEvent('Podcast configuration incomplete', …)`. A disabled podcast with no credentials stays silent.

**Switching it on** (owner): Admin → Jobs → enable **Generate Podcast**. Listen to the Friday episodes and publish them by hand for three or four weeks; then enable **Publish Podcast**. Disable either at any time with the same toggle.

## Selection and dialogue

- **Pool**: `published` stories crawled in the `config.content.storyAssignmentDays` (7) days before the anchor, most relevant first, the same window as the newsletter. Fewer than 4 → error before any call. The anchor is the moment the stories were selected, stored as `storiesSelectedAt`, so the story picker lists exactly the pool the model chose from, however much later a person opens it (not `createdAt`: "Start this week's episode" only creates the row, and the run may start days later).
- **Selection** (`large` tier): ids outside the pool and duplicates are dropped, at most 5 kept, fewer than 4 → error (retryable). The order the model returns is the episode order. The selection prompt (`podcast-select.ts`) asks for normally at most one story per top-level issue; a second from the same issue only when that issue has two clearly outstanding stories (then 5 stories) or another issue has no suitable article (then 4).
- **Dialogue** (`large` tier, `withStructuredOutput(..., { includeRaw: true })`, usage logged): segments `intro`, one `story` per story in order (`storyRef` = 1-based ref), `outro`. An invalid or unparsable answer gets one regeneration with the problems listed in `<PREVIOUS_DRAFT_PROBLEMS>`; a second failure is a `PodcastBlockedError`. Never truncated or patched. Story text goes into the prompt as untrusted input (`<STORIES>`).
- **Hosts**: the two speakers, `HOST_A` and `HOST_B`, are generic AI hosts and are never modelled on a real person.
- **Validation** (`validateDialogue`): every story exactly once; intro first, outro last; the intro exactly one HOST_A turn that welcomes and leads straight into the first story (owner, 2026-10-06: HOST_B's line after the welcome was superfluous); no speaker three times in a row (the code-added opener and sign-off, both HOST_A, count, so the first story segment must open with HOST_B); 4,200-6,200 spoken characters including the opener, sign-off and tags (the top, about 6.5 minutes, was raised from 5,600 by the owner on 2026-10-06, because gpt-6-sol writes about 20% over the length it is asked for; the prompt asks for `config.podcast.spokenCharAim`, 4,900, deliberately below the band's middle, `podcastLengthTargets`, `.context/prompting.md`); turns ≤ 400 characters; tags only from `PODCAST_AUDIO_TAGS`, at most 2 per turn (they are billed as characters); no URLs, markdown or speaker prefixes (the episode's own publisher names are exempt from the URL check, so "Phys.org" passes); episode title non-empty and ≤ `maxTitleChars` (80), title and summary free of URLs and markdown. A band miss is fed back in the prompt's terms (the model's own turns against `dialogueCharBudget()`), not the whole-episode total.
- **Segues** (owner, 2026-10-06): audio is voiced one segment per TTS request, so every segment after the intro must open with its own bridge: a first turn of at least 40 characters that is not just the headline (for the first story, HOST_B picking up the story the intro led into), and no two consecutive story segments opening with the same first five words. Keep this rule in the prompt, the schema description and validation together.
- **Snapshot**: `episodeStories` (ref, id, title, publisher, sourceUrl, slug, issue) is frozen at `selected`; show notes and the later feed read it, never `storyIds`, so story deletion (which strips `storyIds`) cannot shift references. The script stage reloads the prompt material by id in snapshot order (`loadEpisodeStories`); a story no longer published fails the stage ("story "…" is no longer published; change the selection"), kept at `selected`.
- **Stored at `scripted`**: `dialogue` (the model's segments), `title` (`W41: <model title>`, the week number from `weekKey`; no prefix without one), `episodeSummary`, `showNotes` (AI line first, chosen by `humanEdited`, then the summary, then each story with our analysis link and its source), `script` (the rendered spoken episode), `scriptModelId`. A successful stage write also clears `lastError`. A person edits the title freely from `scripted` on; it is written into the MP3's ID3 title at assembly, so a title edited after `ready` differs inside the file (accepted: podcast apps show the feed's title).

The opener and sign-off are code, not prompt: `PODCAST_OPENER` ("Everything you're about to hear was written and voiced by AI from this week's news.", owner-approved 2026-10-06) is the first spoken turn of every episode. Don't move it into the prompt. Changing its wording needs the owner (`.context/ai-transparency.md`).

## Modes, review stops and a person's changes (ADR-0008)

**Mode.** `mode` (`automated | interactive`) is null until a person starts the episode (or the cron sets `automated`). `advanceEpisode` re-reads the row after every stage and stops when `pausesForReview`: mode `interactive` and stage `selected` or `scripted`. `voiced` never stops (assembly follows at once); `ready` ends production in both modes. A mode switch ("Finish automatically") takes effect at the next stage boundary. `awaitingReview` is derived, never stored: interactive, no live lease, no `lastError`, not blocked, stage `selected` or `scripted`.

**A person's changes** happen only at rest (no live lease, not legacy, never published; 409 otherwise) and each takes the lease for its write (`podcastEditing.ts`):

- **Stories** (`PUT /:id/stories`, at `selected`): distinct ids, `minStories` to `maxStories`, each from the pool at `storiesSelectedAt` (422 otherwise). The snapshot is rebuilt with refs 1..n in the submitted order; the picker swaps a story in place and appends an added one.
- **Script** (`PUT /:id/script`, at `scripted`): the client sends the stored structure back with new turn text and summary. `applyTurnEdits` refuses any change of segments, kinds, story refs, turn counts or speakers (422 "the script changed since it was opened"), so speakers stay structural and a stale tab cannot overwrite a regenerated script. The merged dialogue runs through `validateDialogue(…, { authoredBy: 'person' })`: every rule stays an **error** that blocks the save (band, turn length, tags, URLs, markdown, prefixes, speaker runs, coverage), except the two segue rules (bridge of 40 characters that is not the headline; no two story openings with the same five words), which become **warnings**: the save succeeds and returns them. A person may write a short bridge on purpose and hears the result before publishing; the hard rules protect TTS spend, chunking and the feed. A save rewrites `dialogue`, `episodeSummary`, `script` and `showNotes`; when the spoken turns changed (not the summary alone), it also deletes the stored audio chunks, since a failed voicing leaves them behind and a resume skips every stored index, which would otherwise splice old audio into the new script.
- **Title and flag** (`PUT /:id { title?, humanEdited? }`): the title from `scripted` on, until first published; the flag at any stage, also after publication (ticking it on a listed episode waits for the edited line's confirmation, below).

**"Edited by a person"** (`humanEdited`). The server ticks it when a person changes the story set or its order, or the text of a turn or the summary; a title edit, a save of identical text or a mere approval does not. The person can tick or untick it at any time, also on a published episode (it changes only the wording of the disclosure, never the audio or the GUID). It picks the AI line of the show notes, the ID3 comment, the feed's item description and the public page: unticked, `PODCAST_EPISODE_AI_LINE`; ticked, `PODCAST_EPISODE_AI_LINE_EDITED` ("… A person reviewed and edited this episode."). Both lines are owner-approved (the edited one by Odin Mühlenbein in session, 2026-10-06), and `PODCAST_EPISODE_AI_LINE_EDITED_CONFIRMED` in `aiLabelCopy.ts` is true. The guard stays for a future wording change: whenever that constant is false, publishing an episode with the flag ticked, and ticking it on a listed episode, answer 409 (`editedAiLineRefusal` in `podcastGuards.ts`); unticking always works. Every write that changes the summary, the stories or the flag rebuilds the show notes, and toggling the flag on an episode that was ever published also invalidates the feed cache. The ID3 comment inside an MP3 already assembled keeps the line it was assembled with. Regenerating the script keeps the flag; a rewind to `created` clears it.

**Going back** (`rewindEpisode`, `POST /:id/rewind { to, advance }`): refuses a target that is not before the stage (except `created` again, the dry-run reset), a legacy or published episode, and one in progress. Each target clears its successors' output: to `scripted` the audio fields and chunks, with a fresh `ttsSeed`; to `selected` also the dialogue, script, summary, show notes, `scriptModelId`, `ttsSeed` and the title (back to `defaultEpisodeTitle`); to `created` also the snapshot, `storyIds`, `storiesSelectedAt` and `humanEdited`. The previous MP3 and VTT are deleted best-effort. A person's rewind makes the episode **interactive** (a person stepped in, so the run stops at the next review point instead of voicing unseen). The UI uses it as Start over (`created`, advance), Regenerate script (`selected`, advance), Change stories (`selected`), Edit script after voicing (`scripted`) and Regenerate audio (`scripted`, advance).

**Cost before voicing.** Every UI action that will voice (Approve script and voice it, Resume at `scripted`, Regenerate audio, Edit script after voicing) shows `PodcastVoiceConfirm` first: `ttsCharsEstimate` (the characters of `episodeChunks(dialogue)`), "about N credits at 1 credit per character", and the month to date against the cap. A dry run says no credits are spent. A run that will write *and* voice (Fully automated, "Finish automatically" at `selected`, Resume of an automated episode at `created` or `selected`; `runVoices` in `PodcastStageStepper`) asks too (owner, 2026-10-06): there is no script yet, so the dialog gives a typical episode instead, `typicalEpisodeChars` (`config.podcast.spokenCharAim`) with `maxEpisodeChars` (the band's top) beside it, both returned by `GET /usage`. Interactive starts ask nothing (they stop at the next review), and the cron path never asks.

**Progress** (ADR-0009). `GET /api/admin/podcasts/active` lists every episode with a live lease as `{ id, title, stage, mode, activity, chunksDone, chunksTotal }`; `activity` names the step from the stage being left (`created` "Selecting stories", `selected` "Writing the script", `scripted` "Voicing" with stored chunks out of the total, `voiced` "Assembling and uploading"). `PodcastProgressProvider` (mounted once in `AdminLayout`, inside `ToastProvider` and the router) asks it on mount and on window focus, so it reattaches after a reload and to runs another tab or the cron started; it polls every 3 s while it follows any episode. The episode page calls `track(id)` after every 202. Each followed episode has one toast (`podcast-<id>`, spinner, "W41: …: Voicing 3/5") that never fades while the run lasts and links to the episode page. When the episode leaves the active list, the provider reads it once and turns the toast into the outcome ("Stories selected: review them", "Script ready: review it", "Episode ready to listen", or the error or block reason); a success fades after 4 s, an error stays until dismissed. A poll sent before `track` was called cannot end that episode's toast.
## Audio

- **Chunks** (`chunkTurns`): the spoken segments (opener and sign-off included) are packed whole into chunks of at most `chunkMaxChars` (1,800); a segment longer than that alone is split at turn boundaries only. Turns are never split, so a chunk that starts a segment starts with its bridge. About 5 chunks per episode, one per story. The chunking is rebuilt from the stored dialogue on every run, so a resume finds the same indices.
- **Voicing** (`voiceEpisode`, ADR-0007): chunks are voiced in order with `POST /v1/text-to-dialogue`, `model_id` `eleven_v4` (`ttsModelId`), the render's seed (the row's `ttsSeed`, or `config.podcast.ttsSeed` when null; a rewind to `scripted` draws a fresh one, so "Regenerate audio" gives a new take while a resume within one render keeps it), `mp3_44100_128`, HOST_A → `voiceIdA` (Darian), HOST_B → `voiceIdB` (Talia), and text continuity: `previous_text`/`future_text`, the last and first 100 characters of the neighbouring chunks, absent on the first and last chunk (Phase 0 S1: request ids gave no audible gain, text context is stateless). Each chunk's bytes, request id, characters and CBR duration are stored before the next call; a resume skips stored chunks, so nothing is paid twice. The `character-cost` response header is logged per chunk (the per-call truth of what was billed).
- **Retries** (`lib/elevenlabs.ts`): only a 429 that is not a quota refusal, or a 5xx, is retried once. A 401/402/403 or a quota/paused refusal is `ElevenLabsQuotaError` → `PodcastBlockedError`. A timeout is never retried, because ElevenLabs may have billed it.
- **Assembly** (`assembleEpisodeMp3`, ADR-0005): one ffmpeg process (`ffmpeg-static`, pinned) on temp files in `os.tmpdir()`, always removed: each chunk padded with `segmentPauseMs` (700) of silence except the last, concatenated, `loudnorm` to -16 LUFS, re-encoded to 128 kbps CBR mono MP3, ID3v2.3 title, artist and album "Actually Relevant", comment = `podcastEpisodeAiLine(humanEdited)`, and the AI-provenance `TXXX` frames `AI-generated=true` and `digitalSourceType=…/trainedAlgorithmicMedia`. Duration = bytes × 8 / 128 kbps (no ffprobe). Nothing checks the duration against a limit; if a gate is ever added, put it at about 7.5 minutes or more.
- **Transcript** (`buildTranscriptVtt`): one cue per turn, voice spans `<v Host A>`/`<v Host B>`, timed proportionally to characters within each chunk and offset by the preceding chunks' measured durations plus the pauses. Approximate by design; audio tags are left out of the cue text.

## Storage (Bunny)

`putObject`/`deleteObject` talk to `https://storage.bunnycdn.com/<zone>/<path>` with the zone password as `AccessKey` and a SHA-256 `Checksum` header on uploads; both are idempotent and retried. Paths are ASCII only (`[A-Za-z0-9._-]` segments): `episodes/<weekKey>-<8 hex>.mp3` and `.vtt`, under `dry-run/` for a dry run. The public URL is `config.podcast.audioBaseUrl` (`https://audio.actuallyrelevant.news`, the pull zone's custom hostname, Phase 0 S4) plus the path. `.vtt` is served as `text/vtt` by an edge rule on the pull zone.

**Never reuse a file name.** The CDN caches a deleted file for up to 30 days and nothing here purges it (owner decision, 2026-10-06: a takedown removes an episode from the feed and the page; a CDN purge is a manual step in the Bunny dashboard). Every render gets a fresh random suffix, so an old file can never appear under a new episode's URL. Regenerate and delete remove the old objects best-effort; a failure leaves an unreferenced file, logged, never fatal. A run that uploaded but then lost its lease leaves its files unreferenced the same way.

## Spend controls

- **On/off**: the `generate_podcast` and `publish_podcast` job rows (see "Automation"). On the cron trigger the pipeline re-reads `generate_podcast`'s `enabled` flag before every TTS call (`assertJobEnabled`) and stops with `PodcastStoppedError` when it is off. Admin actions (Start, Resume, Regenerate) are not gated by the toggles, but by the configuration check, the cap and the credit block like every run.
- **Configuration check** (`assertPodcastRunnable`): the two voice ids always; on a live run (production) `ELEVENLABS_API_KEY`, `BUNNY_STORAGE_ZONE`, `BUNNY_STORAGE_PASSWORD`; on the cron trigger `WEBHOOK_URL`. A missing one blocks the episode with the names in the reason.
- **Monthly cap** (`reserveTtsChars`): before each TTS call, a short transaction takes `pg_advisory_xact_lock`, sums `podcast_tts_usage` for the UTC calendar month and inserts the chunk's characters if the sum stays within `monthlyTtsCharCap` (32,000, provisional until one call is re-measured after 2026-10-12); otherwise `PodcastBlockedError`. The row is kept whatever the call's outcome and survives episode deletion (`podcastId` set null). Regenerations count. A dry run reserves nothing.
- **Balance pre-check** (`assertBalanceCovers`): before the first pending chunk of a live run, `GET /v1/user/subscription` (`character_limit - character_count`) must cover the remaining chunks' characters. ElevenLabs credits reset on the subscription anniversary and the counter lags a few calls, so this is coarse; the ledger cap is the guard that holds when the vendor's numbers are wrong. The key needs "user read" for it; a refusal blocks.

## Dry run

`config.podcast.dryRun` is `NODE_ENV !== 'production'`, never set, and stored on the row at creation. A dry-run episode always voices with the silent stub (`silentMp3`, as long as the characters would take at `stubCharsPerSecond`), spends no credits and reserves nothing, assembles without `loudnorm` (loudnorm on pure digital silence crashes the encoder), and uploads under `dry-run/`; without Bunny credentials it stops at `voiced` with "storage not configured". LLM calls stay real. Publishing refuses the row, and the feed and `/api/podcast` filter `dryRun = false`.

## Publishing, feed and page (ADR-0010, ADR-0013)

**Publish** (`publishEpisode`, from the admin button and the `publish_podcast` job): requires `stage = ready`, `dryRun = false` and uploaded audio (`publishRefusal`; 409 otherwise). It takes the episode's lease, so it cannot race a rewind or a run (409 "in progress"). It sets `status = published`, `publishedAt` the first time only (a republish keeps the original date, so the item does not jump in podcast apps), clears `unpublishedAt`, and invalidates the feed cache. Not gated by the job toggles. Publishing an edited episode works like any other.

**Unpublish** (`unpublishEpisode`) always works: no lease, no stage check. It sets `status = draft` and `unpublishedAt`, keeps `publishedAt` (so the episode stays "ever published": never regenerated or deleted), and invalidates the feed cache. It never deletes the MP3 or VTT and never purges the CDN (owner decision, 2026-10-06): the files stay reachable at their URLs, apps that downloaded the episode keep it, and a purge is a manual step in the Bunny dashboard. The automatic publish job (`pickAutoPublishCandidate`) never takes an episode with `unpublishedAt` set, so it cannot undo a takedown; it takes only the newest ready, live episode of the current or previous ISO week that was never published and has been ready for `autoPublishMinAgeHours` (8).

**Feed** (`GET /api/podcast/feed.xml`, public URL `https://actuallyrelevant.news/podcast.xml` through a Render rewrite, `.context/seo.md`). Hand-built RSS 2.0 with the `itunes`, `podcast` (Podcasting 2.0), `atom` and `content` namespaces, every value escaped with `lib/xml.ts`:
- Channel: title, link `/podcast`, `atom:link rel="self"`, description and `itunes:summary` = `PODCAST_SHOW_DESCRIPTION` (the standing AI statement), `language en`, copyright, `itunes:author`, `itunes:owner` with `itunes:email` = `config.podcast.ownerEmail` (`contact@actuallyrelevant.news`; Spotify sends its claim code there), `itunes:image` and the RSS `<image>` from `config.podcast.artworkUrl` (3000 px JPEG on Bunny, made deterministically from the brand logo, not AI-generated; a new image needs a new file name, as for audio), `itunes:category` News, `itunes:explicit false`, `itunes:type episodic`, `podcast:locked no`, `podcast:guid` = `config.podcast.feedGuid` (UUIDv5 of the feed URL; never change it), and `<podcast:txt purpose="ai-content">true</podcast:txt>`.
- Items (`getPublishedEpisodes`: `status = published`, `stage = ready`, `dryRun = false`, newest `publishedAt` first): title, `description` (plain text) and `content:encoded` (HTML), both starting with the episode's AI line, then the summary and each story with our analysis link and its source (from the frozen snapshot); `guid isPermaLink="false"` = the row id; `pubDate` = `publishedAt`; `enclosure` = the CDN URL with the exact `audioBytes` and `audio/mpeg`; `itunes:duration` (HH:MM:SS); `podcast:transcript` (the VTT, `text/vtt`); `podcast:txt` ai-content.
- An empty feed (before the first publish) is still valid RSS.
- Cached in-process for `config.feed.cacheMaxAge`; publish, unpublish and a flag change on a published episode invalidate it. A second instance during a deploy serves its own copy until the TTL (accepted).
- The podcast router is mounted **before** `router.use(apiLimiter)` in `routes/public/index.ts`: behind the rewrite, directory crawlers may all arrive from one proxy address, and a shared 100-per-15-minute bucket would answer Apple and Spotify with 429. The cache carries the load. The JSON route keeps `apiLimiter` itself.

**Public JSON** (`GET /api/podcast`, open CORS like the other public read paths, in the OpenAPI spec): `{ show: { title, description, feedUrl, artworkUrl, listenLinks }, episodes }`; each episode carries `aiLine` and an `aiGenerated` marker naming its AI fields (`AI_GENERATED_PODCAST_FIELDS` in `lib/aiProvenance.ts`). Served with both podcast jobs disabled.

**Page** (`/podcast`, `PodcastPage.tsx`): heading, the AI label "Written and voiced by AI." (`AI_DISCLOSURE_COPY.podcastLabel`), intro and the feed link are static and prerender; the listen links and the episode list load client-side. Each episode: "AI" badge and title, date and duration, its AI line, summary, `<audio controls preload="none">` on the Bunny URL (no Render bandwidth; nothing is fetched from Bunny until play), the transcript link and the stories with links to our story page and the source. Listen links are `config.podcast.listenLinks`, empty until the show is listed. In the footer navigation, the sitemap (both lists) and `<link rel="alternate" type="application/rss+xml">`.

## Troubleshooting

- **Episode stuck "In progress"**: a process died without releasing; the lease expires after `leaseMinutes` (30) and the next Resume takes it over.
- **Blocked with "the dialogue is still invalid…"**: the reason lists the rule each draft broke. Resume tries again (two more calls); repeated failures point at the prompt or the band.
- **Blocked with "podcast configuration missing: …"**: set the named variables on the host and Resume.
- **Blocked with "monthly TTS cap reached"**: wait for the next UTC month, or raise `monthlyTtsCharCap` in code (owner decision).
- **Blocked with "ElevenLabs refused (HTTP 401/402/…)" or "credits too low"**: check the key's permissions and the account's credits, then Resume; stored chunks are not voiced again.
- **Stops at "voiced" with "storage not configured"**: Bunny credentials missing (normal in a dev environment without them).
- **"ffmpeg binary not found"**: `ffmpeg-static`'s install script did not run (`.context/deployment.md`).
- **"has N stored chunks for M expected"**: the chunking changed (for example `chunkMaxChars`) between voicing and assembly; Regenerate audio.
- **"only N published stories this week"**: the pool is short; publish more or wait.
- **"story "…" is no longer published; change the selection"**: a selected story was unpublished between selection and scripting; swap it in the picker, then Resume.
- **Episode waits at "Awaiting review" and the cron does nothing**: by design, the cron skips interactive episodes (and reminds once on Friday evening). Approve the step, or choose "Finish automatically".
- **"Run" on Generate Podcast does nothing**: outside the Friday window (UTC, 00:00 to 20:00) the job is a no-op by design; use "Start this week's episode".
- **Publish Podcast failed with "… cannot be listed yet: its AI line awaits the owner's confirmation"**: only possible if `PODCAST_EPISODE_AI_LINE_EDITED_CONFIRMED` was set back to false after a wording change; untick "Edited by a person" or have the owner confirm the new line, then publish by hand.
- **No Saturday publication and no alert**: no candidate (nothing ready for 8 hours this or last week, or it was unpublished before), or the job is disabled.
- **Publish answers 409 "a dry-run episode … cannot be published"**: the episode was produced outside production (silent stub voice). Produce it in production.
- **`/podcast.xml` shows the website instead of XML**: the Render rewrite is missing or below the SPA catch-all.
- **An unpublished episode still plays in an app or at its URL**: expected. Unpublishing removes it from the feed and the page only; purge the file in the Bunny dashboard if it must go.
- **A toast still shows a run after the server restarted**: a graceful shutdown releases the lease, so the next poll turns the toast into the outcome; after a crash the lease (and the toast) lasts until it expires (30 minutes). Either way the stage left mid-way shows Resume.
