# Admin Dashboard

The admin dashboard is a React SPA at `/admin/*`, JWT-based auth with httpOnly refresh cookies, and TanStack Query for data fetching.

## Architecture

- **Auth**: `AuthProvider` wraps the app; stores JWT access token in memory (not localStorage), uses httpOnly cookie for session refresh, redirects to `/admin/login` on auth failure. See `.context/authentication.md` for details.
- **API Client**: `admin-api.ts` provides typed `adminApi.*` methods organized by resource with Bearer auth headers. Auto-refreshes expired tokens via `/api/auth/refresh`.
- **Data Fetching**: TanStack Query with 30s stale time, hooks in `hooks/use*.ts` per resource
- **UI Components**: Headless UI + Tailwind in `components/ui/` (Button, Badge, Card, Pagination, etc.)
- **Admin Components**: Resource-specific in `components/admin/` (tables, forms, detail views)
- **Toast Notifications**: `ToastProvider` in AdminLayout, `useToast()` hook for success/error/progress messages. A progress toast never fades; `addProgressToast(id, message, { href })` and `updateToast(id, { href, sticky })` make a toast a router link to the page it is about (keyboard-reachable) and keep an outcome, typically an error, until it is dismissed. Existing callers pass neither. The toast list is a polite live region, so every text change in it is announced: for a progress count that changes often, pass it as `addProgressToast(id, message, { detail })`, which is shown after the message but `aria-hidden` (a link toast's name still includes it), so only a change of `message` is announced; an outcome drops the detail. The podcast run toast does this for its chunk count. A toast is at most `max-w-xl` wide and shows its message's line breaks (the bulk Research's outcome puts each skipped story on its own line).
- **Jobs page notes**: a job with a note (`note` in `GET /api/admin/jobs`, written on the server, `.context/scheduler.md`) has an info button beside its name, named "About" and the job's name, that shows it on hover, keyboard focus or a tap (`InfoTip`); a `warning`, a state the owner must notice such as research switched off, stays visible under the name. Explanations go in the note, never inline: so does the help of the Review and Flex columns (one beside each header, on the same line; Flex's explains both a job's switch and a chain's hours). **Every job is in one table** (`JobTable`): the column headers once, sticking to the top as the page scrolls from lg on; then each chain as a group (its own `<tbody>`), headed by the chain's own row and its steps indented under it, then the other jobs, indented under an Other jobs heading row. What a chain is waiting on (review, a step's time, a failed step) is a row across the table under the chain's row. The chain's own row (bold, its name and note) has the same columns as its steps: its schedule in the Schedule column (click to edit; below lg under the name, on one line cut short, the full schedule on hover), its switch, its flex cut-off in hours in the Flex column, its status, the whole run's length and cost (no summary: what each step did is in its own row), when it last finished, and Run and Details. Its Review cell stays empty, since only a step waits for review. An hours field saves on blur; a value that is not a quarter hour from 0.25 to 48 is put back with a toast saying so. The table keeps fixed column widths from lg on; below lg it sizes columns to its content and scrolls sideways, so headers never overlap (the header does not stick there: a sideways-scrolling box is what it would stick to).
- **Jobs page errors**: the enable toggle and the Run button on the Jobs page show the server's error text in the error toast (`ApiError.message`): a 422 naming the missing settings when a job's enable check refuses, a 409 when the job is already running (`.context/scheduler.md`).
- **Background Tasks**: `BackgroundTaskProvider` in AdminLayout, `useBackgroundTasks()` hook for fire-and-forget async operations with progress tracking via persistent toasts
- **New version notice**: each client build compiles in an id (`__BUILD_ID__`, `vite.config.ts`) and writes it to `dist/version.json`. `NewVersionBanner` in AdminLayout compares the two on window focus and every 5 minutes and offers a reload when they differ, so an admin tab left open across a deploy does not keep showing old screens (missing buttons, raw job ids). On the dev server there is no `version.json` and the banner stays hidden. Job names go through `jobDisplayName()`, which title-cases a job id the running build has no label for.
- **Long server-side runs** (the pattern for work that outlives the request and the page): the route claims the work before it answers 202, the server lists what is running (`GET /api/admin/podcasts/active`), and an app-level provider in AdminLayout (`PodcastProgressProvider`) asks it on mount and on window focus, polls while it follows anything, and keeps one clickable toast per run until its outcome. The client never guesses when a run starts or ends, so the toast survives navigation and reattaches after a reload. See `.context/podcast.md`, "Progress".

## Route Structure

```
/admin/login          → LoginPage (no auth)
/admin                → AdminLayout (auth required)
  /admin              → DashboardPage (chains waiting on the owner, unseen notices, unread feedback, spending summary, stories in the last 7 and 30 days)
  /admin/stories      → StoriesPage (filters, table, bulk actions)
  /admin/stories/:id  → StoryDetailPage (the story editor; a page, not a panel)
  /admin/feeds        → FeedsPage
  /admin/issues       → IssuesPage
  /admin/issues/new   → IssueEditPage
  /admin/issues/:id/edit → IssueEditPage
  /admin/newsletters  → NewslettersPage
  /admin/newsletters/:id → NewsletterDetailPage
  /admin/subscribers  → SubscribersPage (read-only: local DB vs Plunk reconciliation)
  /admin/podcasts     → PodcastsPage
  /admin/podcasts/:id → PodcastDetailPage
  /admin/jobs         → JobsPage (auto-refreshes every 10s)
  /admin/feedback     → FeedbackPage
  /admin/notices      → NoticesPage (owner alerts; ?source=, ?show=unseen|all, ?page=)
  /admin/users        → UsersPage (admin-only user management)
  /admin/spending     → SpendingPage (spending per job, warning levels)
  /admin/stats        → StatsPage (lifetime totals)
```

The sidebar ends with Users, Spending and Stats, in that order.

## Key Patterns

- **Story filters** persist in URL search params via `useSearchParams()`
- **Story page** (`/admin/stories/:id`, `StoryDetailPage` around `StoryEditForm`; the only story editor, there is no side panel): the story's title as the h1 with its status badge and rating under it (the bar's actions follow the status, so it shows on every tab) and "View on site" for a published story, then the story's sections as tabs (`StoryEditorTabs`, `storyTabs.ts`, `hooks/useStoryTabs.ts`), whose list stays pinned at the top of the view while the page scrolls ("Sticky bars" below), and under them the sticky action bar (`StoryActionBar`). The tabs, in order: **Story** (title label, title, slug, summary, quote and its attribution, marketing blurb), **Assessment** (status, emotion tag, issue, pre-rating and rating, reasons, summary, antifactors, calculation; `StoryEditFields.tsx`), **Source** (the Source and Cluster sections), **Research** (unless `GET /research/usage` answers 404; shown while it loads), **Context** (once its section would show, `contextShown`) and **Social** (a published story, its Bluesky and Mastodon draft buttons, `useSocialDrafts`); the sections are cards with an h2 (`StoryEditorSections.tsx`, `storyEditorClasses.ts`). They are WAI-ARIA tabs (arrow keys, Home, End). The open one is in the address (`?tab=`, an unknown or missing one opening Story): choosing a tab replaces the history entry and keeps its location state, so a reload and browser Back reopen the tab and the back link still returns to where the story was opened from. Every panel stays mounted, so the form holds every tab's fields and a switch keeps unsaved edits. A tab with unsaved edits shows an amber dot, one with a field Save cannot send or a section that failed to load a red icon (the problem wins), each in words in the tab's accessible name ("Assessment, unsaved changes", "Research, has a problem"). The form checks its own fields (`noValidate`; `storyForm.ts`): a rating must be a whole number from 1 to 10, shown inline, and Save with such a field opens its tab and focuses it rather than sending. The note that a researched story's fields are locked sits above the tabs. Save stays on the page, on the same tab and scroll offset: a success toast ("Story updated"), the form takes the values the server saved (not only what it sent: a slug sent empty is kept), so no tab is marked unsaved and Save is disabled again, and the header's status and rating follow the saved story ("Story data after a change"). Cancel and the "Back to …" link above the title return to where the story was opened from. A 404 shows "Story not found"; another failure "Failed to load story" with Try again
- **Story page's action bar** (`StoryActionBar`, `storyActions.ts`): the story's actions by status, as the stories list offers them, then Cancel and Save. The status's next step leads, as the primary button while nothing is unsaved (Save is then the one to press): Pre-assess on fetched, Assess on pre-analyzed, Publish on analyzed and selected; published, rejected and trashed have none. The others follow: fetched and pre-analyzed Publish, Reject, Trash; analyzed and selected Re-assess, Research, Reject, Trash; published Re-assess, Research, Gather context, Reject, Trash; rejected Publish, Re-assess, Trash; trashed Publish, Reject. Research shows unless the backend has no research, and Gather context ("Gather more context" once the story has a run) only where the Context section could show. From `md` up they sit beside the primary one; below, in a "More" menu that opens above the bar, where a closed action gives its reason in words. Each runs as on the list (`hooks/useStoryActions.ts`, shared with `StoriesPage`'s row actions: the same background tasks, toasts and status mutation), Research and Gather context as their sections ran them (`useResearchAction`, `useGatherAction`). Every action is a `ReasonButton`: closed with its reason while the form saves, a status change is under way or a task of this tab works on the story, plus the action's own (Publish without a rating, research's refusals, Gather's). An action that writes the story's fields or status (Pre-assess, Assess, Re-assess, Publish, Reject, Trash) asks first while edits are unsaved ("Discard your unsaved changes?", "Discard and publish"), and confirming discards them before it runs, since kept edits would carry the old values and a later Save would write them back; Research and Gather context write nothing on the story and never ask. Re-assess always asks, saying it replaces the AI-written fields (and drops a researched version). There is no Unpublish: Reject or Trash take a published story off the site. Delete stays on the list
- **The way back from a story** (`components/admin/storyReturn.ts`): a link to a story's page carries location state `returnTo` (`returnState(location)`): the path and search of the page it was opened from, that history entry's key, and a label by its path ("Back to stories", "Back to newsletter", "Back to podcast", else "Back to previous page"). The stories list keeps its filters, sort, page and page size in its URL, so the way back restores them all. The list's titles are links (a new tab works) and its Edit buttons go to the same place; the newsletter's and the legacy podcast's assigned stories (`AssignedStoriesList`) and "Newer coverage" (`NewerCoverageNote`) carry their return too. Without the state (a bookmark, a typed address, a reload in a new tab) the page goes back to `/admin/stories`, the list's defaults. A list address with `?open=<id>` (the side panels' URL pattern) goes to that story's page in place of the list's entry, its other parameters kept as the way back. `backLink(state)` accepts only an `/admin` path and a known label, since history state can hold anything
- **Scroll position** (`hooks/useAdminScroll.ts`, in `AdminLayout`): `<main>` is the admin's scroll box, so the browser restores nothing for it. Each history entry's offset is remembered (in memory, and in `sessionStorage` when the page is left or reloaded, the newest 50 entries); a link to another path starts at the top; browser Back or Forward puts the entry's offset back, and so does a link whose state names the entry (`restoreScrollOf`, which the story page's back link sets); a change of the search alone (a filter, a page) keeps the offset. A restore waits up to 2 seconds for the page to grow tall enough (its rows may still be loading) and stops when the person scrolls, taps or types first
- **Bulk actions** use selection state (resets on filter/page change) with confirmation dialogs. Each action the bar asks for (`BulkAction`) has one handler in `components/admin/storyBulkActions.ts`, which `StoriesPage` gives its state and dialogs: a new LLM action that confirms and then runs one polled task is a `POLLED_ACTIONS` entry (title, description, label, `submitFn`), a social draft a `SOCIAL_DRAFTS` entry; the bulk Research and the bulk "Use researched versions" are single entries, their wording in `bulkResearch.ts`
- **Bulk LLM operations** (preassess, reclassify, assess, select, research) run as background tasks via `useBackgroundTasks()` — dialog closes immediately, progress toasts persist across navigation, query invalidation fires on completion. **Research** (after Assess in the bar) researches up to 50 stories through each story's own research path and applies nothing: its confirmation names the count and the cost upper bound (every run at its $0.25 reservation), the button stays visible with its reason when research can't run, and its outcome toast names each skipped story with the reason and stays until dismissed (`.context/story-research.md`, "Bulk research")
- **Use researched versions** (after Research in the bar) is not a background task: one synchronous request puts each selected story's newest research run on it through the single "Use this version" (up to 50, one story at a time, one embedding call each), the way the bulk status change answers in its request. The dialog closes at once, a progress toast follows the request and becomes the outcome (applied, failed, skipped with reasons, each named by title; a story whose newest run research found old news or contradicted is skipped, never overruled in bulk), and the story queries are re-read; the button stays visible with its reason while applying is closed (`.context/story-research.md`, "Bulk apply")
- **Story data after a change**: every task, job or mutation that changes stories on the server ends with `invalidateStoryQueries()` (`hooks/useStories.ts`), which marks the lists, the counts and every story's detail query (`['story', id]`, behind the story's page) stale, so a story opened after an assessment shows the assessed data. A write of one story whose answer is the story's own fields (Save, `PUT /stories/:id`; a status move, `PUT /stories/:id/status`) first lays that answer over the cached detail, never in place of it (`storeWrittenStory`): the detail also holds the feed, issue, cluster and post counts only `GET /stories/:id` joins in, and the page would show them empty until the next read. A story with no cached detail gets none from a write
- **Edit forms follow refetched data** (`useEditForm`): when the loaded entity changes (a background refetch) and the form has not been edited, the form takes the new values; once edited, it keeps the edits and stays dirty. Its `onSuccess` gets what the mutation answered, so a form that stays open after a save (the story page) puts the saved entity's values in itself
- **LLM operations** (newsletter generation) show persistent loading state with "may take a minute" message
- **Podcast episodes** run server-side in the background: Resume and a rewind that continues answer 202 once they hold the episode's lease, `usePodcastProgress().track(id)` follows the run, and the detail page polls every 5 s only while the lease is live (`inProgress`). The detail page is tabbed by stage (`?tab=`) with a sticky action bar at the bottom; a component that holds unsaved edits (story picker, script editor) reports it to the page, which keeps approval disabled and guards tab switches and in-app links until they are saved or discarded; see `.context/podcast.md`, "Admin". **New podcast** on the list creates a standalone episode whose stories a person picks in `PodcastStoryFinder` (filters, paginated published stories, AI "Suggest stories"), sharing the draft hook `usePodcastStoryDraft` with the weekly picker; see `.context/podcast.md`, "Standalone episodes"
- **Unsaved-changes guard** (on the podcast episode page, the story's page (`StoryEditForm`), and the issue editors, the `IssueEditPage` route, which compares its form with what it loaded, and the Issues list's `IssueEditPanel`): `useUnsavedChangesGuard(dirty)` returns `guard(action)` plus the state for its dialog, `UnsavedChangesDialog`; while dirty it also holds every in-app navigation to another path through react-router's `useBlocker` (a `Link`, a `navigate()` call, browser Back/Forward) in the same dialog, and asks on reload or close (`beforeunload`). A change of the search alone on the same path passes (it is the page's own URL state, such as `?tab=`; tab switches go through `guard`). A navigation that itself discards the edits passes `state: LEAVE_UNSAVED` (e.g. after deleting the episode); a save that then navigates calls `markSaved()` first, since the form has not re-rendered as clean when the navigation is checked. Cancel buttons that navigate ask like any other navigation. `useBlocker` needs the data router (`createBrowserRouter` in `main.tsx`), so a component test of a guarded page renders in a `createMemoryRouter`, as `renderInAdmin` (`client/src/test/podcasts.tsx`) and `renderAdminRoutes` (`client/src/test/admin.tsx`) do; a router allows one active blocker at a time, so a page mounts one guard. On the story's page the back link, Cancel, the sidebar and browser Back are all navigations to another path, so each asks while edits are unsaved; a tab switch is a change of the search and passes, since every tab's fields stay in the one form; a story action that writes the story asks in its own dialog and discards the edits (above, "Story page's action bar"); Save stays on the page and puts the saved values in the form, so the guard has nothing left to hold once the save re-renders (no `markSaved()`). The Issues list's edit panel opens and closes through local state, not a navigation, so closing it with unsaved edits does not ask; leaving the list while it holds edits does
- **Actions that cannot run now stay visible with their reason**: `ReasonButton` (`aria-disabled`, focusable, the reason as tooltip and `aria-describedby`) rather than a hidden or plainly disabled button. `Tooltip` (`components/ui/Tooltip.tsx`) opens on hover and keyboard focus, stays while hovered, closes on Escape, and keeps its text in the DOM for the description. It does not open on a tap; an explanation that must reach touch users goes in an `InfoTip` (`.context/accessibility.md`, "Info notes")
- **Story research section** (`StoryResearch`, the story page's Research tab): the month's research spend against the cap ("This month's research usage could not be loaded." when that read fails) and a picker of the story's runs rendered by `ResearchRunView`. Its Research action is in the page's action bar (`useResearchAction` in `hooks/useResearch.ts`), a `ReasonButton` visible with its reason when switched off, at the cap, of the wrong status or already running, which starts the run through `launchPolledTask`; the tab and the action are absent when `GET /research/usage` answers 404, as the stories list's bulk Research is. `.context/story-research.md`
- **Story context section** (`StoryContextAdmin`, the story page's Context tab; hooks in `hooks/useStoryContextAdmin.ts`; the routes are `.context/story-context.md`, "Admin"). The tab is absent while the story has no context run and cannot have one gathered (`gather.eligible`: published, with research facts), when `GET /stories/:id/context` answers 404, and until the section's data has loaded, so an address with `?tab=context` opens Story first and then Context; a failed read shows the tab with its problem mark. An eligible story without a run shows "This story has no context cards yet." **Gather context** ("Gather more context" once the story has a run; `useGatherAction` around `useGatherContext`, `.context/story-context.md`, "On demand") is in the page's action bar. It starts an editor's run as a polled background task with a progress toast ("Gathering context..."), then reads the section again and says "Context gathered"; a refusal (409) or a failed run ends in an error toast with the server's reason, a failed run's kept until dismissed. It is a `ReasonButton`, closed with its reason while web search is off, the story is not eligible, or a run of the story is running (its task in this tab, or the newest run `running`, during which the section is read again every 5 seconds). A line says what the newest run did and when (built, kept no card, skipped, failed with its error, running), noting when the cards shown are an earlier run's; it does not say whose run it was, which is not recorded. Then how many cards readers see and where ("1 beside the text, 1 beside Why This Matters, 3 under More context"), how many are hidden, and that an unpublished story shows none. The cards are listed in groups by where they sit (Beside the text, Beside Why This Matters, More context), each with its kicker, heading, phone line, sources, as-of date and "placed by an editor"; a hidden card is struck through with a Hidden tag and "Readers no longer see it; nothing was deleted." Each row has a place select ("Where X sits"; the story's paragraphs and points with their start, and More context; disabled only for a hidden card, since every shown card may move; an In numbers card stored before 2026-11-17 is not listed) and Hide/Show, each change confirmed by a toast. "Hide all context" asks first in a `ConfirmDialog`; once every card is hidden it becomes "Show all context", which does not ask. "See it on the story page" opens the published story in a new tab. "What the run did" (`ContextRunView`, a closed disclosure) gives each slot's outcome (found, found with a search of its own, reported by the story, "searched, nothing sourced, so no card" for a response not found, nothing the sources support, not needed; a search an earlier run made counts as the slot's), what it built on earlier runs (facts carried over, each search not made again, results already read; nothing on a first run), the searches with cache hits and results left out, the checks' tally with each dropped fact and card line and its reason, and the cost (AI, web search, the story's total, to a tenth of a cent). Who hid a card, and when, is not recorded, so the section does not say. Every control is `type="button"`, since it sits in the form; changing the cards never touches the form's own fields
- **Sticky bars**: the action bars (the podcast episode's, the story page's actions with Save and Cancel; `STICKY_ACTION_BAR` in `components/admin/stickyActionBar.ts`) sit at the end of the page in flow (`sticky -bottom-4 lg:-bottom-6`, negative margins to the edges of `<main>`'s padding: `<main>` is the scroll container and a `bottom-0` would stick at its padding edge, leaving a strip below the bar that content scrolls through) rather than `fixed`, so they never cover content, and below the toasts (`z-10` against `z-50`). The story page is a flex column at least as tall as `<main>` (`min-h-full`, the form `flex-1`), so its bar sits at the bottom of the view under a short tab too, not halfway up. The story page's tab list is pinned the same way at the top (`STICKY_TAB_LIST` in `components/admin/stickyTabList.ts`: `sticky -top-4 lg:-top-6`, opaque on the page's `bg-neutral-50` with its bottom border and a light shadow, `z-10`, so the bar's More menu, later in the page, still opens over it); on a phone it sits under the admin header, which is outside `<main>`. Its panels give every descendant a scroll margin (`CLEAR_OF_STICKY_BARS`), so a field reached with Tab or Shift+Tab stops clear of both bars (WCAG 2.4.11). A tab switch made while the panels' top is under the pinned list scrolls back up until they start just below it (`revealPanels`); a switch higher up, and the tab the page opens on, move nothing, so Back's restored offset stands
- **`<main>` is `relative`**: it is the containing block for absolutely positioned descendants, above all `sr-only` text such as table captions. Without it that text resolves against the document, sits wherever it falls in the scrolled content, and makes the window itself scroll past the one-screen shell into blank space (the sidebar's `<aside>` is `relative` for the same reason).
- **Sortable tables**: every admin table whose rows are all loaded sorts by its columns through `useSortableRows` and `SortableHeader` (`components/ui/SortableHeader.tsx`): a button in each header with `aria-sort` on the `th`, numbers starting largest first and text A to Z (a column's `firstDirection` overrides, e.g. dates newest first), a second click flipping it, empty values always last, ties in the order the server sent. Sort state is per table and not in the URL. Issues sort parents and, within each parent, its children, so the hierarchy holds. Not sortable: Stories (paged on the server, sorted by its own control), Feedback (paged), Jobs (grouped into chains in run order) and the Stats rating and status breakdowns (fixed bucket order), and the podcast Stage and Status badges (no natural order).
- **Sidebar badges**: `NavItems` takes a `badgeCounts` map (`layouts/navBadges.ts`), one per badged item: Feedback (unread count) and Notices (unseen count), each polled every 60 s. The Notices badge is red while any unseen notice is `critical`, brand-colored otherwise; the color is never the only signal, so a badged link's accessible name carries the count in words ("Notices, 3 unseen, 1 critical") and the visual badge is `aria-hidden`.
- **Notices** (`.context/admin-notices.md`): the Notices page lists every owner alert newest occurrence first, 25 a page, with the source and unseen filters in the URL. An unseen row is tinted and carries an "Unseen" badge (text, not color alone); expanding a row or its Mark seen button marks it seen, except that in the "Unseen only" view (where the Dashboard card links) expanding does not, since a seen row drops out of that list on refetch before it can be read; a later page that empties goes back to the last page with notices; "Mark all seen" applies to the current source filter without a confirm (a recurrence reopens a notice anyway). There is no delete: retention prunes. The Dashboard opens with an "Unseen notices" card (newest 5, hidden when there are none). Hooks in `hooks/useNotices.ts`; both mutations invalidate `['admin','notices']` and `['noticeCount']`.
- **Dashboard** (`/admin`): only what needs the owner and the high-level numbers, in this order: Waiting on you (`WaitingOnYouCard`, from `GET /api/admin/jobs`: each chain paused after a step whose Review switch is on, linking to where its work waits, the newsletters, podcasts or stories page, or stopped at a failed step, each with the Jobs page's Continue or Resume button; a chain held for a step's set time goes on by itself and is not listed, nor is a failed `build_story_context`, which does not stop its chain (its Error stays on its row on the Jobs page, `.context/scheduler.md`, "Chains"), and a draft shows here only when its step has Review on, owner 2026-11-17), Unseen notices (`UnseenNoticesCard`, newest 5), Unread feedback (`UnreadFeedbackCard`, newest 5 with category, message and age, linking to `/admin/feedback?status=unread`), all three hidden when empty; a spending summary (`SpendingSummaryCard`: this month's total so far, the month at this pace, last month's total, and a badge per row whose warning level is passed or about to be, linking to the Spending page); and Stories, the last 7 and the last 30 days from `GET /api/admin/stories/recent-stats` (crawled in the window, of those screened and fully assessed with their share, and published in the window whenever crawled), linking to Stats. No jobs table: the Jobs page and the notices cover them. An old spending notice's link to `/admin#spending` is sent on to `/admin/spending`.
- **Spending page** (`pages/admin/SpendingPage.tsx`, `/admin/spending`; `hooks/useSpending.ts`; the rules are `.context/scheduler.md`, "Spending"): the header names the month so far ("November so far (16 of 30 days)"), then a table of `GET /api/admin/spending` with columns Job, AI, Web search, This month, Month at this pace, the two months before by name, and Warn at; a `tbody` per group with its chain's name (or "Other") as a `rowgroup` header, each row's job as a `row` header, and the total ("All jobs") in the `tfoot`. The server decides the rows, their order and whether a level is passed or heading past at this pace; such a row shows a "passed $X" or "on pace to pass" badge beside its pace, in amber. Zero shows as a dash. The podcast's voice characters are a line in the group holding the podcast jobs. A Warn at field is a text field with a hidden label ("Warning level for Research Stories") that saves when it loses focus (Enter blurs it): "$25", "25" and "1,200" save whole dollars, an empty field (or "none") clears the level, an unchanged value saves nothing, and anything else is put back with an error toast; a success toast names the job and the level, and the overview is re-read. A spending notice links to `/admin/spending`
- **Clear site cache** (Dashboard header button, `POST /api/admin/cache/clear`, admin and editor): empties every in-memory server cache that holds what visitors see, so their next request reads the database. Each such cache registers itself where it is created with `registerPublicCache()` (`server/src/lib/publicCaches.ts`); a new public cache must register too, or the button misses it. Registered: homepage, issues, sources, RSS feeds, sitemap, podcast feed, related stories, story link-preview pages and images, feed favicons, and the client shell, which is only marked stale (the next story page revalidates it and keeps the last good copy if the fetch fails). Caches visitors never read (search-query embeddings, social metrics) stay out. Costs: each story's related list is re-ranked by one small-tier model call on its next view. Limits: it does not reach copies already in visitors' browsers, which keep a response for its `Cache-Control` max-age (60 s to 5 min for most API reads, 15 min for RSS, 1 h for the sitemap, 1 day for feed favicons, 3 days for related stories), and it clears only the instance that answers, which is the whole cache while the API runs as one Render instance. The toast reports how many entries were dropped
- **Feedback** (`/admin/feedback`): status and category filters in the URL (`?status=`, `?category=`; `correction` is "Correction (story error)"). A correction shows the story it was reported from under the message (`story` in `GET /api/admin/feedback`), linked to its public page while published, else its title and status; "Story deleted or not given" when the link is gone (`.context/public-website.md`, "Feedback")
- **Feed changesets** (Feeds page header): "Import changes" opens a side panel that previews an uploaded JSON file of feed changes and applies it all or nothing; the info icon beside it opens the copyable agent instructions for writing one (`.context/feed-management.md`, "Changesets"). "Export" beside it downloads or copies the feeds with problems, or all feeds, as JSON, and copies two agent prompts with that JSON and the changeset instructions inside, one to fix the feeds with problems and one to analyze coverage gaps (`.context/feed-management.md`, "Export")
- **Carousel ZIP download** uses `response.blob()` + `URL.createObjectURL` + auto-click download
- **Files built in the browser** (subscribers CSV, feed export) download through `downloadFile()` (`lib/download.ts`), which revokes the object URL only after the click
- **Cron editing** is inline in the jobs table with save/cancel
- **Issue slug** auto-generates from name in create mode
- **Issue hierarchy** supports one level of nesting (parent/child). Issues table shows children indented under parents. Edit form has optional parent selector and static content editors (evaluation criteria, sources, make-a-difference links). Feed selector shows hierarchical issue dropdown.
- **Subscribers page** is read-only: `GET /api/admin/subscribers` (service `subscribers.ts`) reads all `PendingSubscription` rows and all Plunk contacts, dedupes the DB side by email, and reconciles by lowercased email into summary counts + a table (DB status vs Plunk status, with "drift" rows). Plunk is the authoritative list — every Plunk contact is shown, sorted subscribed-first, then unsubscribed, then rows absent from Plunk (drift first within a group). Plunk is best-effort: if it's unavailable (`PROJECT_DISABLED`) or the bounded fetch only partially completes (the 10 s deadline, a failed later page, or a paging fault: more pages announced without a cursor, or a repeated cursor, which `contactPages` in `plunkContacts.ts` throws on), the page still renders the DB side with a notice; reaching the 100-page cap marks it truncated instead. An "Export CSV" action downloads the reconciled rows client-side (`lib/subscribersCsv.ts`) for an email-address backup.
