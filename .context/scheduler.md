# Job Scheduler

The scheduler runs jobs in-process using `node-cron`, with configuration and run history stored in the `job_runs` database table. No external job queue infrastructure is needed.

## How It Works

On server startup, `index.ts` calls `startScheduler()`, which runs `initScheduler()`:
1. Loads all job definitions from the `job_runs` table
2. For each enabled job with a valid cron expression, registers a cron task. A job is skipped (logged) if it is disabled, has no handler in `JOB_HANDLERS`, or has a cron expression that fails `cron.validate`. The expression is read on the server's clock (UTC on Render), except for a job listed in `jobs/jobTimeZones.ts`, which is registered with node-cron's `timezone` option and read on that zone's clock, summer and winter time included. Today that is only the two podcast publish jobs, `publish_podcast` and `publish_uplifting_podcast` (Europe/Berlin). `GET /api/admin/jobs` returns each job's `timeZone` (null for the server's clock), and the Jobs page shows it beside the schedule. It also returns `note` and `warning` (`jobs/jobNotes.ts`, read at each request, so the values a note names come from config). The note says in plain words what the job does and the rules its name does not tell (what it skips or waits on, its limits, its relation to other jobs); the Jobs page shows it behind an info icon beside the job's name, on hover, keyboard focus or a tap (`InfoTip`, `.context/accessibility.md`), and a job without one shows no icon. The warning is a state the owner must notice, kept visible under the name: today only the research step's, while research is switched off. Neither names a setting, function or file (`jobNotes.test.ts` checks every job's text).
3. Collects the overdue jobs (more than 2× the estimated interval since `lastCompletedAt`; see Overdue detection), sweeps for interrupted runs (see Interrupted runs) and starts one catch-up chain that runs the overdue jobs and the interrupted ones it resumes one after another, in pipeline order; a second sweep follows once a lease live at the start would have run out
4. Logs which jobs were registered, skipped, or queued for catch-up

**Boot retry**: if step 1 fails (database down at restart), `startScheduler()` retries on an unref'd timer — 5 s doubling to a 5 min cap, forever (`config.scheduler`). After 3 failed attempts it sends one `critical` notice ("Scheduler could not start", key `job-failure:scheduler`). With the database down that notice usually cannot be stored, only forwarded to `WEBHOOK_URL` where one is set, so when the scheduler finally starts after such an alert it records a `warning` notice under the same key ("scheduler started after N failed attempts: <reason>"); a start with no earlier alert records nothing. `stopScheduler()` cancels a pending retry. Without this the web service would look healthy while no job ran until the next deploy.

## Reliability Features

**Overlap prevention** (ADR-0017; lease timing ADR-0020): two guards, and every trigger path goes through `runJob`: cron ticks, the boot catch-up and the admin manual run.
- **In this process**, `runningJobs` (a `Set<string>` in `scheduler.ts`) is the fast path: a job already in it is skipped with a warning log, without touching the database.
- **Across processes** (old and new instance during a zero-downtime deploy, or a second process on the same database), the **job lease** on the job's `job_runs` row (`locked_by`, `locked_until`; `jobs/jobLease.ts`). `claimJobRun` takes it and starts the run in one conditional `UPDATE` on the database clock: it sets `locked_by` to this process's id (`hostname:pid:8 hex chars`), `locked_until` to now + `config.scheduler.leaseSeconds` (120), `last_started_at` to now and clears `last_error`, only where no live lease exists (`locked_until` null or past, or already this process's). One row: the run proceeds. No row while the job's row exists: another process holds it, and the run is skipped with an info log (`held by another process, skipping`): nothing recorded, no alert. A missing row is a failure, alerted like any other.
- While the handler runs, `withJobLeaseHeartbeat` renews the lease every `leaseRenewMs` (30 s), fenced on `locked_by = me`. A renewal matching no row logs `lost the job lease` once and stops renewing; a renewal that throws (pool timeout, database blip) is logged and the next tick tries again. The handler is not aborted (handlers are not cancellable; the podcast's own writes stay fenced by its episode lease). So a crashed holder blocks its job for at most 2 minutes, whatever the job's length.
- **Lease timing** (ADR-0020): `JOB_LEASE_SECONDS` (default 120) and `JOB_LEASE_RENEW_SECONDS` (default 30), parsed by `parseJobLeaseTiming` in `config.ts`, which refuses to start on a non-positive or fractional value or a renewal interval above half the lease. The defaults give four renewal chances per lease, so a live run loses its lease only if its event loop stalls, or its renewals fail, for about 90 s on end. Nothing in the jobs blocks the loop for anywhere near that: every database, LLM, HTTP and ElevenLabs call is async, ffmpeg runs as a child process, and the longest synchronous work is one JSDOM/Readability or cheerio parse of a page capped at `crawl.maxParseBytes` (2 MB) or one `rss-parser` parse of a feed capped at 5 MB, seconds at most even on the 0.5 vCPU instance. A renewal is one single-row `UPDATE`; Prisma's pool timeout (10 s by default) fails a starved one well inside the 30 s tick. Raise both values together (keeping the renewal at most half the lease) if a job ever gains long synchronous work, such as an in-process parse of a much larger document.
- `finishJobRun` always records the finish and clears `locked_by`/`locked_until` only where this process still holds them, so another holder's lease is never cleared. On graceful shutdown `index.ts` calls `releaseHeldJobLeases()` (beside the podcast's `releaseHeldLeases()`), so the next instance can run those jobs at once instead of up to 2 minutes later.
- **Shutdown waits for runs in progress.** `runJob` keeps each run's promise; on SIGTERM/SIGINT, after the HTTP server closes and the bulk tasks drain, `index.ts` awaits `waitForRunningJobs()` with whatever is left of the shared 9-second drain deadline (the force exit is at 10 s), bookkeeping (`finishJobRun`) included, and only then releases the leases. A job still running at the deadline is logged ("job drain timeout exceeded"), recorded as interrupted before the leases are released (`recordShutdownInterruptions`, one statement fenced on this process holding the lease; a failed write is logged, never thrown), and cut off by the exit. The next start resumes it if it is a pipeline job, or alerts (Interrupted runs, below). The window helps a run that is near its end (a newsletter build between its steps, a last cleanup batch); a long crawl relies on the resume, a podcast stage on its own recovery.
- The lease is raw SQL on purpose: the database clock for every comparison, and it works whether or not the generated Prisma client knows the columns. Rejected: `pg_try_advisory_lock` (Prisma's pool may unlock on another connection, ADR-0003), a fixed per-job lease with no heartbeat, a separate leases table.
- The admin manual run asks first (`isJobRunning`, async: in `runningJobs`, or a live lease on the database clock in any process) and answers 409 "already running", which the Jobs page and the Dashboard show as an error toast. `GET /api/admin/jobs` reports `running` the same way and leaves `lockedBy`/`lockedUntil` out of the response.

**Overdue detection**: At startup, a registered job is overdue if more than **2×** its estimated interval has passed since `lastCompletedAt` (`isOverdue`). A job that never finished (`lastCompletedAt` null: a fresh or newly seeded row) is **not** overdue; it waits for its first cron tick. Catch-up keys on `lastCompletedAt` (last finished), not `lastSucceededAt`: it exists to make up runs missed while no server was up, and keying it on success would rerun and re-alert a persistently failing job on every deploy.

**Sequenced catch-up**: the overdue jobs and the interrupted jobs a sweep resumes run as one fire-and-forget chain, **one after another**, in `JOB_PIPELINE_ORDER` (`jobs/handlers.ts`: crawl, the daily edition chain, then preassess, assess, select, research, publish, social, Bluesky and Mastodon metrics, generate and publish newsletter (each edition), generate and publish podcast (each show), Plunk poll, queued signup confirmations, story cleanup; a job missing from the list runs last); a job both overdue and interrupted runs once. Each sweep queues its batch behind the batch before it (`catchUpTail`), so the second sweep's resumes wait for the boot batch rather than overlap it, while the sweep itself records what it finds at once. Before each step the chain re-reads the job's row and skips it if it is no longer registered or enabled (disabled meanwhile) or neither overdue nor still to resume (a run finished meanwhile: its cron tick, or an earlier batch). `stopScheduler()` ends the chain before its next step. Cron ticks keep firing in parallel; `runningJobs` and the lease keep them from overlapping the chain.

The interval comes from `estimateCronIntervalMs`, a heuristic and not a full cron evaluator. It reads the hour field first:
- `*/N` means N hours.
- A comma list `H1,H2,…` means 24 ÷ (number of hours).
- A single hour means 24 h.
- Anything else (`*`, ranges) gives no estimate, so the job is **never** overdue.

That figure is then multiplied by 7 ÷ (days per week in the day-of-week field), so `0 4 * * 6` comes out at 168 h and `0 9 * * 1-5` at 24 h × 7/5, and by 30 ÷ (number of days) when the day-of-month field is a fixed day or list (`0 3 1 * *` comes out at 30 days; a range or step there counts as `*`). The day-of-week parser understands `*`, single days (0 and 7 are both Sunday), ranges, wrap-around ranges (`5-2` = Fri to Tue) and comma lists. An unrecognized pattern (e.g. `*/2`) falls back to a multiplier of 1.

**Error tracking**: Each job run updates `lastStartedAt` at start, then `lastCompletedAt` when it finishes, either way ("Last Finished" on the Jobs page), plus `lastSucceededAt` on success or `lastError` on failure ("Last Success"; migration `20261007200000_job_run_lease_and_success` backfilled it from `last_completed_at` where `last_error` was null). The status badge stays as it was: a failed run already shows **Error**. All three times come from the database clock, so the "Incomplete" comparison below compares like with like. Failed jobs don't block subsequent runs. `runJob` never rejects: a failed start or completion write counts as a job failure (a failed start write means the handler never runs), a failed error-path write is logged (`failed to record job failure`), and the job always leaves `runningJobs`. Cron ticks go through `launchJob`, which adds a defensive `.catch`, and the catch-up chain has its own `.catch` (a failed re-read ends the chain; the remaining jobs wait for their schedule). A rejection escaping here used to crash the process (Node exits on unhandled rejections); there is deliberately no process-wide `unhandledRejection` handler, so any other escape still crashes visibly. A **hard kill** (OOM, SIGKILL) bypasses the finish writes, leaving `lastStartedAt` newer than `lastCompletedAt`; the admin Jobs table surfaces that as an **Incomplete** (red) status rather than a stale **OK**, so a crashed run is visible (see `JobStatusBadge.tsx`). Incomplete lasts only until the next scheduler start's sweep records the run as interrupted, which turns it into **Error** with the reason (Interrupted runs, below); until then the badge's tooltip (on hover and keyboard focus; the Dashboard dot's `title`) gives the run's start in UTC and says so.

**Run bookkeeping**: A run starts by adding the job to `runningJobs`, then claims the lease, which in the same statement writes `lastStartedAt = now` and clears `lastError` (`interrupted_runs` is left as it is, so a resumed run that is cut off again counts on). The handler is called only after that claim succeeds, under the heartbeat. On success the run writes `lastCompletedAt` and `lastSucceededAt`. On failure it writes `lastError` and `lastCompletedAt` and calls `notify(jobFailureNotice(jobName, error))`. Both finish writes set `interrupted_runs` to 0 and release this process's lease. Either way the job leaves `runningJobs` in a `finally`.

**Interrupted runs** (`jobs/interruptedRuns.ts`, statements in `jobLease.ts`): `job_runs.interrupted_runs` counts the consecutive runs of a job that were cut off before they finished; any normal finish, success or failure, resets it. Recording an interruption writes, in one statement on the database clock, `last_error` = a plain-English reason, `last_completed_at` = now, `interrupted_runs` + 1, and clears the lease. The Jobs page then shows **Error** with that reason. Two paths record one:
- **Graceful shutdown**, for each job still running at the drain deadline, fenced on this process holding the lease: "Interrupted: the server shut down (deploy or restart) N min into the run, before it finished." No notice here (it must be quick, and a deploy is routine).
- **The sweep** at the scheduler's start (`sweepInterruptedRuns`), for every row whose run started, has not finished since and holds no live lease, so its process died without writing anything: "Interrupted: the server stopped without shutting down (likely out of memory or a forced restart) while this run was in progress (started <YYYY-MM-DD HH:MM> UTC)." Each such run gets a job-failure notice (warning, title "Job <name> interrupted", the reason and what happens next). A row whose lease is still live is left alone: a run in this or another process, the old instance during a zero-downtime deploy (Render boots the new instance before it SIGTERMs the old one), or a dead holder whose lease has not run out. So the sweep runs **once more** `leaseSeconds` + `interruptedRecheckSlackMs` (120 + 30 s) after the start, on an unref'd timer that `stopScheduler()` cancels; by then a live holder has renewed and is left alone, and a dead one's lease has run out. The second sweep runs whatever happened at boot, so it also catches a run the old instance started after the new one booted and recorded at its shutdown.

After each sweep, every job with `interrupted_runs` >= 1 is settled:
- **Resumed** (queued on the catch-up chain, log `interrupted, resuming`) when it is scheduled in this process (enabled, with a handler and a valid expression), in `RESUMABLE_JOBS` and interrupted at most `config.scheduler.maxResumes` (2) times in a row. Resumable are `crawl_feeds`, `preassess_stories`, `assess_stories`, `select_stories`, `research_stories` and `publish_stories`: each works off what is left to do and skips what is done (a crawled feed is no longer due, a stored URL is deduped, the story stages read their input status, which each story leaves when its own write commits, and the research step skips every story with a pipeline run, the one cut off included, which the publish gate stops waiting for once its run is stale), so a rerun does only the rest and repeats no side effect. A run the shutdown recorded is resumed silently; one the sweep just found dead gets its notice saying it is resumed.
- **Not resumed** otherwise (log `interrupted, not resuming`): one notice saying why (not scheduled; not resumable, since a rerun could repeat a send or a post; or interrupted N times in a row, the crash-loop guard against a run that kills the server each time), and `interrupted_runs` back to 0 so a later sweep does not repeat it. `last_error` stays. The job waits for its schedule or a person. Never rerun on their own: the newsletter and podcast jobs, social posting and metrics, the Plunk poll, queued confirmations and the story cleanup (`interruptedRuns.test.ts` holds a tripwire on the senders).

Left open: an old instance that is SIGTERMed more than about 2.5 minutes after the new one booted is recorded but only resumed at the next start (or its next scheduled run); a live run whose heartbeat stalls past its lease can be swept and resumed elsewhere, the lease's own risk (Lease timing, above).

**Disabling the scheduler**: `SCHEDULER_ENABLED=false` (also `0`, `no`, `off`, case-insensitive; default on; `config.scheduler.enabled`) is for a second process run against the production database. That process schedules nothing: `startScheduler()` logs `scheduler disabled (SCHEDULER_ENABLED)` and loads no job, `reloadJob` saves nothing into the schedule (an enable or schedule change made through that process is saved to the row and picked up by the scheduling process at its next restart), and `index.ts` skips `checkPodcastConfigAtBoot`, whose alert concerns scheduled podcast runs. The admin **Run** button still works there: it is a person's explicit action, and the lease keeps it from overlapping the main instance.

**Failure notifications** (ADR-0028): a failed run becomes an admin notice (`.context/admin-notices.md`), one row per job (key `job-failure:<jobName>`) that each new failure reopens as unseen with a higher count. `jobFailureNotice` (`lib/notify.ts`, `JOB_FAILURE_HOMES`) files the four newsletter jobs under Newsletter, the four podcast jobs under Podcast and `send_queued_confirmations` under Subscriptions, linking their admin pages (`/admin/newsletters`, `/admin/podcasts`, `/admin/subscribers`); every other job goes under Jobs, linking the Jobs page. `notify()` also forwards it to `WEBHOOK_URL` when that is set; the variable is optional and nothing checks for it.

**Hot reload**: When a job's cron expression or enabled flag is updated via the admin API (`PUT /api/admin/jobs/:jobName`), the scheduler reloads only that job (`reloadJob`) — stopping its cron task and re-registering it from the database. It does not run an overdue check. No server restart needed. On reload, the job is registered again only if it is still enabled, has a handler in `JOB_HANDLERS`, and has an expression that passes `cron.validate`; otherwise it stays unregistered. `PUT /api/admin/jobs/:jobName` rejects an invalid cron expression with 400 before saving.

**Enable checks**: a request that sets `enabled: true` first asks `jobEnableRefusal` (`jobs/jobEnableChecks.ts`), a map of job name to precondition. A job whose every run would block on a missing setting is refused with 422 and nothing is saved; the error names what is missing, and the Jobs page shows it in the error toast. Today `generate_podcast` and `publish_podcast` check the podcast configuration as the automatic run needs it (voices, `ELEVENLABS_API_KEY`, `BUNNY_STORAGE_ZONE`, `BUNNY_STORAGE_PASSWORD` outside a dry run, i.e. in production; not `WEBHOOK_URL`), and `publish_newsletter` checks `PLUNK_SECRET_KEY`; `generate_uplifting_newsletter` needs the newsletter editions open (both `PLUNK_FULL_EDITION_SEGMENT_ID` and `PLUNK_UPLIFTING_SEGMENT_ID`), and `publish_uplifting_newsletter` those and `PLUNK_SECRET_KEY`; `generate_uplifting_podcast` and `publish_uplifting_podcast` need the Actually Uplifting podcast open (`upliftingShowProblem()`: `PODCAST_UPLIFTING_ENABLED`, its confirmed description and its artwork) and then the podcast configuration. Disabling a job or changing only its schedule checks nothing.

**Manual triggers**: Every job can be triggered via `POST /api/admin/jobs/:jobName/run`, which runs the job in the background regardless of schedule, or answers 409 while it is already running in this or another process.

## Chains

(ADR-0059; `jobs/chains.ts`, `jobs/chainDefinitions.ts`.) A **chain** is a job whose run is its steps, one after another, from one start time, instead of separate schedules with guessed gaps between them. It is an ordinary job row (schedule, on/off, lease, overdue catch-up, failure notice, Run button), plus a flex cut-off and a deadline. Its steps are ordinary jobs that **never run on their own schedule**: `initScheduler` and `reloadJob` skip every job in `CHAINS`, and the admin API refuses a schedule for one (400). Each step still runs through `runJob`, so it keeps its own lease, bookkeeping, failure notice, notes and Run button.

- **Step switches** (the Jobs page's Enabled and Review switches, the same Enabled switch as every other job, on the step's own row): **Enabled** (`enabled`; off: skipped, the next step runs on what there is), **Review** (`pause_for_review`, on an enabled step: runs, then the chain stops, records `resume_step` = the next step with `resume_reason` 'review' and an info notice `chain-review:<chain>`, and waits for a person's **Continue** on the Jobs page, `POST /api/admin/jobs/:chain/continue`). A Review on the last step has nothing to wait for. The chain's run counts as a success when it pauses. Because Off is `enabled = false`, everything that reads a step's own flag keeps working: the enable checks, research's switch-off check before each story and the publish gate.
- **A failed step stops the chain.** Nothing after it runs; the chain's run fails with "Stopped at <step>, so the steps after it did not run: <error>" (one notice for the step, one for the chain), and `resume_step` holds the step with 'failed', so the Jobs page offers **Resume from <step>**. No item-failure threshold: a step fails only when its job fails.
- **Where a run starts.** A scheduled run, Run on the Jobs page and a boot catch-up start from the first step, also after a pause or a stop: each step works off what is left, so a fresh start is safe and a forgotten review never blocks the pipeline. Only a run cut off by a restart goes on from the step it was in: while running, the chain keeps `resume_step` = its current step ('running'), and a run that starts with `interrupted_runs` > 0 starts there, or after it when that step is not in `RESUMABLE_JOBS` (a cut-off social post is not posted again). The chains are in `RESUMABLE_JOBS`; an interrupted step of a chain is left to its chain by the sweep (count cleared, no notice, not rerun alone).
- **A step's "not before" time** (`not_before`, "HH:MM" or a weekday and a time such as "Sat 07:00", on the step's own clock: its `jobTimeZones.ts` zone, else UTC; set in the step's details panel): a chain that reaches the step earlier holds there. It records `resume_step` = the step, `resume_reason` 'waiting' and `resume_at` = the first such time after the run's start (`chain_started_at`, written when a run starts from its first step), ends its run as a success (lease let go), and sets a timer; at `resume_at` the timer goes on through `runJob` (`runChain(chain, 'continue')`) unless a person went on meanwhile or switched the chain off. A step reached after its time runs at once, so a late run never waits a day. The Jobs page shows "<step> runs at HH:MM UTC." with **Run <step> now**, which goes on at once. The timers live in the process: `initScheduler` sets them again from the rows (`resumeHeldChains`; one past its time goes on at once) and `stopScheduler` drops them. The next scheduled run starts from the first step and drops a hold left over. The daily edition's social post is held until 11:30.
- **A step already running** when its chain reaches it (a run by hand, another process) is waited for, checking every 15 s up to `config.chains.stepWaitMinutes` (120), then run, so the chain never goes on past a step that has not run for it; still running after that is a failure.
- **Flex cut-off and deadline** (`flex_until`, `deadline`, "HH:MM" UTC, set on the chain's card): each run takes the next such time after its start (`nextClockTime`). After the cut-off every model call in the chain goes at standard price, Flex switches or not. After the deadline `research_stories` starts no other story (those in flight finish and are applied, the rest wait as stories past its per-run limit do), so publishing follows within minutes. Only the daily edition offers a deadline on the Jobs page.

**Publishing time.** With the daily edition starting at 23:00 UTC, stories publish as soon as research is done, by about 05:00 UTC at the latest, instead of at a fixed 02:45 (owner direction 2026-11-16). Publishing stays once a day, and so does assessing: one batch of the day's crawled stories, at night, at the flex price. The social post follows at 11:30 UTC.

## Cost and flex

Every run, chains and steps alike, runs in a run scope (`lib/runUsage.ts`) that the OpenAI fetch (`services/openaiFetch.ts`; `.context/llm-analysis.md`, "Flex processing and run costs") reads: the job's Flex switch (`job_runs.flex`, on by default, a switch on the Jobs page for jobs that make model calls, `MODEL_JOBS` in `services/job.ts`), the chain's cut-off and deadline, and a tally of calls, flex calls, refused-flex fallbacks, tokens, USD as billed and USD at standard price, plus research's web searches. A step's tally counts for its chain too. `finishJobRun` stores the tally in `job_runs.last_run_usage`, on a failure too (what the run spent until then); an interrupted run's record clears it. The Jobs page shows, for each job, the last finished run's length (start to finish) and cost, with calls, flex use and the standard-price figure on hover. The figure prices tokens at `config.llm.modelPrices` list prices: an estimate, not the invoice.

**The podcast jobs** keep their retry policy in podcast code, not here (ADR-0013; `.context/podcast.md`, "Automation"). `generate_podcast` does nothing outside its UTC Friday window (00:00 until 20:00), so a boot catch-up on another day, or a manual Run then, never starts an episode. Inside it, each slot resumes the week's episode; failures are counted on the episode, and at 3 (or on an error a retry cannot fix) the episode is blocked and the run fails once, so one job-failure notice is recorded and later slots skip quietly. `publish_podcast` does nothing on any day that is not a Saturday in Berlin, publishes only an episode that has been ready for 8 hours, and re-reads its own row's `enabled` flag before publishing. When it finds nothing to publish on its Saturday while enabled, it records the missed-week notice ("No podcast episode ready to publish this Saturday", with the reason), at most once per ISO week: the week is claimed in `podcast_missed_week_alerts` first, so a retry, a manual Run or a boot catch-up that day stays silent. A never-completed row never runs at boot, so their freshly seeded rows wait for a cron tick; the `last_completed_at` their migration seeds (from before that rule) goes stale after two weeks, so a boot catch-up can still launch either job on any day once it has run: the Friday window and the Saturday guard are what make that harmless. A `generate_podcast` run holds the job lease, and `advanceEpisode` still claims the episode lease inside it: the two are independent (`.context/podcast.md`, "The lease"). At boot, when any of the four podcast rows is enabled, `checkPodcastConfigAtBoot` (`index.ts`) records missing podcast settings as a notice (key `podcast-config`); enabling any of them from the Jobs page is refused while a setting is missing (Enable checks, above). The two Actually Uplifting jobs run the same handlers for the other show (`runGeneratePodcast(now, 'uplifting')`, `runPublishPodcast(now, 'uplifting')`), each re-reading its own row, and claim the missed-week alert per show.

## Adding a New Job

To make an existing job a chain's step, add it to `CHAINS` (`jobs/chainDefinitions.ts`) at its place; a new chain also needs its handler in `JOB_HANDLERS`, `RESUMABLE_JOBS` (`jobs/interruptedRuns.ts`) and a row with its schedule. A job whose work includes model calls goes in `MODEL_JOBS` (`services/job.ts`), so the Jobs page offers its Flex switch.

1. Create handler in `server/src/jobs/yourJob.ts` exporting an `async function runYourJob(): Promise<void>`
2. Register handler in `server/src/jobs/handlers.ts` by adding to the `JOB_HANDLERS` map, and add the name to `JOB_PIPELINE_ORDER` there (the boot catch-up order) at its place in the pipeline
3. Add its `job_runs` row (`jobName`, `cronExpression`, `enabled`) in a migration with `ON CONFLICT DO NOTHING`, as `20261025120000_publish_newsletter_job` does, so existing and new databases both get it, and to `src/scripts/seed-jobs.ts` (`npm run db:seed:jobs`), which lists every job. The scheduler runs only jobs that have a row
4. Add the name to `JobName` (`shared/types`) and the admin's `JOB_DISPLAY_NAMES` and `JOB_PIPELINE_ORDER` (`client/src/lib/constants.ts`)
5. Give it a note in `jobs/jobNotes.ts` when its rules are not obvious from its name (what it skips or waits on, its limits, a switch it needs), with any config value read from `config`

## Admin API

| Endpoint | Description |
|----------|-------------|
| `GET /api/admin/jobs` | List all jobs with status, last run times, errors |
| `PUT /api/admin/jobs/:jobName` | Update cron expression or enabled flag (422 when an enable check refuses) |
| `POST /api/admin/jobs/:jobName/run` | Manually trigger a job (runs in background; 409 while it is running in any process) |
| `POST /api/admin/jobs/:jobName/continue` | A chain waiting for review, or stopped at a step: go on from that step (400 with nothing to continue, 409 while it runs, 404 for a job that is not a chain) |

`PUT` also takes `flex` (any job), `pauseForReview` (a chain's step only) and `flexUntil` / `deadline` ("HH:MM" or null, a chain only); a setting on the wrong kind of job is refused with 400 and nothing is saved.

## Concurrency

LLM-powered jobs (preassess, assess, select) process work items in parallel using a counting semaphore to cap concurrent LLM calls. Default concurrency is 10 per job type, configurable via environment variables:

| Env Var | Default | Controls |
|---------|---------|----------|
| `CONCURRENCY_PREASSESS` | 10 | Max concurrent pre-assessment batches |
| `CONCURRENCY_ASSESS` | 10 | Max concurrent full assessments |
| `CONCURRENCY_SELECT` | 10 | Max concurrent selection groups |
| `LLM_DELAY_MS` | 500 | Minimum delay between LLM calls (serialized) |

Set any concurrency to `1` for sequential processing (original behavior). The rate limiter serializes delays across all concurrent workers via a timestamp-based approach (`nextAvailableTime` in `llm.ts`), so each LLM call waits at least `LLM_DELAY_MS` after the previous one regardless of concurrency level. All jobs use `Promise.allSettled` so individual failures don't abort the batch.

The Semaphore utility is at `server/src/lib/semaphore.ts`.
