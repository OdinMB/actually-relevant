# Model Eval Harness

Compares OpenAI models and reasoning efforts on this project's real call sites, using stored data. It was built for the GPT-6 migration (gpt-5-nano/mini → gpt-6-luna, gpt-5.2 → gpt-6-sol) and is meant to be re-run whenever a model or undated alias changes; since 2026-10-27 its large-tier suite compares gpt-6-sol with gpt-6.1-sol (below). It never writes to any database and never changes production settings.

## Running

```bash
npm run eval:models --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --api-check --budget 0.1   # 1 trivial call per arm and 1 cache probe per model, no DB
npm run eval:models --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --dry-run                 # sample fixtures, print estimates, no API calls
npm run eval:models --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --suites related --limit 2 # smoke run (6 calls)
npm run eval:models --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval                           # full run (default --budget 18)
```

| Flag | Meaning |
|------|---------|
| `--out` | Output folder (required). Use a dated folder under the gitignored `DOCS/`; `--prefix server` makes the path relative to `server/`. |
| `--suites` | Comma list of `preassess, assess, dedup, related, social, large` (default: all) |
| `--limit N` | At most N fixture items per suite part (partial runs; verdicts are then not evidence) |
| `--dry-run` | Sample fixtures and print per-suite call counts and $ estimates; refuses any uncached API call |
| `--api-check` | One trivial structured-output call per arm of the selected suites and of the research steps (`research/pipeline.ts`'s `STEP_ARMS`, the extraction steps at their own effort among them); proves each model accepts `reasoning_effort` through the production client. Then one cache probe per model that takes the cache controls (`apiCheck.ts`): a split prompt whose fixed block is about 1,900 tokens, sent with the breakpoint, which proves the API accepts `prompt_cache_options` and `prompt_cache_breakpoint` and prints the tokens written and read (a warning when it reports neither; the check fails only on a call that does not answer). Needs no database. |
| `--budget` | USD stop for live calls (default 18; values above 20, this project's cap `MAX_BUDGET_USD`, are refused) |
| `--concurrency` | Parallel calls (default 4; the related-stories suite always runs one at a time for latency) |
| `--refresh-fixtures` | Resample fixtures instead of reusing `.cache/fixtures.json` |
| `--floor YYYY-MM-DD` | Earliest crawl date for the pre-assess, assess, dedup and social-post samples (default 2026-03-01, when the current prompts and issue set were in place). Move it earlier only for a database copy older than that; the report states the floor. Cached fixtures with a different floor are resampled, so pass the same `--floor` on every run against one output folder. |
| `--assess-size N` | Full-assessment stories to sample (default 50, phase 1's; at most 300). The minimums scale with it (`assessQuotas`: half rated 4-6, a fifth non-English, a tenth Han-script). Recorded in the fixtures; cached fixtures with another size are resampled. |
| `--exclude <folders>` | Comma list of eval folders whose cached pre-assessment and full-assessment stories leave those pools, so a fresh sample shares no story with a spent one. Recorded by folder name; cached fixtures with other exclusions are resampled. |

The run needs `DATABASE_URL` reachable (the local Postgres service must be running) except for `--api-check`. It prints only `local`/`remote` for the database and `present`/`missing` for `OPENAI_API_KEY`, never values.

### Large tier: gpt-6-sol vs gpt-6.1-sol (2026-10-27)

The large tier's default moved to gpt-6.1-sol on 2026-10-27 (`.context/llm-analysis.md`), to be merged only after this comparison and the owner's podcast listening check. The large-tier suite reruns gpt-6-sol@medium, production's model until then, against gpt-6.1-sol@medium on its three call sites. Run it from the repository root, in a new folder: the rating deliverable is written only into a folder that has none, so the 2026-09-24 folder cannot take the new sets.

```bash
npm run eval:models --prefix server -- --out ../DOCS/2026-10-27_gpt61-sol-eval --suites large --api-check --budget 0.1   # 2 trivial calls, no DB: both models take reasoning_effort and json_schema
npm run eval:models --prefix server -- --out ../DOCS/2026-10-27_gpt61-sol-eval --suites large --dry-run                  # samples fixtures from the local DB, prints the estimate; no API calls
npm run eval:models --prefix server -- --out ../DOCS/2026-10-27_gpt61-sol-eval --suites large --budget 5                 # full run: 20 selection groups, 4 newsletters, 1 podcast, both arms
```

- **Budget.** About 50 calls. The dry run's estimate assumes about 4,500 output tokens per selection call (phase 1 measured about 520 for gpt-6-sol), so it should print roughly $3 while the run itself costs about $1-2. A suite whose estimate exceeds what is left of `--budget` is skipped: if the dry run prints more than about $4.5, pass `--budget` at the estimate plus $1 (20 at most).
- **No smoke run in this folder.** A `--limit` run writes `rating-sets.json` from its few items, and the full run then leaves that partial deliverable in place. Smoke-test in a scratch folder, if at all.
- **The gate** is phase 1's, now against gpt-6-sol: exact-count compliance on every selection group (relaxed only to gpt-6-sol's own rate), and on each call site no more declines or failed calls than gpt-6-sol, nor more non-compliant newsletters, dialogues failing validation or sentences over 18 words. The declines catch the over-refusal some users report for 6.1 Sol. The large row recommends gpt-6.1-sol only when all three call sites pass.
- **What to read:** in `results.md`, the large row of "Recommendation per tier", "Is gpt-6-sol better in any way?" and the three large-tier call sites; then rate `rating-sets.json` blind (story selection, at most 5 groups, and the podcast script; `rating-key.json` maps the labels to arms). gpt-6.1-sol's price is marked unverified: input and output as gpt-6-sol's from OpenAI's pages, cached input kept at gpt-6-sol's $0.20 as the upper bound though secondary sources report $0.10.
- **Before merging,** check that Render sets no `OPENAI_MODEL_LARGE`, which beats the default and keeps gpt-6-sol, and no `OPENAI_EFFORT_LARGE=none`, which gpt-6.1-sol rejects (the large-tier client then throws at its first use). To stay on gpt-6-sol, revert the `config.ts` default with the model ids in `llm-analysis.md` and `ai-transparency.md`.

## Outputs (in `--out`)

- `results.md` — per call site: arms, outcome counts (ok / parse failure / empty-or-declined / truncated / error / budget-skipped), p50/p95 latency, mean input/cached/output/reasoning tokens, $/call and $/month at the inventory volumes, quality metrics, the automated verdict; then the per-tier recommendation, current-vs-proposed monthly cost, "Is <large-tier baseline> better in any way?", fixture shortfalls, prices (gpt-5.2 and gpt-6.1-sol marked unverified) and spend. A "Fabricated-number spot check" section is left for a person to fill.
- `rating-sets.json` / `rating-key.json` — the owner's blind-rating sets (full assessments 12, social posts 10, podcast script 1, story selection 5 at most; the phase-1 deliverable also holds 4 newsletter intros, a set no suite drafts since the intro was removed on 2026-10-26, kept in `RatingSetSlug` so that file still validates). The key maps each item's labels to `model@effort`. **Written only when the folder has none yet** (`ratingFiles.ts`): the owner rates from this file with a local tool (which keeps its own `ratings.json`, never touched here), so a re-run or a partial run leaves an existing deliverable alone. To regenerate one set, use the recalibration's `rating-set` step, which swaps in a versioned set (`…-v2`, new item IDs) and leaves every other set byte for byte. **No model name may appear anywhere in `rating-sets.json`, item context included** (owner's decision, 2026-09-24; terms in `blinding.ts`: the eval model IDs, `Luna`, `Sol`, `nano`, and anything starting `gpt`, `ChatGPT` or `OpenAI`). Single-story items whose story or output mentions one are dropped at build time; multi-story fixtures (selection groups, newsletters, the podcast) drop such stories before any prompt is built, so no arm sees them. The written files are re-validated and a failure exits non-zero.
- `.cache/fixtures.json` — the sampled inputs, reused so prompts (and cache keys) stay stable while the DB changes.
- `.cache/calls.jsonl` — response cache **and** spend ledger, keyed by `sha256(model@effort + schema + prompt)`. Re-runs and resumes never pay twice; errors are not cached so they retry.

## How it stays safe

- **Read-only DB.** `readOnlyDb.ts` opens a session with `default_transaction_read_only=on`, or, if a pooler rejects that option, runs all reads inside one `SET TRANSACTION READ ONLY` transaction; `SHOW transaction_read_only` must be `on` before any query. `fixtures.ts` issues SELECTs only.
- **No second write path.** The eval calls prompt builders, Zod schemas and `createChatModel` directly and never the persisting service functions. It may import only `createChatModel` (`services/llm.ts`), production's prompt-input builders (all of `services/promptInputs.ts`, and `blueskyDraftInput` / `mastodonDraftInput` from `services/bluesky.ts` / `services/mastodon.ts`) the pure podcast dialogue rules (`services/podcastDialogue.ts`: `validateDialogue`, `assembleSpokenSegments`, `renderScript`, `dialogueCharBudget`) and production's research steps (`services/researchPipeline.ts`, `researchInput.ts`, `researchFilter.ts`, `researchChecks.ts`, `researchCopying.ts`, each held to no client, HTTP or retry of its own); `imports.test.ts` enforces this statically, plus that `promptInputs.ts` imports only config and prompt types, and no `lib/prisma`, `rateLimitDelay`, `withRetry` or Prisma write calls.
- **Budget.** Estimates use chars/4 (Han chars/1) input and per-suite output assumptions (Luna +25%, low ×0.4, high ×1.5). A suite whose estimate exceeds the remaining budget is skipped; live calls stop once the ledger reaches `--budget`, and call sites with skipped calls get no verdict.
- **No retries around calls.** Parse failures and declines are what is measured, so calls are not wrapped in `withRetry` (ChatOpenAI's own transport retries still apply).

## Methodology

- **Baselines are rerun.** Every suite reruns today's model on the same prompts. Agreement with stored production values is reported for the rerun too: that is the noise floor. An absolute "≥" bar is relaxed to the noise floor minus 5 points only when the baseline rerun itself misses it.
- **Winner** per call site is the lowest-effort candidate that passes every automated check. The per-tier recommendation takes the highest of those efforts across the tier's call sites (small: dedup, related, pre-assess; medium: pre-assess, assess, social pick) and flags any site not tested at that effort.
- **Baselines are constants.** Each suite's baseline arm is a constant, never read from `config`. The large-tier suite was rebased on 2026-10-27: `LARGE_BASELINE` (gpt-6-sol@medium, production's model until then) against `LARGE_CANDIDATE` (gpt-6.1-sol@medium) in `suites/largeTier.ts`, which the report's large-tier recommendation and comparison read, so the next rebase changes only those two. The small- and medium-tier suites still run the pre-switch baselines (gpt-5-nano, gpt-5-mini) from phase 1; a comparison for a change there should make today's default (gpt-6-luna) the baseline first.
- **Dedup labels** come from arm consensus; sets where the arms disagree go to two judges (gpt-5.2@high, gpt-6-sol@high) with the unchanged prompt, and pairs the judges split on are excluded. Existing clusters were made by gpt-5-nano, so agreement with them is secondary.
- **Windows are anchored on the data.** "Last N days" windows count back from the newest assessed crawl date, so a stale local DB copy still yields fixtures (the dry run warns when the anchor is over 14 days old). The fixed crawl floor is not anchored; see `--floor`.
- **Adaptations are reported.** When the data is thin, `fixtures.ts` records what it changed in `adaptations` (moved floor, extra nearest-neighbour dedup sources filling missing cluster-member slots, the synthetic social-pick scan, blinding removals with the terms that matched), and `results.md` lists them under Fixtures.
- **Prompt inputs come from production's builders.** Each call site's DB-row → prompt-input mapping is an exported pure function that the service itself calls before its model call (`services/promptInputs.ts`: assess, select, related stories, social pick, newsletter select, podcast select and script; the Bluesky and Mastodon draft inputs in their services). `fixtures.ts` and `suites/podcast.ts` call the same functions, so a change to how a service builds its input reaches the eval the day it lands; there is no copy to update. `services/promptInputs.test.ts` pins the prompts each service sends for fixed rows, so a builder refactor that changes one fails there. What stays the eval's own is the sampling: which rows are loaded (`fixtures.ts`'s SELECTs, batched per source where production queries one story) and their order, which keeps prompts and cache keys stable. Fixtures cached before the builders were shared (2026-10-25) hold inputs from the old copies, which the builders reproduce, so their prompts and cache keys stay as they were.

## Phase-2 recalibration (`eval:recalibrate`)

Checks the recalibrated rating prompts (pre-assessment and full assessment) and the tightened dedup prompt on gpt-6-luna against the owner's acceptance rules (2026-09-24), on the sample cached in `--out`: the phase-1 sample, or a fresh one (below). It needs no database and never resamples: the split and the labelled dedup set are defined on those fixtures.

```bash
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --half calibration --dry-run      # estimates + labelled-set preflight
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --half calibration --budget 5.9    # iterate here only
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --half holdout --budget 5.9        # report once the prompt is final
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --steps rating-set --budget 5.9    # full-assessment set v2
```

### A rating-prompt change on a fresh sample, with repeated runs

Both phase-1 halves are spent, so judge a further rating-prompt change on the fresh sample in `DOCS/2026-11-01_rating-eval`, run several times. Sample it first (read-only database session, no API calls; the local Docker database must be running), from the repository root:

```bash
npm run eval:models --prefix server -- --out ../DOCS/2026-11-01_rating-eval --dry-run --assess-size 150 --exclude ../DOCS/2026-09-24_gpt6-eval --floor 2026-01-01   # samples fixtures, prints the anchor and estimates
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-11-01_rating-eval --floor 2026-01-01 --steps assess --repeat 3 --dry-run                             # estimate: 3 runs × 150 stories
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-11-01_rating-eval --floor 2026-01-01 --steps preassess,assess --repeat 3 --budget 3                  # the check
```

- **The sample.** eval:models' own sampler with a larger full-assessment set (`--assess-size 150`, three times phase 1's) and every phase-1 pre-assessment and full-assessment story left out (`--exclude`), so no story the prompts were tuned on is judged again. The pre-assessment sample stays 300. Check the anchor the dry run prints (it warns when over 14 days old) and refresh the local database copy if it is stale. Pass the same `--floor` and flags on every eval:models call against the folder, or the fixtures are resampled and every cache key changes. `--half` still splits it (75/75 full-assessment stories), for tuning on one half and reporting the other.
- **What it can judge.** The preassess and assess rating checks against stored production values work on any sample. Stored values are what production wrote: stories crawled after the 2026-09-24 switch were stored by gpt-6-luna on the prompt of that day, so on such a sample the bars measure drift from current production rather than from the gpt-5-mini archive; the report states the crawl window. Phase 1's issue and emotion agreement numbers were measured on other stories, so on a fresh sample they are shown for reference and not required. The format bars stay required. The steps that read phase 1's ledger (`dedup`, `selection`, `rating-set`) are skipped there with the reason ("needs the phase-1 folder"); a folder counts as phase 1's when its fixtures' `createdAt` is phase 1's (`freshSample.ts`). `social-post` and `podcast` run on any folder.
- **`--repeat N`** (pre-assessment and full assessment, 1 to 10, default 1) runs each rating prompt N times. The response cache would answer an identical prompt from the ledger, so run k ≥ 2 calls with the schema name tagged `~run<k>` (`repeats.ts`): a distinct cache key, the same request (the schema name never reaches the API). Run 1 keeps the plain key, so an earlier single run is reused as run 1 and a later `--repeat 5` reuses runs 1-3 of a `--repeat 3`. The criteria table pools all runs (the averaged numbers against the bars; meta-commentary counts every output). Below it the report lists each run's mean offset and share at the threshold, the spread across runs (mean, range, standard deviation), and per story how often the rating differs between runs, how often the threshold split flips, and the mean spread of a story's ratings; for pre-assessment also issue and emotion disagreement. This is the run-to-run noise nobody had measured: a rating shift smaller than the spread between single runs is not evidence. The report name gains `-repeat-N`.
- **Measured noise (2026-11-01, Luna@medium, 150 stories × 3 runs).** One prompt's single-run mean offsets span about 0.03 (SD 0.01); a story's rating differs between runs for 55-59% of stories and its ≥5 split flips for 15-19%. Paired before/after with 3 runs each resolves about ±0.06 on the mean (95% half-width; 80%-power detectable effect about 0.09) and about 4.6 points on the share ≥5. Compare two prompts on the paired per-story deltas, not on whether each clears the ±0.25 bar: a 0.02 drift moved the offset from -0.27 (fail) to -0.24 (pass) with no real change. The first use (headline subject word, 27e9a43) is in `DOCS/2026-11-01_rating-eval/recalibration-all-assess-repeat-3-{before,after}.md`. That sample was drawn from a local copy ending 2026-02-08, hence `--floor 2026-01-01` in the commands above; its stored ratings come from the gpt-5-mini era.
- **Cost.** Each run is one full-assessment call per story (about $0.003 estimated, $0.0017 measured on Luna@medium), so 3 runs × 150 stories is roughly $0.75-1.25; pre-assessment adds about $0.06 per run. The fresh folder's ledger starts at $0, so `--budget` is this folder's own total.

| Flag | Meaning |
|------|---------|
| `--half` | `calibration`, `holdout` or `all` (default). Tune prompts on `calibration` only; the holdout is the result. |
| `--steps` | Comma list of `preassess, assess, dedup, rating-set, social-post, selection, podcast` (default: the three checks). `rating-set` and the ship checks run only when named; `rating-set` refuses `--limit`. |
| `--effort` / `--dedup-effort` | gpt-6-luna effort for the rating checks, the rating set and social posts (default `medium`) / for dedup (default `low`). |
| `--budget` | Cap on the **ledger total** for the folder, as in eval:models. The ledger already holds phase 1's $2.96, so pass the ledger plus this run's allowance. |
| `--repeat N` | Runs of each rating prompt (pre-assessment, full assessment), 1 to 10, default 1; run k ≥ 2 has its own cache key (above) |
| `--limit`, `--dry-run`, `--concurrency`, `--floor` | As in eval:models; `--floor` is only checked against the cached fixtures |

- **What is judged against what** (`recalibration.ts`): ratings against the stored production values (the archive the site must stay comparable with): mean offset within ±0.25 on both stages, share at or above 5 within 5 points of stored, published stories passing the pre-assessment gate ≥ 75%, issue and emotion agreement not below phase-1 Luna@medium (74.0%, 70.3%; 71.6% is reported as the aim), full-assessment format checks not below phase-1 gpt-5-mini, and no full assessment whose published fields talk about the input ("the article does not quantify…", "the supplied excerpt"; `metaCommentary.ts`, which skips the verbatim quote). Dedup: no more wrong merges than gpt-5-nano and a recall at least 15 points above nano's, on the same labelled pairs.
- **The report name says what ran.** `recalibration-<half>.md` is the report of record: default steps at the default efforts. Another effort, step list or `--limit` adds tags (`recalibration-holdout-effort-high.md`, `recalibration-all-assess-social-post.md`, `…-limit-3.md`), so a trial never overwrites it. Re-running the same command does overwrite its own file: rename a report first if you need it as a before/after reference.
- **Ship checks** (`shipChecks.ts`, rules in `shipRules.ts`) cover the other prompt changes that ship with the phase-2 switch, on the whole cached sample whatever `--half` says. `social-post`: Luna at `--effort` drafts every cached Bluesky and Mastodon post; every draft must name the story's main actor or a key number (`storyAnchors.ts`: a capitalised word the story uses mid-sentence, an acronym other than topic ones like AI or HIV, or a number the story states), stay within the limit and state no number the story lacks. Names the story never mentions are listed for the embellishment spot check but do not fail it; the report lists every draft for that read. The heuristic misses a number in words ("a quarter" for 25%) and a story whose only actor is a group ("developers"), so read the drafts it flags before calling a miss. `selection`: gpt-6-sol@medium on every cached selection group with publication dates; the gate is phase 1's (exactly N valid IDs in every group, no declines). Fixtures cached before the date field show each candidate's group crawl day. One candidate per group, the first one production selected, is re-dated to 2023-06-01 as a stale probe; the report compares how often the model keeps it with how often it picked the same stories in phase 1 without dates, read free from the ledger through the frozen phase-1 prompt (`suites/selectPhase1Prompt.ts`; never edit it). `podcast` (2026-10-06): gpt-6-sol@medium runs the podcast selection on the cached podcast pool and the dialogue on a fixed pick from it (`suites/podcast.ts`: the most relevant story per issue, then by relevance, up to 5); the gate is `checkDialogue` with no validation error (every story covered, the spoken band, a bridge opening every segment after the intro, tags, no markup) and a selection of 4-5 valid pool ids spread over the issues the pool offers. The report lists every segment's opening turn (the segue report) and the picks. This is the check CLAUDE.md asks for after a podcast prompt change; the podcast pool is not part of the spent calibration halves, so no fresh sample is needed. Both the `selection` and `podcast` steps still run gpt-6-sol, not gpt-6.1-sol, the large tier's default since 2026-10-27 (`selection` compares with phase 1's gpt-6-sol picks); until the `podcast` step follows the default, check a podcast prompt change on gpt-6.1-sol too, with the large-tier comparison above (`eval:models --suites large` in its folder). Fixtures cached before 2026-10-06 hold the old podcast shape (no ids, no relevance, each story's own issue): `suites/podcast.ts` fills ids by position and keeps their order.
- **Layout checks** (`layoutChecks.ts`, 2026-11-18) cover the two prompts the house order changed that no other check ran (`.context/prompting.md`, "Checking a changed prompt"), on the whole cached sample, only when named in `--steps`. `reclassify`: reclassification on gpt-6-luna@low (the small tier) over the pre-assessment batches; the gate is the format (no story left out, no unknown id, no issue slug off the list, no failed call), and the issue and emotion agreement with the stored values is reported beside phase 1's pre-assessment numbers (74.0%, 70.3%), not required, since it is another prompt's: read it beside the `preassess` step's on the same sample. `uplifting-select`: the Actually Uplifting selection on gpt-6.1-sol@medium (the large tier) on each cached newsletter longlist, cut to its uplifting stories when it has more than the issue carries (10), else whole, since the gate does not turn on the tone: exactly the issue's count of valid, unique ids in every case, no invalid id, no decline, no failed call; the report lists the picks for a read.
- **The split** (`splitHalves` in `sampling.ts`) alternates items in a salted hash order within strata (published × stored gate; stored split × language; dedup set kind), so the halves are balanced and fixed across runs.
- **The labelled dedup set is phase 1's.** Labels come from `labelDedupSets` run with the frozen phase-1 prompt (`suites/dedupPhase1Prompt.ts`) through a cache-only context, so they cost nothing and cannot drift as the production prompt changes; gpt-5-nano's phase-1 verdicts on the same pairs are the reference. Never edit the frozen prompt. eval:models still labels with the current prompt.
- **Versioned schema names.** The cache key holds the schema name, not the schema, so these checks call with `versionedSchemaName` (`name#<hash of the JSON schema>`): editing only a Zod `.describe()` is never answered from the old cache. eval:models keeps plain names so phase-1 entries stay reachable.
- **The rating set** runs gpt-5-mini@medium and Luna@`--effort` on every fixture story with the recalibrated prompt, then `replaceRatingSetFiles` swaps `actually-relevant-full-assessment` for `…-v2`. It refuses files not in the harness's own JSON format (so re-serializing cannot change other sets) and an empty set.
- Output: `recalibration-<half>[-tags].md` in `--out` (criteria table per check, wrong-merge and missed-duplicate titles, meta-commentary hits, every social draft, $/call and $/month). Stored phase-1 numbers in `results.md` are not rewritten.
- **The halves are small for the full assessment.** On 25 stories, gpt-5-mini's own phase-1 rerun sits 0.52 below stored on the calibration half and 0.24 above it on the holdout, so the ±0.25 offset bar is inside the noise there. The 2026-09-24 run therefore aimed the full assessment at parity with the gpt-5-mini rerun on the calibration half, not at that half's stored mean. Pre-assessment halves (150 stories) do not have this problem (mini rerun +0.05 / -0.01).
- **Both halves are now spent.** The 2026-09-24 recalibration tuned on the calibration half and reported the holdout (results in `DOCS/2026-09-24_gpt6-eval/results.md`, "Recalibration"). A further rating-wording change is judged on the fresh sample in `DOCS/2026-11-01_rating-eval` with `--repeat` (above); the phase-1 folder stays the place for dedup, selection and the rating set.

## Research measurement (`eval:research`)

Measures what the planned multi-source story research would cost per story, before anything changes in production, and writes the researched drafts beside today's published text for a first look at quality. It is its own CLI, not an `eval:models` suite: its steps depend on each other and it needs Tavily, which `eval:models` must not require. Run it on the computer with the local database copy:

```bash
npm run eval:research --prefix server -- --out ../DOCS/2026-11-12_research-eval --dry-run    # sample, print the per-step estimate; no API calls
npm run eval:research --prefix server -- --out ../DOCS/2026-11-12_research-eval --limit 1    # smoke run: one story, confirms SQL, Tavily parameters and real cost
npm run eval:research --prefix server -- --out ../DOCS/2026-11-12_research-eval --budget 3   # full run
```

- **Sample:** the newest published stories (30 by default, `--size` at most 60), cached in `--out/.cache/research-fixtures.json` (`--refresh-fixtures` resamples).
- **What runs:** production's first research pass (`services/researchPass.ts`, `.context/research-passes.md`) on each story, as a first pass whatever the story's history: research's steps below, then the card steps (structure, gap list, gap searches and extraction, the one fact check of every fact, the card write and check), whose calls and credits the report counts too. Two differences from the research step: the writer reads only the facts the pass's fact check supported, which is the change to read against the 2026-11-13 baseline; and a pass writes cards, here on the story's assessed text (the fixtures do not hold the research column) with no earlier stories' facts offered. Before 2026-11-17 the eval ran `researchStory`, research's steps alone.
- **Steps per story** (models are constants, today's tier defaults): neighbour confirmation with production's dedup prompt (gpt-6-luna@low); queries (luna@low); Tavily news search (advanced depth, 14 days before to 7 after the article's date, 8 results a query); a deterministic filter (date window, one per domain, syndicated copies, a press-release and content-farm blocklist, up to 6 sources with the original article); extraction per source (luna@none since 2026-11-18, production's `RESEARCH_EXTRACTION_EFFORT` default, as the gap extraction and the structure call; the pass's extraction asks for the structured fields too, under its own schema name `research-extract-structured`); our earlier coverage from the last 12 months (luna@low); the write step (luna@medium), which reads the facts, never the article's text; the citation and copying checks in code, then a fact check that also judges copying (luna@low); up to two repair rounds on a failure that rewrite the failing items alone, each rechecked, and a title, summary or blurb still copying written again from the kept story (luna@medium; `story-research.md`, "Repair"); the gate (`stale`, `contradicted`, `research-rating`, recorded only, `keep`, or `fallback` with its category; `story-research.md`, "What a run does").
- **Budget:** one `--budget` (default $3, the $20 cap applies) covers the folder's model ledger plus every Tavily credit in `.cache/tavily.jsonl` at $0.008, free credits counted as paid. A story starts only while what is left covers one story's estimate (every step's desk estimate, the card steps' included, plus one advanced coverage search per query and three basic gap searches); the rest are reported as skipped.
- **Outputs:** `research-report.md` (tokens and USD per step and per story, the fact check's input per call, Tavily credits, a 250-stories-a-month projection, and "Own words": first-draft problems by cause, `kind` × `by` and for the code check `against`, the repaired runs they caused, items dropped, `draft_failed_check` fallbacks by the cause of the item they failed on and those on a part the draft had nothing in, the items the fact check left without a verdict, the items with number hints and how many of them the fact check failed (ADR-0057), and each first-draft item's longest shared run per kind (`statement` apart from `wording`, since the scope rule has a figure repeat its fact's words) with the shares at 8+ and 12+ words, `scripts/eval/research/ownWords.ts`) and `research-drafts.md` (each draft with its sources, beside the published text); `-limit-N` in the names for a `--limit` run. Caches: `calls.jsonl`, `tavily.jsonl`.
- **Safety:** the read-only session (SELECT only); Tavily is the eval's only HTTP besides OpenAI, through production's `lib/tavily.ts`; the eval itself uses `withRetry` nowhere (`imports.test.ts`); `TAVILY_API_KEY` is sent as a header, never cached, printed only as present or missing, and errors are reduced to a status; fetched text is untrusted input in the prompts. Locally the key is the owner's `server/.env` one; on Render it is the switch of the admin research action (`.context/story-research.md`), which the eval never reaches.
- **The own-words run (2026-11-13, before that change merges):** a new folder on the same sample. Copy `.cache/research-fixtures.json`, `.cache/tavily.jsonl` and `.cache/calls.jsonl` from `DOCS/2026-11-12_research-eval` into `DOCS/2026-11-13_research-own-words-eval/.cache/`, and that folder's `research-report.md` alongside as `research-report-baseline-2026-11-12.md`; never write to the 2026-11-12 folder. The steps whose prompt or schema changed (extraction, write, fact check, rewrite) miss the call cache and run again; the unchanged ones (confirmation, queries, earlier coverage) answer from the copied `calls.jsonl`, so the queries, and with them the searches, match the cached Tavily answers at no Tavily cost. Without `calls.jsonl` the queries are written again, may differ and then cost credits. The copied ledgers count toward `--budget` (the run prints "folder spend so far" first), so the run is `npm run eval:research --prefix server -- --out ../DOCS/2026-11-13_research-own-words-eval --budget 3`. Compare with the baseline: kept drafts and fallbacks by category and cause, the rewrite rate and items dropped, first-draft flags by cause, the longest-run distribution per kind, fact-check input tokens and cost per story, the research-rating drift. Then read 10 drafts beside their sources, non-English sources first, for close copying the judge missed, and the new fact statements against their supporting sentences for fidelity. `eval:recalibrate` does not apply: no production rating, dedup, social or selection prompt changed, and research's rating is recorded only.
- **Shared with production:** the eval runs production's research modules (`prompts/research.ts`, `schemas/research.ts`, `services/researchFilter.ts`, `researchChecks.ts`, `researchCopying.ts`, `researchPipeline.ts`, `researchInput.ts`), the pass (`researchPass.ts`, `researchPool.ts`) and story context's modules through the adapter `scripts/eval/research/pipeline.ts`, which maps each step's tier to a constant arm (gpt-6-luna@low or @medium, an extraction step at `config.research.extractionEffort` on its tier's model; `pipeline.test.ts` fails when they part from `config.llm.models`' defaults), names research's steps with research's versioned schema names and the card steps with the `context` step's (`overview-context-<step>`), so both evals ask the call cache alike, and sends the gap searches as production builds them (`evalSearch`). Eval-only: the call cache and ledger, the Tavily response cache, sampling the newest published stories (then `researchStoriesByIds`), the per-story budget, the cost projection and the report. The write prompt still copies the assess prompt's generic limiting factors.

### `keys`: answer keys

- **What they are:** for each past development we covered, what a perfect overview system would have done with our published stories: the charter (what's in, what's out, the end event) and whether it closed; the figures worth tracking with their definitions; every story that belongs (`join: must`, or `optional` where careful editors could disagree, which scoring ignores) with its role (`turning_point` with a `kind`, or `routine`), the figure values it states (with `approx`, `asOf`, whether the value `matches` the figure's definition and else what it `countedAs`, and the exact words of our story), and the statuses it changes; the tempting `nearMisses` that must not join; and `notes` on our stories' own contradictions.
- **Where they live:** one file per development, `server/src/scripts/eval/overviews/keys/<id>.json`, committed (a file is named after its `id`). The first nine (2026-11-16): Ebola in eastern DR Congo, Hormuz shipping, the 2026–27 El Niño, the 2026 war in Lebanon, the investigations into the RSF's El Fasher atrocities, the WHO pandemic agreement's PABS annex talks, the Colorado River post-2026 rules, the UN talks on autonomous weapons, H5N1 in Australia's wildlife: 382 stories, 200 clear joins, 82 borderline, 114 near misses. They were drafted from the published stories with the whole history in view (for an answer key, hindsight is the point) and checked against those stories; every quote was found in its story's published text. Edit a key when a published story is corrected or a label proves wrong, never to make a step pass.
- **Format:** `keySchema.ts` (Zod, the field rules in its `.describe()`s). `validateKey` adds: entries in date order and unique; a turning point has a `kind`, a routine entry none; every value names one of the key's figures; `countedAs` set exactly when `matches` is false; every figure has at least 3 values (a development with no such number has `figures: []`); no slug both an entry and a near miss; `closed.slug`, when set, is an entry. **Version 2** (`schemaVersion: 2`, 2026-11-18, decision D10) adds an optional `responses[]`: what is being done about the development (`date`, `what`, the `slug` of the entry that reports it or null, and its `quote`), in date order, one row for each story that reports a response under way (a response three stories report is three rows, so the stands of any day are held to the stories of that time); a quote goes only with a slug, and the database check finds it in that story's text. Version 1 keys stay valid. `closed` may carry the `quote` that reports the end (only beside its `slug`). **Review marks** (2026-11-19): each response and `closed` carries `reviewed`, false or absent for a draft; `stands` refuses a half that holds an unreviewed response and `closure` and `replay` one that holds an unreviewed end (`awaitingReview`, before any read or call), so no bar rests on key data no person has checked.
- **The halves** (`developmentHalves.ts`, plan decision D-OV6): a committed list, not a slug hash, so the judged half holds Ebola and each half holds developments of several kinds. Judged: Ebola, El Niño, Lebanon, the PABS annex, the Colorado River; tuned: Hormuz, autonomous weapons, El Fasher, H5N1 in Australia. A new key goes into one list in the change that commits it (`developmentHalves.test.ts` fails until it does).
- **Tests:** `keys.test.ts` runs the schema and `validateKey` on every committed key, with no database, so a key can't rot in CI. Prettier formats the JSON: run `npm run format` after editing one.
- **The database check** (the step): every slug is a published story; each entry's `date` is its UTC publication day; every quote (a value's, a response's, the end's) occurs in one field of the story's published text (title, summary, relevance reasons, antifactors, and the applied research's paragraphs, the text readers see through `storedResearchText`), after evening out whitespace, quote marks and dashes. A miss is an error in the key, to fix there; it passes or fails nothing in production. The report gives counts per development, including its responses, how many entry stories have a stored research run (what module 1's replay will need) and the drafts still to review.

### `key-draft`: the keys' responses and ends, drafted for the owner's review

The stands' "What's being done present" bar needs `responses[]` and the closure's "closed within 14 days" a `closed` end our stories report; the nine keys of 2026-11-16 have neither. Their stories' texts are only in the owner's database copy, so this step drafts both there:

```bash
npm run eval:overviews --prefix server -- --out ../DOCS/2026-11-19_key-drafts --steps key-draft --half judge --dry-run   # the keys it would draft, and the estimate
npm run eval:overviews --prefix server -- --out ../DOCS/2026-11-19_key-drafts --steps key-draft --half judge --budget 3
npm run format --prefix server   # the committed layout again; then review the drafts in the keys, then --steps keys
```

- **What it asks** (`keyDraft.ts`, eval-only prompt in `prompts.ts`): one call per version 1 key of `--half` (gpt-6.1-sol@high, the gap drafts' arm) with the charter, the key's notes and every entry published in the database (must and optional, each field of its published text named), for what each must entry reports as being done about the development (production's stands prompt's sense: aid, a vaccination campaign, a ceasefire mission, a court case, a funding pledge, under way, by a named actor; not a call, a warning, a plan not acted on) and whether any entry reports the charter's end event itself (not a step toward it, a partial or provisional end, or an end elsewhere; the notes name each key's traps).
- **What code keeps:** a response only from a must entry, one a story (`MAX_RESPONSES_PER_STORY`: a checkpoint is due when any response by then has a story with current facts, so a second adds review time and nothing to the bar), dated by its story, its quote found in that story's published text as the `keys` step finds it; the end only with its quote found likewise, dated as the story gives it, else by the story's day. The rest is listed as left out, with why. Kept items go into the committed key file (`keys/<id>.json`, two-space JSON; `npm run format` restores the committed layout), each `"reviewed": false`, the key raised to version 2, the responses before `notes`; a key with nothing kept stays as it was. A version 2 key is left alone, so a rerun drafts only what is still version 1, and a cached call costs nothing again.
- **The review** is the owner's: the report (`overview-eval-steps-key-draft-half-judge.md` in `--out`) lists each key's rows (date, story, what is being done, quote), its end or the drafter's reason there is none, and what was left out. He deletes a wrong row or end, corrects one, and marks each kept one `"reviewed": true`; `--steps keys` then checks every quote against the database. Until then `stands`, `closure` and `replay` refuse the half.
- **Cost:** about $1 for the judged half (151 entries shown, the estimate counts 150 output tokens a story at high effort), about $0.70 more for the tuned half, which only tuning the stands needs. The dry run prints the estimate. No paid run has been made.
- **What it may find:** the keys were drafted with every story in view and are all open on 16 November 2026, seven of them with the reason in their notes (Ebola: Uganda's end is not Congo's; Lebanon: the April truce and the June deal did not hold; the PABS annex, the Colorado River rules, the autonomous-weapons talks, H5N1 in Australia and El Fasher: no end reported); El Niño's and Hormuz's are open without one. So "closed within 14 days" will most likely still have no sample after this step: only a key of a development that ended in our stories would give it one.

### `gap-draft` and `gap-keys`: gap keys

- **What they are:** for one one-off story each, what a careful editor would add beside it so a reader can size and place it, slot by slot of production's checklist (`CONTEXT_SLOTS`: compared, why now, build-up, who is affected, response, next, key term). Story context's `context` step is scored against them. For an answer key, general knowledge is the point: the key is the answer, not the step it checks.
- **Format** (`gapKeySchema.ts`, Zod with the field rules in its `.describe()`s): one file per story, `server/src/scripts/eval/overviews/gapKeys/<slug>.json`, committed and named after its slug: `schemaVersion: 1`, `slug`, `title`, `date` (the story's UTC publication day), `needs` (each with `id`, `slot`, `need`, `kind` `figure`, `fact` or `term`, `importance` `must` or `nice`, `inStory`: our story's exact words when it already states the need, else null, `accepts`: what meets the need, concrete enough to judge yes or no, and `example`: one value and its source, or null when no source is known), `notNeeded` (slot and why) and `notes`. `validateGapKey` adds: a calendar date; 2 to 8 needs with unique ids, at least one `must`; a set `inStory` is not empty; every slot is in `needs` (once or more) or `notNeeded` (once), never both; and `response` is always a `must` need (D10, ADR-0065): with `inStory` set when the story reports the response, and `accepts` saying so with `example` null when no source is known. `gapKeys.test.ts` holds every committed key to the format with no database.
- **The sample** (`gapDraft.ts`, `--steps gap-draft`): 30 published stories of the 4 months up to the newest published one, each with a completed research run whose sources hold facts, none an entry or near miss of a development key, in the eval's hash order, spread round robin over the strata of top-level issue × figure-heavy (at least 3 significant numbers in the published text, years included) or figure-light. Cached in `.cache/gap-sample.json` (`--refresh-fixtures` samples again); shortfalls are reported, never padded.
- **Drafting:** one call per story to gpt-6.1-sol@high (the fact check's label arm) with the eval-only drafting prompt (`prompts.ts`): the story's published text (title, day, paragraphs, Why This Matters points, caveats, as production's `loadContextInput` gives them) and its research run's fact statements, never what the context step finds. Each answer is written as `--out/gap-drafts/<slug>.json` in the committed layout, with its format errors in the report. The calls run only when their uncached estimate fits the budget and `OPENAI_API_KEY` is set; the dry run prints the estimate.
- **The check before commit**, by the coordinating session as for the development keys: cut generic needs ("more background"), make each `accepts` concrete enough to judge, confirm `must` against `nice`, set `inStory` where the story states the need, fix the format errors, then commit to `gapKeys/` and run `npm run format`. No owner time is needed. The same change puts the context-cards paragraph back on the methodology page (`.context/story-context.md`, "Before switching on").
- **The database check** (`--steps gap-keys`, SELECT only): every slug is a published story; `date` is its UTC publication day; a completed research run with facts exists (what the replay needs); every `inStory` quote occurs in the published text after the same normalization as `keys`. The report lists each key's half, needs (must, and must not in the story) and whether its response need is in the story, findable or without a source. A key changes when a story is corrected or a label proves wrong, never to make a step pass.
- **The halves:** the parity of the first byte of the slug's sha256 (`halfOf` in `contextScore.ts`): even is `tune`, odd is `judge`, fixed for good.

### `context`: story context replayed against the bars

- **The replay** (`context.ts`): production's first research pass (`runResearchPass`, `.context/research-passes.md`) on each chosen gap key's story (no format errors, in `--half`, in file order, the first `--limit`), `--repeat` times, run 1 on every story before run 2, its cards judged. The input is production's `loadFirstPassInput` through the read-only session: research's story, the story's own places and the earlier stories' reusable facts, with an empty pool and no version, so it reads no pass table and replays a first pass whatever the story's history. It is cached by slug in `.cache/pass-inputs.json`; a key whose story research cannot run on is left out and listed. The eval's deps are eval:research's adapter's (`research/pipeline.ts`): each step's tier on a constant arm, calls through the call cache under versioned schema names with run k ≥ 2 under its own key; the gap searches through the eval's cached Tavily client with production's request (`tavilyRequestFor`, ending on the story's publication day) and result shaping (`searchResultFrom`), research's coverage window ending on the story's day too; no opt-out policy (`optOutChecked: false`, as eval:research). A search the cache answers counts the credits it cost when made, so a story's cost is what production pays without its own 7-day cache. The judges read the pass as a context run (`cardsResult`): its cards, the pool's facts with structured fields, the card steps' record and the whole pass's cost; the cards are placed on version 1's text when the pass kept a draft, else on the story's own (`judgedInput`). Before 2026-11-17 the replay ran `buildStoryContext` on `loadContextInput` (`.cache/context-inputs.json`, which `gap-draft` still reads).
- **Needs both keys** outside a dry run: each step's calls depend on the answers before it, so whether the caches hold them all is known only by running. A story starts only while the budget covers a first pass's ceiling of $0.40 a story (`runStories`); the rest are listed as not run. The dry run prints a desk estimate of $0.50 a story and run (the ceiling plus the judge).
- **The strong judge** (`contextJudge.ts`, gpt-6.1-sol@high, eval-only prompts in `prompts.ts` except box support): which of the key's needs the story doesn't state the kept cards meet, each against its `accepts`, citing fact ids; whether each kept sentence, tile and chart is supported by its cited facts (production's own fact-check prompt on production's box-check items, so the yardstick is the prompt the step uses); whether each note `model` or `random` placement puts beside a paragraph or point adds to it without restating it (the boxes placed as the page places them, through production's `servedBoxes` and `placeServed`); and once over all runs, whether up to 300 figure facts' structured fields (value, unit, counted, place, as-of, credited) are right, and whether a value is a number its evidence never states. The judge runs once (no `--repeat`), only when its planned calls fit what is left of the budget; otherwise the report scores without verdicts and says why.
- **Scores and bars** (`contextScore.ts`, the design's first proposal; the first run measures baseline and noise), per run and as the mean over the runs with its spread, each shown as met or not:

  | Measure | Bar |
  |---|---|
  | Must needs the story doesn't state, met by the kept cards | at least 60% |
  | Wasted searches (none of whose sources gave a supported fact a kept card cites), the `response` searches apart | at most 1 a story |
  | A response card, on stories whose key has a findable response need not in the story | at least 70% |
  | Box items the judge finds unsupported (each listed for a read) | none |
  | Notes `model` places beside the text that add to it (`random` beside it for comparison) | at least 85%; below it, launch with `STORY_CONTEXT_PLACEMENT=section` |
  | Cost per story, the whole first pass (its article and its cards): model calls at the flex price (half the ledger's) plus credits at $0.008 | at most $0.20 (the context step alone was held to $0.05 before 2026-11-17) |
  | Figure facts with every structured field right; invented numbers the fact check passed | at least 95%; none |
  | Planted errors on the step's facts (`--facts context`, below) | catch at least 90%, false rejection at most 5% |

  Searches for a slot the key marks not needed are counted per run. The `response` searches are never counted as wasted: the step makes them on every story (D10, ADR-0065), so they are no choice the step could save. The report gives them a column of their own per run, the share that found a fact a kept card cites (the same rule as a wasted search, turned around). The gate is the judged half, means over 3 runs (ADR-0066); the owner reads it and switches the step on.
- **Replay hindsight:** the end date filters only dated results, and a page updated after the story can keep its first date. Each search's result dates are logged, and the report counts the undated ones and those dated after the story's day: the share by which the replay can flatter production. The smoke run (`--limit 3`) is where to read them first.
- **Cost:** about $1–2 to draft the keys; a full gate run (3 repeats on the judged half, with the fact check on its facts) about $3–6, mostly the strong judge; Tavily is paid once per query and then cached. `--budget` is a cap on the folder, not a spend.

### `update`: a later pass's updates against the bars

A research pass's later-pass article step (`.context/research-passes.md`, "The later pass"; ADR-0068) replayed on past stories:

```bash
npm run eval:overviews --prefix server -- --out ../DOCS/2026-11-18_update-eval --steps update --half judge --repeat 3 --dry-run
npm run eval:overviews --prefix server -- --out ../DOCS/2026-11-18_update-eval --steps update --half tune --limit 3   # smoke run
npm run eval:overviews --prefix server -- --out ../DOCS/2026-11-18_update-eval --steps update --half judge --repeat 3   # the gate
```

- **The stories** (`updateFixtures.ts`): every `must` entry of the development keys in `--half` (by its slug's half, as the gap keys), the first `--limit`, that is published and researched. Each is read as the legacy import would make it (`readLegacyImport`: its newest research run with facts as the pool, its columns and projection as version 1), SELECT only and never written, cached by slug in `.cache/update-inputs.json`. The facts the version cites count as supported, as a later pass's own fact check would have judged them; the eval measures the article step, not the check. A story without a researched version is left out and listed.
- **Four cases a story**, each a later pass's input with the new facts on sources of their own:
  - `key`: the later `must` entries within 14 days (at most 4) give their figure values (those that match the figure's definition, with `asOf` and the key's quote as the sentence) and their turning points (the title) as new facts. A section stating a figure value of the story's own entry (found by the key's quote) that a later value of the same figure changes is expected flagged; each turning point is expected to found some section's rewrite. Without a turning point every other section is expected unchanged, so a routine window expects nothing. A changed value whose quote no section holds is counted and left out.
  - `wrong-number`, `wrong-year`: a correction of the first cited fact `plant.ts` can change (×1.5 or ×2; the year back one), for the same measure and moment, from a wire report two days after the story: every section citing the old fact is expected flagged, and the old fact demoted.
  - `benign`: the key's first near miss as a new fact on another subject: nothing expected.
- **The replay** (`update.ts`): production's `updateArticle` on each case, `--repeat` times, with eval:research's step caller (`research/pipeline.ts`: each step's tier on a constant arm, `pass-judge`, `pass-update` and `pass-note` beside research's schema names, run k ≥ 2 under its own key). No search: the new facts are the fixtures'. A case starts only while the budget covers $0.10 (`runStories`); the dry run's desk estimate is $0.12 a case and run (that and the note judge). Needs `OPENAI_API_KEY` outside a dry run.
- **The strong judge** (the fact check's label arm, eval-only prompt in `prompts.ts`) reads each served Update note with the changes (each section's text before and after) and the facts they rest on, and answers whether it is accurate (states nothing they do not) and complete (says what changed and why). It runs only when its planned calls fit what is left of the budget.
- **Scores and bars** (`updateScore.ts`), per run and as the mean over the runs with its spread; a case the budget or a failed call stopped is counted, not measured:

  | Measure | Bar |
  |---|---|
  | Expected changes flagged on the right section (a turning point: some rewrite rests on it) | at least 90% |
  | Sections a strict case expects unchanged that were rewritten | at most 10% |
  | Sections no change names, byte-identical in the new version (a code assertion) | 100% |
  | Planted contradictions whose old fact was demoted | at least 90% |
  | Cases demoting a fact they do not expect | at most 5% |
  | Served notes the strong judge finds accurate and complete | at least 90% |
  | Notes written that production's fact check found unsupported: every round it read counts, a note a repair round replaced and one the fixed line was served after too, so a run of fixed lines after unsupported notes fails; unmeasured when it read none | none |
  | Notes' copying-flag share (of the notes the checks ran on) against the rewritten sections' | no higher |

  Each run's row also gives the fixed lines' share of the served notes. The report lists up to 30 missed changes, false rewrites, false demotions and notes judged short. The gate is the judged half, means over 3 runs (ADR-0066), beside the `context` step's bars.

What the owner runs before opening `OVERVIEW_EVAL_GATE` (`.context/overviews.md`, "Switching on", which has the bars in one table with what each rests on, and what follows the gate). **Precondition: research passes are on** (their gate open and `research_pass` enabled), since overviews switch on only after them. The costs are desk estimates, as the folder's ledger counts them (calls at the standard price, Tavily at $0.008 a credit, a first pass at about $0.10–0.25); no paid run has been made. **About $15 in all** (about $11–24 if the desk figures are off), and never more than $27, the four folders' caps.

### `fact-check`: planted errors

Decision D4 of the overview plan makes the fact-check call the only defense against a wrong number (ADR-0057's rule, extended), so this measures its leniency on production's own prompt.

- **Sample** (`factFixtures.ts`): facts from finished `story_research_runs` results, newest first, one run per story (its newest): each source's facts whose supporting sentence code found in the source text and whose statement states a significant number (`readNumbers`, `significant`), at most 10 a run and 3 a source, each with what it measures and its source's outlet and date. Cached in `.cache/fact-fixtures.json` (a cache of another size or fixture version is resampled); runs stored in an older shape are skipped and counted, a source stored without a date counts as undated. A fact's language is known only when its source is one of our crawled stories.
- **Variants** (`plant.ts`, pure), each labeled by construction, each changing one number that production's number reader finds, never one inside a word, an id or a URL-like string:
  - `faithful`: the statement as extracted (expected supported).
  - `reworded` (expected supported): "half", "a quarter" or "three quarters" for 50%, 25% or 75%, only before "of" or after "by" ("a 50% rise" would turn ungrammatical); a whole million in the other form; a number of at least 1,000 as "about" at two significant figures, never a bare four-digit one (no group separator, no currency, percent or scale word, under 10,000), which is as often a year, a period's bound ("1850-1900") or a name ("Resolution 1701") as a count. A fact no rule fits gets none.
  - `wrong-number`: ×1.5 at the same precision, else ×2; never a year.
  - `dropped-qualifier`: "nearly", "almost", "about", "around", "more than", "over", "at least", "up to" or "some" removed before a number, never from a negated one ("no more than") and never before a year ("up 5% over 2024").
  - `wrong-year`: a year from 1900 to 2099 moved back one.
  - `wrong-scale`: thousand, million and billion swapped once.
  - For module-1 facts only (`--facts context`), four field-level kinds, each changing one structured field before production's `renderFact` renders the fact again (a change the rendering doesn't show is dropped): `wrong-place` (another place named among the story's facts, where the rendering shows the place as its own detail), `wrong-as-of` (the month moved back one at its own precision, or the year for year precision, never to a month or year the evidence names), `wrong-credit` (another credited body among the story's facts, where the rendering says "according to"), `cumulative-swap` ("total" or "cumulative" swapped with "new" or "weekly" in what is counted, only where one is there and the evidence doesn't use the other). A peer is never one the evidence or the rendering already names.
- **`--facts context`** (`contextFacts.ts`): the sample is the facts the `context` step's run 1 kept on each chosen story (supported by production's check, none reused), taken in turn from each story up to `--size`. Each is shown as production's `renderFact` renders it and reaches the check with production's evidence and number hints (`factCheckItems`): the sentence or passage, then the source's date fact. The text kinds apply to the rendering, the field kinds to the fields. The labels, the arms and the bars are the same as for research's facts.
- **`--facts stands`** (`standsFactFixtures`, with the `stands` step): the sample is the lines the `stands` step's run 1 kept, up to `--size`, each with its cited facts' source sentences as its evidence and what they count as its measure, so the text kinds are planted in stands lines (the field kinds need a single structured fact and do not apply).
- **Labels first:** an extracted statement may itself misstate its evidence, which would make a correct rejection look false. So gpt-6.1-sol@high judges each sampled fact once with the same prompt; the facts it rejects leave the sample, and variants are built only from facts it accepts. The report lists the rejected ones, with the judge's reason, as "statements their evidence does not support (sentence, what it measures, source date)". That is not an extraction-fidelity measure: the judge never sees the source's full text, and extraction is told to carry a figure's scope and period into the statement, which may come from elsewhere in the article.
- **The call:** production's `buildFactCheckPrompt(items, [], [])` and `factCheckSchema` (versioned name), 10 items a call, shuffled with a fixed seed so variants of one fact rarely share a call. Each item is what production shows for a story paragraph citing the fact, minus the extraction's own statement: the fact with the source sentence as both statement and supporting sentence and its stored `measures`, then the source's date fact (`publishedFact`) when the source has a date. The evidence and the number hints come from production's `checkedItems`, so they follow production. Only `supported` is scored.
- **Budget, per pass:** the label pass runs only when its own uncached calls fit what is left of `--budget`; once the labels are known (cached or fresh), the arms' calls are planned on the accepted facts' variants and checked again before any arm runs. A pass the cache answers in full always runs, without the API key too, so a re-run of a finished run costs nothing and is never refused. The dry run prints both estimates, the arms' as an upper bound (every fact's variants) while a label is still uncached.
- **Scores** (`factCheckScore.ts`): per kind, the share judged unsupported. The catch rate is the share of planted errors caught; false rejection is the share of faithful and reworded items rejected. Both are held against the design's first bars (catch at least 90%, false rejection at most 5%), shown as met or not, never a gate. With `--repeat`, the spread across runs and the share of items whose verdict flips. Up to 30 misses and 30 false rejections are listed beside their sentences, for a read.

## Adding a suite or arm

1. Add `suites/<name>.ts` exporting a `Suite` (`name`, `arms`, `describe`, `plan`, `run`) and a pure `decide*` function with a test; reuse `runArms`/`metricRow` from `suites/shared.ts` and `pickLowestPassing`/`effectiveBar` from `decide.ts`.
2. Add its fixture sampling to `fixtures.ts` (SELECT only) and its name to `SUITE_NAMES` in `options.ts` and `SUITES` in `run.ts`. Build the prompt input with the service's own builder; if the service shapes it inline, export a pure builder first (in `services/promptInputs.ts`, with a pin in its test) and have the service call it.
3. A new model needs a price row in `MODELS` (`models.ts`). GPT-6 rejects `minimal`; gpt-5-mini/nano and gpt-6.1-sol reject `none` (`createChatModel` throws).
4. A new taste set needs a slug in `RatingSetSlug`, a budget in `RATING_BUDGET` and a picking rule in `SET_SPECS` (`ratingSets.ts`).
