# Model Eval Harness

Compares OpenAI models and reasoning efforts on this project's real call sites, using stored data. It was built for the GPT-6 migration (gpt-5-nano/mini → gpt-6-luna, gpt-5.2 → gpt-6-sol) and is meant to be re-run whenever a model or undated alias changes; since 2026-10-27 its large-tier suite compares gpt-6-sol with gpt-6.1-sol (below). It never writes to any database and never changes production settings.

## Running

```bash
npm run eval:models --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --api-check --budget 0.1   # 1 trivial call per arm, no DB
npm run eval:models --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --dry-run                 # sample fixtures, print estimates, no API calls
npm run eval:models --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --suites related --limit 2 # smoke run (6 calls)
npm run eval:models --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval                           # full run (default --budget 18)
```

| Flag | Meaning |
|------|---------|
| `--out` | Output folder (required). Use a dated folder under the gitignored `DOCS/`; `--prefix server` makes the path relative to `server/`. |
| `--suites` | Comma list of `preassess, assess, dedup, related, social, large` (default: all) |
| `--limit N` | At most N fixture items per suite part (partial runs; verdicts are then not evidence) |
| `--dry-run` | Sample fixtures and print per-suite call counts and $ estimates; refuses any uncached API call |
| `--api-check` | One trivial structured-output call per arm of the selected suites; proves each model accepts `reasoning_effort` through the production client. Needs no database. |
| `--budget` | USD stop for live calls (default 18; values above 20, this project's cap, are refused) |
| `--concurrency` | Parallel calls (default 4; the related-stories suite always runs one at a time for latency) |
| `--refresh-fixtures` | Resample fixtures instead of reusing `.cache/fixtures.json` |
| `--floor YYYY-MM-DD` | Earliest crawl date for the pre-assess, assess, dedup and social-post samples (default 2026-03-01, when the current prompts and issue set were in place). Move it earlier only for a database copy older than that; the report states the floor. Cached fixtures with a different floor are resampled, so pass the same `--floor` on every run against one output folder. |
| `--assess-size N` | Full-assessment stories to sample (default 50, phase 1's; at most 300). The minimums scale with it (`assessQuotas`: half rated 4-6, a fifth non-English, a tenth Han-script). Recorded in the fixtures; cached fixtures with another size are resampled. |
| `--exclude <folders>` | Comma list of eval folders whose cached pre-assessment and full-assessment stories leave those pools, so a fresh sample shares no story with a spent one. Recorded by folder name; cached fixtures with other exclusions are resampled. |

The run needs `DATABASE_URL` reachable (the local Postgres service must be running) except for `--api-check`. It prints only `local`/`remote` for the database and `present`/`missing` for `OPENAI_API_KEY`, never values.

### Large tier: gpt-6-sol vs gpt-6.1-sol (2026-10-27)

The large tier's default moved to gpt-6.1-sol on 2026-10-27 (`.context/llm-analysis.md`), to be merged only after this comparison and the owner's podcast listening check. The large-tier suite reruns gpt-6-sol@medium, production's model until then, against gpt-6.1-sol@medium on its three call sites. Run it from the repository root, in a new folder: the rating deliverable is written only into a folder that has none, so the 2026-09-24 folder cannot take the new sets.

```bash
npm run eval:models --prefix server -- --out ../DOCS/2026-10-27_gpt61-sol-eval --suites large --api-check --budget 0.1   # 2 trivial calls, no DB: both models take reasoning_effort and json_schema
npm run eval:models --prefix server -- --out ../DOCS/2026-10-27_gpt61-sol-eval --suites large --dry-run                  # samples fixtures from the local DB, prints the estimate; no API calls
npm run eval:models --prefix server -- --out ../DOCS/2026-10-27_gpt61-sol-eval --suites large --budget 5                 # full run: 20 selection groups, 4 newsletters, 1 podcast, both arms
```

- **Budget.** About 50 calls. The dry run's estimate assumes about 4,500 output tokens per selection call (phase 1 measured about 520 for gpt-6-sol), so it should print roughly $3 while the run itself costs about $1-2. A suite whose estimate exceeds what is left of `--budget` is skipped: if the dry run prints more than about $4.5, pass `--budget` at the estimate plus $1 (20 at most).
- **No smoke run in this folder.** A `--limit` run writes `rating-sets.json` from its few items, and the full run then leaves that partial deliverable in place. Smoke-test in a scratch folder, if at all.
- **The gate** is phase 1's, now against gpt-6-sol: exact-count compliance on every selection group (relaxed only to gpt-6-sol's own rate), and on each call site no more declines or failed calls than gpt-6-sol, nor more non-compliant newsletters, dialogues failing validation or sentences over 18 words. The declines catch the over-refusal some users report for 6.1 Sol. The large row recommends gpt-6.1-sol only when all three call sites pass.
- **What to read:** in `results.md`, the large row of "Recommendation per tier", "Is gpt-6-sol better in any way?" and the three large-tier call sites; then rate `rating-sets.json` blind (story selection, at most 5 groups, and the podcast script; `rating-key.json` maps the labels to arms). gpt-6.1-sol's price is marked unverified: input and output as gpt-6-sol's from OpenAI's pages, cached input kept at gpt-6-sol's $0.20 as the upper bound though secondary sources report $0.10.
- **Before merging,** check that Render sets no `OPENAI_MODEL_LARGE`, which beats the default and keeps gpt-6-sol, and no `OPENAI_EFFORT_LARGE=none`, which gpt-6.1-sol rejects (the large-tier client then throws at its first use). To stay on gpt-6-sol, revert the `config.ts` default with the model ids in `llm-analysis.md` and `ai-transparency.md`.

## Outputs (in `--out`)

- `results.md` — per call site: arms, outcome counts (ok / parse failure / empty-or-declined / truncated / error / budget-skipped), p50/p95 latency, mean input/cached/output/reasoning tokens, $/call and $/month at the inventory volumes, quality metrics, the automated verdict; then the per-tier recommendation, current-vs-proposed monthly cost, "Is <large-tier baseline> better in any way?", fixture shortfalls, prices (gpt-5.2 and gpt-6.1-sol marked unverified) and spend. A "Fabricated-number spot check" section is left for a person to fill.
- `rating-sets.json` / `rating-key.json` — the owner's blind-rating sets (full assessments 12, social posts 10, podcast script 1, story selection 5 at most; the phase-1 deliverable also holds 4 newsletter intros, a set no suite drafts since the intro was removed on 2026-10-26, kept in `RatingSetSlug` so that file still validates). The key maps each item's labels to `model@effort`. **Written only when the folder has none yet** (`ratingFiles.ts`): the owner rates from this file with a local tool (which keeps its own `ratings.json`, never touched here), so a re-run or a partial run leaves an existing deliverable alone. To regenerate one set, use the recalibration's `rating-set` step, which swaps in a versioned set (`…-v2`, new item IDs) and leaves every other set byte for byte. **No model name may appear anywhere in `rating-sets.json`, item context included** (owner's decision, 2026-09-24; terms in `blinding.ts`: the eval model IDs, `Luna`, `Sol`, `nano`, and anything starting `gpt`, `ChatGPT` or `OpenAI`). Single-story items whose story or output mentions one are dropped at build time; multi-story fixtures (selection groups, newsletters, the podcast) drop such stories before any prompt is built, so no arm sees them. The written files are re-validated and a failure exits non-zero.
- `.cache/fixtures.json` — the sampled inputs, reused so prompts (and cache keys) stay stable while the DB changes.
- `.cache/calls.jsonl` — response cache **and** spend ledger, keyed by `sha256(model@effort + schema + prompt)`. Re-runs and resumes never pay twice; errors are not cached so they retry.

## How it stays safe

- **Read-only DB.** `readOnlyDb.ts` opens a session with `default_transaction_read_only=on`, or, if a pooler rejects that option, runs all reads inside one `SET TRANSACTION READ ONLY` transaction; `SHOW transaction_read_only` must be `on` before any query. `fixtures.ts` issues SELECTs only.
- **No second write path.** The eval calls prompt builders, Zod schemas and `createChatModel` directly and never the persisting service functions. It may import only `createChatModel` (`services/llm.ts`), production's prompt-input builders (all of `services/promptInputs.ts`, and `blueskyDraftInput` / `mastodonDraftInput` from `services/bluesky.ts` / `services/mastodon.ts`) the pure podcast dialogue rules (`services/podcastDialogue.ts`: `validateDialogue`, `assembleSpokenSegments`, `renderScript`, `dialogueCharBudget`) and production's research steps (`services/researchPipeline.ts`, `researchInput.ts`, `researchFilter.ts`, `researchChecks.ts`, `researchCopying.ts`, each held to no client, HTTP or retry of its own); `imports.test.ts` enforces this statically, plus that `promptInputs.ts` imports only config and prompt types, and no `lib/prisma`, `rateLimitDelay`, `withRetry` or Prisma write calls.
- **Budget.** Estimates use chars/4 (Han chars/1) input and per-suite output assumptions (Luna +25%, low ×0.4, high ×1.5). A suite whose estimate exceeds the remaining budget is skipped; live calls stop once the ledger reaches `--budget`, and call sites with skipped calls get no verdict.
- **No retries around calls.** Parse failures and declines are what is measured, so calls are not wrapped in `withRetry` (ChatOpenAI's own transport retries still apply).

## Methodology

- **Baselines are rerun.** Every suite reruns today's model on the same prompts. Agreement with stored production values is reported for the rerun too: that is the noise floor. An absolute "≥" bar is relaxed to the noise floor minus 5 points only when the baseline rerun itself misses it.
- **Winner** per call site is the lowest-effort candidate that passes every automated check. The per-tier recommendation takes the highest of those efforts across the tier's call sites (small: dedup, related, pre-assess; medium: pre-assess, assess, social pick) and flags any site not tested at that effort.
- **Baselines are constants.** Each suite's baseline arm is a constant, never read from `config`. The large-tier suite was rebased on 2026-10-27: `LARGE_BASELINE` (gpt-6-sol@medium, production's model until then) against `LARGE_CANDIDATE` (gpt-6.1-sol@medium) in `suites/largeTier.ts`, which the report's large-tier recommendation and comparison read, so the next rebase changes only those two. The small- and medium-tier suites still run the pre-switch baselines (gpt-5-nano, gpt-5-mini) from phase 1; a comparison for a change there should make today's default (gpt-6-luna) the baseline first.
- **Dedup labels** come from arm consensus; sets where the arms disagree go to two judges (gpt-5.2@high, gpt-6-sol@high) with the unchanged prompt, and pairs the judges split on are excluded. Existing clusters were made by gpt-5-nano, so agreement with them is secondary.
- **Windows are anchored on the data.** "Last N days" windows count back from the newest assessed crawl date, so a stale local DB copy still yields fixtures (the dry run warns when the anchor is over 14 days old). The fixed crawl floor is not anchored; see `--floor`.
- **Adaptations are reported.** When the data is thin, `fixtures.ts` records what it changed in `adaptations` (moved floor, extra nearest-neighbour dedup sources filling missing cluster-member slots, the synthetic social-pick scan, blinding removals with the terms that matched), and `results.md` lists them under Fixtures.
- **Prompt inputs come from production's builders.** Each call site's DB-row → prompt-input mapping is an exported pure function that the service itself calls before its model call (`services/promptInputs.ts`: assess, select, related stories, social pick, newsletter select, podcast select and script; the Bluesky and Mastodon draft inputs in their services). `fixtures.ts` and `suites/podcast.ts` call the same functions, so a change to how a service builds its input reaches the eval the day it lands; there is no copy to update. `services/promptInputs.test.ts` pins the prompts each service sends for fixed rows, so a builder refactor that changes one fails there. What stays the eval's own is the sampling: which rows are loaded (`fixtures.ts`'s SELECTs, batched per source where production queries one story) and their order, which keeps prompts and cache keys stable. Fixtures cached before the builders were shared (2026-10-25) hold inputs from the old copies, which the builders reproduce, so their prompts and cache keys stay as they were.

## Phase-2 recalibration (`eval:recalibrate`)

Checks the recalibrated rating prompts (pre-assessment and full assessment) and the tightened dedup prompt on gpt-6-luna against the owner's acceptance rules (2026-09-24), on the sample cached in `--out`: the phase-1 sample, or a fresh one (below). It needs no database and never resamples: the split and the labelled dedup set are defined on those fixtures.

```bash
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --half calibration --dry-run      # estimates + labelled-set preflight
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --half calibration --budget 5.9    # iterate here only
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --half holdout --budget 5.9        # report once the prompt is final
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-09-24_gpt6-eval --steps rating-set --budget 5.9    # full-assessment set v2
```

### A rating-prompt change on a fresh sample, with repeated runs

Both phase-1 halves are spent, so judge a further rating-prompt change on the fresh sample in `DOCS/2026-11-01_rating-eval`, run several times. Sample it first (read-only database session, no API calls; the local Docker database must be running), from the repository root:

```bash
npm run eval:models --prefix server -- --out ../DOCS/2026-11-01_rating-eval --dry-run --assess-size 150 --exclude ../DOCS/2026-09-24_gpt6-eval --floor 2026-01-01   # samples fixtures, prints the anchor and estimates
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-11-01_rating-eval --floor 2026-01-01 --steps assess --repeat 3 --dry-run                             # estimate: 3 runs × 150 stories
npm run eval:recalibrate --prefix server -- --out ../DOCS/2026-11-01_rating-eval --floor 2026-01-01 --steps preassess,assess --repeat 3 --budget 3                  # the check
```

- **The sample.** eval:models' own sampler with a larger full-assessment set (`--assess-size 150`, three times phase 1's) and every phase-1 pre-assessment and full-assessment story left out (`--exclude`), so no story the prompts were tuned on is judged again. The pre-assessment sample stays 300. Check the anchor the dry run prints (it warns when over 14 days old) and refresh the local database copy if it is stale. Pass the same `--floor` and flags on every eval:models call against the folder, or the fixtures are resampled and every cache key changes. `--half` still splits it (75/75 full-assessment stories), for tuning on one half and reporting the other.
- **What it can judge.** The preassess and assess rating checks against stored production values work on any sample. Stored values are what production wrote: stories crawled after the 2026-09-24 switch were stored by gpt-6-luna on the prompt of that day, so on such a sample the bars measure drift from current production rather than from the gpt-5-mini archive; the report states the crawl window. Phase 1's issue and emotion agreement numbers were measured on other stories, so on a fresh sample they are shown for reference and not required. The format bars stay required. The steps that read phase 1's ledger (`dedup`, `selection`, `rating-set`) are skipped there with the reason ("needs the phase-1 folder"); a folder counts as phase 1's when its fixtures' `createdAt` is phase 1's (`freshSample.ts`). `social-post` and `podcast` run on any folder.
- **`--repeat N`** (pre-assessment and full assessment, 1 to 10, default 1) runs each rating prompt N times. The response cache would answer an identical prompt from the ledger, so run k ≥ 2 calls with the schema name tagged `~run<k>` (`repeats.ts`): a distinct cache key, the same request (the schema name never reaches the API). Run 1 keeps the plain key, so an earlier single run is reused as run 1 and a later `--repeat 5` reuses runs 1-3 of a `--repeat 3`. The criteria table pools all runs (the averaged numbers against the bars; meta-commentary counts every output). Below it the report lists each run's mean offset and share at the threshold, the spread across runs (mean, range, standard deviation), and per story how often the rating differs between runs, how often the threshold split flips, and the mean spread of a story's ratings; for pre-assessment also issue and emotion disagreement. This is the run-to-run noise nobody had measured: a rating shift smaller than the spread between single runs is not evidence. The report name gains `-repeat-N`.
- **Measured noise (2026-11-01, Luna@medium, 150 stories × 3 runs).** One prompt's single-run mean offsets span about 0.03 (SD 0.01); a story's rating differs between runs for 55-59% of stories and its ≥5 split flips for 15-19%. Paired before/after with 3 runs each resolves about ±0.06 on the mean (95% half-width; 80%-power detectable effect about 0.09) and about 4.6 points on the share ≥5. Compare two prompts on the paired per-story deltas, not on whether each clears the ±0.25 bar: a 0.02 drift moved the offset from -0.27 (fail) to -0.24 (pass) with no real change. The first use (headline subject word, 27e9a43) is in `DOCS/2026-11-01_rating-eval/recalibration-all-assess-repeat-3-{before,after}.md`. That sample was drawn from a local copy ending 2026-02-08, hence `--floor 2026-01-01` in the commands above; its stored ratings come from the gpt-5-mini era.
- **Cost.** Each run is one full-assessment call per story (about $0.003 estimated, $0.0017 measured on Luna@medium), so 3 runs × 150 stories is roughly $0.75-1.25; pre-assessment adds about $0.06 per run. The fresh folder's ledger starts at $0, so `--budget` is this folder's own total.

| Flag | Meaning |
|------|---------|
| `--half` | `calibration`, `holdout` or `all` (default). Tune prompts on `calibration` only; the holdout is the result. |
| `--steps` | Comma list of `preassess, assess, dedup, rating-set, social-post, selection, podcast` (default: the three checks). `rating-set` and the ship checks run only when named; `rating-set` refuses `--limit`. |
| `--effort` / `--dedup-effort` | gpt-6-luna effort for the rating checks, the rating set and social posts (default `medium`) / for dedup (default `low`). |
| `--budget` | Cap on the **ledger total** for the folder, as in eval:models. The ledger already holds phase 1's $2.96, so pass the ledger plus this run's allowance. |
| `--repeat N` | Runs of each rating prompt (pre-assessment, full assessment), 1 to 10, default 1; run k ≥ 2 has its own cache key (above) |
| `--limit`, `--dry-run`, `--concurrency`, `--floor` | As in eval:models; `--floor` is only checked against the cached fixtures |

- **What is judged against what** (`recalibration.ts`): ratings against the stored production values (the archive the site must stay comparable with): mean offset within ±0.25 on both stages, share at or above 5 within 5 points of stored, published stories passing the pre-assessment gate ≥ 75%, issue and emotion agreement not below phase-1 Luna@medium (74.0%, 70.3%; 71.6% is reported as the aim), full-assessment format checks not below phase-1 gpt-5-mini, and no full assessment whose published fields talk about the input ("the article does not quantify…", "the supplied excerpt"; `metaCommentary.ts`, which skips the verbatim quote). Dedup: no more wrong merges than gpt-5-nano and a recall at least 15 points above nano's, on the same labelled pairs.
- **The report name says what ran.** `recalibration-<half>.md` is the report of record: default steps at the default efforts. Another effort, step list or `--limit` adds tags (`recalibration-holdout-effort-high.md`, `recalibration-all-assess-social-post.md`, `…-limit-3.md`), so a trial never overwrites it. Re-running the same command does overwrite its own file: rename a report first if you need it as a before/after reference.
- **Ship checks** (`shipChecks.ts`, rules in `shipRules.ts`) cover the other prompt changes that ship with the phase-2 switch, on the whole cached sample whatever `--half` says. `social-post`: Luna at `--effort` drafts every cached Bluesky and Mastodon post; every draft must name the story's main actor or a key number (`storyAnchors.ts`: a capitalised word the story uses mid-sentence, an acronym other than topic ones like AI or HIV, or a number the story states), stay within the limit and state no number the story lacks. Names the story never mentions are listed for the embellishment spot check but do not fail it; the report lists every draft for that read. The heuristic misses a number in words ("a quarter" for 25%) and a story whose only actor is a group ("developers"), so read the drafts it flags before calling a miss. `selection`: gpt-6-sol@medium on every cached selection group with publication dates; the gate is phase 1's (exactly N valid IDs in every group, no declines). Fixtures cached before the date field show each candidate's group crawl day. One candidate per group, the first one production selected, is re-dated to 2023-06-01 as a stale probe; the report compares how often the model keeps it with how often it picked the same stories in phase 1 without dates, read free from the ledger through the frozen phase-1 prompt (`suites/selectPhase1Prompt.ts`; never edit it). `podcast` (2026-10-06): gpt-6-sol@medium runs the podcast selection on the cached podcast pool and the dialogue on a fixed pick from it (`suites/podcast.ts`: the most relevant story per issue, then by relevance, up to 5); the gate is `checkDialogue` with no validation error (every story covered, the spoken band, a bridge opening every segment after the intro, tags, no markup) and a selection of 4-5 valid pool ids spread over the issues the pool offers. The report lists every segment's opening turn (the segue report) and the picks. This is the check CLAUDE.md asks for after a podcast prompt change; the podcast pool is not part of the spent calibration halves, so no fresh sample is needed. Both the `selection` and `podcast` steps still run gpt-6-sol, not gpt-6.1-sol, the large tier's default since 2026-10-27 (`selection` compares with phase 1's gpt-6-sol picks); until the `podcast` step follows the default, check a podcast prompt change on gpt-6.1-sol too, with the large-tier comparison above (`eval:models --suites large` in its folder). Fixtures cached before 2026-10-06 hold the old podcast shape (no ids, no relevance, each story's own issue): `suites/podcast.ts` fills ids by position and keeps their order.
- **The split** (`splitHalves` in `sampling.ts`) alternates items in a salted hash order within strata (published × stored gate; stored split × language; dedup set kind), so the halves are balanced and fixed across runs.
- **The labelled dedup set is phase 1's.** Labels come from `labelDedupSets` run with the frozen phase-1 prompt (`suites/dedupPhase1Prompt.ts`) through a cache-only context, so they cost nothing and cannot drift as the production prompt changes; gpt-5-nano's phase-1 verdicts on the same pairs are the reference. Never edit the frozen prompt. eval:models still labels with the current prompt.
- **Versioned schema names.** The cache key holds the schema name, not the schema, so these checks call with `versionedSchemaName` (`name#<hash of the JSON schema>`): editing only a Zod `.describe()` is never answered from the old cache. eval:models keeps plain names so phase-1 entries stay reachable.
- **The rating set** runs gpt-5-mini@medium and Luna@`--effort` on every fixture story with the recalibrated prompt, then `replaceRatingSetFiles` swaps `actually-relevant-full-assessment` for `…-v2`. It refuses files not in the harness's own JSON format (so re-serializing cannot change other sets) and an empty set.
- Output: `recalibration-<half>[-tags].md` in `--out` (criteria table per check, wrong-merge and missed-duplicate titles, meta-commentary hits, every social draft, $/call and $/month). Stored phase-1 numbers in `results.md` are not rewritten.
- **The halves are small for the full assessment.** On 25 stories, gpt-5-mini's own phase-1 rerun sits 0.52 below stored on the calibration half and 0.24 above it on the holdout, so the ±0.25 offset bar is inside the noise there. The 2026-09-24 run therefore aimed the full assessment at parity with the gpt-5-mini rerun on the calibration half, not at that half's stored mean. Pre-assessment halves (150 stories) do not have this problem (mini rerun +0.05 / -0.01).
- **Both halves are now spent.** The 2026-09-24 recalibration tuned on the calibration half and reported the holdout (results in `DOCS/2026-09-24_gpt6-eval/results.md`, "Recalibration"). A further rating-wording change is judged on the fresh sample in `DOCS/2026-11-01_rating-eval` with `--repeat` (above); the phase-1 folder stays the place for dedup, selection and the rating set.

## Research measurement (`eval:research`)

Measures what the planned multi-source story research would cost per story, before anything changes in production, and writes the researched drafts beside today's published text for a first look at quality. It is its own CLI, not an `eval:models` suite: its steps depend on each other and it needs Tavily, which `eval:models` must not require. Run it on the computer with the local database copy:

```bash
npm run eval:research --prefix server -- --out ../DOCS/2026-11-12_research-eval --dry-run    # sample, print the per-step estimate; no API calls
npm run eval:research --prefix server -- --out ../DOCS/2026-11-12_research-eval --limit 1    # smoke run: one story, confirms SQL, Tavily parameters and real cost
npm run eval:research --prefix server -- --out ../DOCS/2026-11-12_research-eval --budget 3   # full run
```

- **Sample:** the newest published stories (30 by default, `--size` at most 60), cached in `--out/.cache/research-fixtures.json` (`--refresh-fixtures` resamples).
- **Steps per story** (models are constants, today's tier defaults): neighbour confirmation with production's dedup prompt (gpt-6-luna@low); queries (luna@low); Tavily news search (advanced depth, 14 days before to 7 after the article's date, 8 results a query); a deterministic filter (date window, one per domain, syndicated copies, a press-release and content-farm blocklist, up to 6 sources with the original article); extraction per source (luna@low); our earlier coverage from the last 12 months (luna@low); the write step (luna@medium), which reads the facts, never the article's text; the citation and copying checks in code, then a fact check that also judges copying (luna@low); one rewrite on a failure (luna@medium); the gate (`stale`, `contradicted`, `research-rating`, recorded only, `keep`, or `fallback` with its category; `story-research.md`, "What a run does").
- **Budget:** one `--budget` (default $3, the $20 cap applies) covers the folder's model ledger plus every Tavily credit in `.cache/tavily.jsonl` at $0.008, free credits counted as paid. A story starts only while what is left covers one story's estimate; the rest are reported as skipped.
- **Outputs:** `research-report.md` (tokens and USD per step and per story, the fact check's input per call, Tavily credits, a 250-stories-a-month projection, and "Own words": first-draft problems by cause, `kind` × `by` and for the code check `against`, the rewrites they caused, items dropped, `draft_failed_check` fallbacks by the cause of the item they failed on and those on a part the draft had nothing in, the items the fact check left without a verdict, and each first-draft item's longest shared run per kind (`statement` apart from `wording`, since the scope rule has a figure repeat its fact's words) with the shares at 8+ and 12+ words, `scripts/eval/research/ownWords.ts`) and `research-drafts.md` (each draft with its sources, beside the published text); `-limit-N` in the names for a `--limit` run. Caches: `calls.jsonl`, `tavily.jsonl`.
- **Safety:** the read-only session (SELECT only); Tavily is the eval's only HTTP besides OpenAI, through production's `lib/tavily.ts`; the eval itself uses `withRetry` nowhere (`imports.test.ts`); `TAVILY_API_KEY` is sent as a header, never cached, printed only as present or missing, and errors are reduced to a status; fetched text is untrusted input in the prompts. Locally the key is the owner's `server/.env` one; on Render it is the switch of the admin research action (`.context/story-research.md`), which the eval never reaches.
- **The own-words run (2026-11-13, before that change merges):** a new folder on the same sample. Copy `.cache/research-fixtures.json`, `.cache/tavily.jsonl` and `.cache/calls.jsonl` from `DOCS/2026-11-12_research-eval` into `DOCS/2026-11-13_research-own-words-eval/.cache/`, and that folder's `research-report.md` alongside as `research-report-baseline-2026-11-12.md`; never write to the 2026-11-12 folder. The steps whose prompt or schema changed (extraction, write, fact check, rewrite) miss the call cache and run again; the unchanged ones (confirmation, queries, earlier coverage) answer from the copied `calls.jsonl`, so the queries, and with them the searches, match the cached Tavily answers at no Tavily cost. Without `calls.jsonl` the queries are written again, may differ and then cost credits. The copied ledgers count toward `--budget` (the run prints "folder spend so far" first), so the run is `npm run eval:research --prefix server -- --out ../DOCS/2026-11-13_research-own-words-eval --budget 3`. Compare with the baseline: kept drafts and fallbacks by category and cause, the rewrite rate and items dropped, first-draft flags by cause, the longest-run distribution per kind, fact-check input tokens and cost per story, the research-rating drift. Then read 10 drafts beside their sources, non-English sources first, for close copying the judge missed, and the new fact statements against their supporting sentences for fidelity. `eval:recalibrate` does not apply: no production rating, dedup, social or selection prompt changed, and research's rating is recorded only.
- **Shared with production:** the eval runs production's research modules (`prompts/research.ts`, `schemas/research.ts`, `services/researchFilter.ts`, `researchChecks.ts`, `researchCopying.ts`, `researchPipeline.ts`, `researchInput.ts`) through the adapter `scripts/eval/research/pipeline.ts`, which maps each step's tier to a constant arm (gpt-6-luna@low or @medium) and keeps the versioned schema names. Eval-only: the call cache and ledger, the Tavily response cache, sampling the newest published stories (then `researchStoriesByIds`), the per-story budget, the cost projection and the report. The write prompt still copies the assess prompt's generic limiting factors.

## Adding a suite or arm

1. Add `suites/<name>.ts` exporting a `Suite` (`name`, `arms`, `describe`, `plan`, `run`) and a pure `decide*` function with a test; reuse `runArms`/`metricRow` from `suites/shared.ts` and `pickLowestPassing`/`effectiveBar` from `decide.ts`.
2. Add its fixture sampling to `fixtures.ts` (SELECT only) and its name to `SUITE_NAMES` in `options.ts` and `SUITES` in `run.ts`. Build the prompt input with the service's own builder; if the service shapes it inline, export a pure builder first (in `services/promptInputs.ts`, with a pin in its test) and have the service call it.
3. A new model needs a price row in `MODELS` (`models.ts`). GPT-6 rejects `minimal`; gpt-5-mini/nano and gpt-6.1-sol reject `none` (`createChatModel` throws).
4. A new taste set needs a slug in `RatingSetSlug`, a budget in `RATING_BUDGET` and a picking rule in `SET_SPECS` (`ratingSets.ts`).
