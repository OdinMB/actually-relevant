## New Capabilities Identified

### 1. "Report an error" on each story, linked to the story (High)
- **What**: A "Report an error in this story" link on every story page that opens the feedback form pre-bound to that story (`/feedback?story=<slug>`), stored as a new `correction` category with a nullable `storyId` on `Feedback`. The admin Feedback page shows and links the story, and the admin story detail page lists its reports with a count badge in the story table.
- **Where**: `server/prisma/schema.prisma` (`Feedback.storyId String?`, relation with `onDelete: SetNull`, `FeedbackCategory.correction`; migration via `db:migrate:create`), `server/src/routes/public/feedback.ts` (accept `storySlug`, resolve to a published story or drop it), `server/src/routes/admin/feedback.ts`, `client/src/pages/StoryPage.tsx` (link next to the AI label / "How it works"), `client/src/pages/FeedbackPage.tsx` (read `?story=`, show the story title, preselect the category), `client/src/pages/admin/FeedbackPage.tsx`, `client/src/pages/admin/StoryDetailPage.tsx`. Update `.context/ai-transparency.md` §7 (correction channel) and `server/src/lib/openapi.ts` if the feedback route is documented there.
- **Why**: Every story is AI-written and, per the methodology copy, nobody reviews it before it is published. Today the only correction channel is the generic `/feedback` page, so a report reaches the admin with no story attached and the editor has to work out which one it means. Tying reports to stories makes the AI Act correction commitment concrete and gives the owner a per-story quality signal that the eval harness cannot.
- **Effort**: small–medium (one migration, two forms, two admin views)
- **Lens**: use case / capability gap
- **Note**: Touches the open feedback-retention backlog item (the retention job would delete these rows too) and possibly the privacy page's feedback disclosure. The link wording is user-facing copy beside an AI label, so the owner approves it.

### 2. Story-specific link previews for shared story URLs (High, owner judgment)
- **What**: Make a shared `/stories/<slug>` link preview as that story (title, summary, per-story image) on LinkedIn, X, Slack, WhatsApp, Facebook and Mastodon instead of the homepage. Two parts: (a) `GET /api/stories/:slug/og.png`, a 1200x630 image rendered with the existing `createStoryImage()` canvas code from the newsletter carousel, carrying the XMP AI marker (`embedXmpInPng`), cached; (b) story-specific meta tags in the HTML that non-JS crawlers receive. Then make Bluesky's `publishPost()` use the per-story image, as `.context/seo.md` and `.context/bluesky.md` already say it should once one exists.
- **Where**: `server/src/services/carousel.ts` (factor the slide renderer to take a size), new `server/src/routes/public/storyPreview.ts`, `server/src/services/bluesky.ts`, `client/src/pages/StoryPage.tsx` (Helmet `og:image`), `render.yaml` routes, `.context/seo.md`, `.context/ai-transparency.md` (new image surface).
- **Why**: Story pages are dynamic, not prerendered (`.context/seo.md`), so crawlers that do not run JavaScript only see `index.html`'s homepage fallbacks. The site has `ShareButtons` for X, LinkedIn and email on every story, and today every one of those shares previews as the generic homepage card. Sharing is the main organic growth path for a site with no ads and no tracking.
- **Effort**: medium
- **Lens**: capability gap / integration
- **Decision for the owner**, part (b), one of two ways:
  - **Proxy story pages through the backend.** A Render rewrite sends `/stories/*` to an Express route that returns the SPA shell with the story's meta tags injected, so every story link previews correctly, including ones copied from the address bar. The cost is that every story page view then depends on the API instance (memory-capped, also running cron, LLM and ffmpeg work) and adds a backend round trip. Check that Render's rewrite supports the path form needed.
  - **A share URL on the API host.** `api.actuallyrelevant.news/s/<slug>` serves the meta tags plus a redirect, and the share buttons and social posts use it. Story pages stay static, but links people copy from the address bar keep the generic preview.

### 3. Public newsletter archive: web edition of each issue (Medium, owner judgment)
- **What**: `/newsletter/archive` listing published issues and `/newsletter/:weekKey-or-slug` rendering an issue's stored markdown `content` as a page (react-markdown is already a client dependency), with the issue's AI label (`NEWSLETTER_TOP_LABEL`) at the top, story headlines through `StoryTitleLabel`, and links to the story pages. The newsletter's existing `status: 'published'` step becomes what makes an issue public. The server sitemap lists issues, and an archive link goes on `/newsletter` and in the issue HTML ("View in browser").
- **Where**: new `server/src/routes/public/newsletters.ts` (published only, `aiGenerated` marker as for stories), `server/src/routes/public/index.ts`, `server/src/routes/public/sitemap.ts`, new `client/src/pages/NewsletterArchivePage.tsx` and `NewsletterIssuePage.tsx`, `client/src/App.tsx`, `client/src/routes.ts` (archive index only), `server/src/services/newsletter.ts` (resolve `{feed:id}` tags for the web render; optional slug), `.context/newsletter-podcast.md`, `.context/ai-transparency.md`, `.context/seo.md`.
- **Why**: Issues are built every Saturday, but they reach no one while sending stays paused for Plunk's complaint risk (BACKLOG: one complaint disables the account until about 5,800 sends). A web edition gives each week's work a reader without sending a single email, matches what the podcast already does with public transcript pages, and lets a prospective subscriber see what they would get before signing up, which should also cut complaints once sending resumes. It was explicitly left out of scope in `.plans/completed/2026-02-16_newsletter-page.md` and never picked up.
- **Effort**: medium
- **Lens**: underserved use case
- **Decision for the owner**: whether issues should be public at all, and whether "published" in the admin (today a bookkeeping status) should be the switch or there should be a separate one.

### 4. Incremental sync for API consumers: `since`, `minRelevance` and the feed (Medium, quick win)
- **What**: Add `publishedSince` / `publishedBefore` (ISO date-times on `datePublished`) and `minRelevance` (1–10) to `GET /api/stories` and the RSS feeds (`?minRelevance=7`), documented in the OpenAPI spec and shown on `/free-api` and `/developers`.
- **Where**: `server/src/schemas/story.ts` (`publicStoryQuerySchema`), `server/src/services/story.ts` (`getPublishedStories` where clause; leave hybrid search unchanged), `server/src/routes/public/feed.ts`, `server/src/lib/openapi.ts`, `client/src/pages/FreeApiPage.tsx` example, tests next to `stories.test.ts` and `feed.test.ts`. Note the change in `.context/public-website.md`.
- **Why**: `/free-api` promotes team-channel digests and "alerting systems", but a consumer can only page through the newest stories and diff them, which on a 60-second-cached, rate-limited API is wasteful for everyone. "Only stories rated 7+ since my last poll" is the request a Slack bot or alerting pipeline actually makes, and the same filter gives RSS readers a high-signal feed.
- **Effort**: small
- **Lens**: extension point / DX
- **Note**: It commits the project to these parameter names as part of the public API contract.

### 5. Podcast chapters linking each segment to its story (Low)
- **What**: At the `ready` stage, write a Podcasting 2.0 JSON chapters file next to the MP3 and VTT (one chapter per story segment, titled with the story's headline, `url` pointing at its story page, plus the opener and outro), and reference it with `<podcast:chapters url=… type="application/json+chapters"/>` in the feed. Optionally also embed ID3 `CHAP` frames during ffmpeg assembly.
- **Where**: `server/src/services/podcastChunks.ts` (a `buildChapters()` beside `buildTranscriptVtt()`, from the same chunk durations and pause length), `server/src/services/podcastAudioStages.ts` (upload under a fresh name, following Bunny's never-reuse-a-name rule; extend `deleteEpisodeObjects`), schema field `chaptersPath`/`chaptersUrl` on `Podcast`, `server/src/services/podcastFeed.ts`, `podcastPublish.ts`, `.context/podcast.md`.
- **Why**: Apple Podcasts added `podcast:chapters` JSON support in iOS 26.2 (late 2025), alongside Podcast Index apps. Without chapters supplied, Apple generates its own automatic chapters, which carry no links. Chapters let listeners skip to a story, and the per-chapter link turns each segment into a click to the story page, which is the podcast's only path back to the site. The timing data already exists: the VTT transcript is built from the same chunk durations.
- **Effort**: small–medium
- **Lens**: emerging pattern
- **Note**: The chapters file is AI-derived text, so add it to the AI inventory in `.context/ai-transparency.md`.
