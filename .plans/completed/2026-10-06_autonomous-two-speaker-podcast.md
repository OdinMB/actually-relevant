## Problem

Today an admin creates a podcast row, assigns every story of the week, and gets a single-voice script with a URL list appended; the owner then pastes it into an external TTS tool and uploads it to Buzzsprout by hand. Nothing produces audio, nothing is hosted by us, and the script format (one string, no turns, no length target, a PHP-era prompt) cannot drive a two-speaker voice model. The owner wants a weekly episode that writes, voices and stores itself, which he publishes with one click, and later fully automatically.

### Shape of the solution

Two axes on the existing `Podcast` row, never conflated:

- **`stage`** (production, forward-only): `legacy` for rows that existed before this change; `created` (row exists, nothing produced) → `scripted` (stories selected and snapshotted, dialogue JSON, title, summary and show notes stored) → `voiced` (every TTS chunk stored in `podcast_audio_chunks`) → `ready` (MP3 and VTT uploaded to Bunny, URLs, paths, bytes and duration stored, `readyAt` set, chunks deleted). A failure never overwrites the stage: it sets `lastError` and `failedAt`, and the next run resumes from the stage (critique 1.4, 1.6). Selection is not a stage of its own: it is one cheap call, persisted together with the script. *(Superseded by Phase 2b: selection becomes the stage `selected`, so a person can review it.)*
- **`status`** (`ContentStatus`, unchanged; newsletters share it): `published` means "listed in the feed and on /podcast". Only `podcastPublish.ts` changes it, and only for a `ready` row whose own `dryRun` flag is false. `PUT /api/admin/podcasts/:id` accepts `title` only (critique 2.7). *(Phase 2b adds `humanEdited` to it, and separate endpoints for stories and script; `status` still changes only through publishing.)*

`weekKey` (ISO week in UTC, e.g. `2026-W41`, unique, null for legacy rows) makes the weekly run idempotent.

**Modules.** Each new file holds one reason to change:

- `services/podcastPipeline.ts`: the stage machine. `advanceEpisode(id)` claims the lease, runs each remaining stage, persists each stage's output before the next starts, and decides dry-run behaviour (prefixes, stub voice). `resetEpisode(id)` goes back to `created`. The lease helpers (claim, renew, fenced write, release) are private to it; they serve only the stage machine.
- `services/podcastWeekly.ts`: "this week's episode" and its retry policy. `runWeeklyEpisode({ trigger: 'cron' | 'admin' })` resolves `weekKey`, finds or creates the row, honours `blockedAt`, counts automatic failures, classifies errors, and returns an outcome. The cron handler and the admin "Start this week's episode" route both call it, so no route imports from `jobs/` (architecture review 1).
- `services/podcastScript.ts`: the two LLM calls (select, write) and show notes.
- `services/podcastDialogue.ts`: pure dialogue logic (validate, assemble spoken turns, chunk, render the admin script view, build the VTT).
- `services/podcastGuards.ts`: "may we spend or publish now": configuration check, the TTS spend reservation, the job-row `enabled` re-check for the automatic path, and the typed `PodcastBlockedError` and `PodcastStoppedError`. Used by the pipeline, the publish service and the admin routes from Phase 2 on, so the checks are never scattered (architecture review 2).
- `services/podcastPublish.ts`: publish, unpublish, the published-episode query, and the feed cache invalidation call.
- `services/podcastFeed.ts`: the RSS document and its cache (`getFeedXml`, `invalidateFeedCache`).
- `lib/elevenlabs.ts`, `lib/bunnyStorage.ts`: vendor HTTP contracts only, no dry-run logic (paths and voice choice come from the pipeline).
- `lib/podcastAudio.ts`: ffmpeg (assemble, tag, generate silence for the dry-run stub).
- `lib/xml.ts`: `escapeXml`, moved from `prompts/shared.ts`, which re-exports it unchanged, so the feed does not import from `prompts/`.

`services/podcast.ts` keeps CRUD only (its script generation moves out), and `deletePodcast` gains its guards.

**Cross-process claim, fenced** (critique 1.3; correctness review 3). Claim with raw SQL on the database clock: `UPDATE podcasts SET lease_owner = $me, lease_until = now() + interval '30 minutes' WHERE id = $id AND (lease_until IS NULL OR lease_until < now())`; zero rows means another process has it and the call returns quietly. `$me` is a per-process random id. The lease is renewed at the start of every stage and before every TTS chunk; every stage write is `updateMany({ where: { id, leaseOwner: me } })` and aborts when it matches nothing (a process that lost its lease after a pause cannot overwrite the new owner's work); release is `WHERE lease_owner = $me`, in `finally` and in the existing SIGTERM handler in `server/src/index.ts`. Chosen over `pg_try_advisory_lock`: Prisma's pool can run each query on a different connection, so a session lock is not reliably held by the code that took it.

**Weekend retries and first enable, without touching the shared scheduler** (ADR-0011; critique 1.1-1.2). `generate_podcast` runs at `0 6,10,14,18 * * 6,0` (node-cron uses server-local time; Render runs in UTC, and the handler's window is computed in UTC, so a developer machine in another zone cannot misfire it). The handler:

1. returns quietly unless now is inside the weekend window, Saturday 05:00 to Sunday 23:59 UTC (a config constant). The window is needed even with the weekend-only cron: `isOverdue` catches up a weekly job at boot once about 42 hours have passed, so a Wednesday deploy would otherwise produce a midweek episode for the next ISO week (correctness review confirms; the simplicity review's proposal to drop it is not adopted);
2. calls `runWeeklyEpisode({ trigger: 'cron' })`, which returns `skipped` (already ready or published, `blockedAt` set, another process holds the lease), `stopped` (the `generate_podcast` row was disabled during the run), `done`, `retry-later` or `blocked`;
3. on `retry-later` or `stopped` returns normally (no alert); on `blocked` throws, so `runJob` alerts through `notifyJobFailure` exactly once, because later slots see `blockedAt` and skip; on `done` sends a success notice through a new `notifyEvent()` (title, duration, characters billed this episode and month to date, admin link), so a missing Saturday message is itself a signal.

`runWeeklyEpisode` blocks the episode (`blockedAt`, `blockedReason`) on a non-retryable error (`PodcastBlockedError`: credits, cap, configuration missing, dialogue invalid after its one regeneration) or when automatic failures reach `config.podcast.maxAttemptsPerWeek` (3). Disabling the job is not a block: on the cron trigger the pipeline re-reads the `generate_podcast` row's `enabled` flag before every TTS call and throws `PodcastStoppedError` when it is off; the stage and stored chunks are kept, no attempt is counted, no alert is sent, and the next enabled slot (or an admin Resume) continues from there. Only automatic runs count attempts; the admin "Resume" clears `blockedAt` and resets `attempts`. A row whose `dryRun` flag is true while the config is no longer dry-run is reset to `created` with `dryRun = false` and regenerated, so a dry run in production cannot occupy the week (correctness review 6). The migration seeds both job rows with `last_completed_at = now()`, so neither runs at boot just because it never completed; `seed-jobs.ts` (fresh dev databases) leaves it null, which the window makes harmless.

The generic scheduler weaknesses (per-process overlap guard, `lastCompletedAt` written on failure, boot run for never-completed jobs) stay for the other jobs and go to follow-up work: fixing them changes boot behaviour of every job, which is out of proportion here. (The first `jobRun.update` outside the `try` was fixed separately by the scheduler hardening of 2026-10-06, which also made `runJob` never reject and added a boot retry for `initScheduler`.) The strongest-end-state architect proposed a DB claim in `runJob` for all jobs in this change; it is recorded as follow-up because the podcast's own lease and ledger already make it safe.

**Publish** (ADR-0012). `publishEpisode(id)` requires `stage = ready` and the row's `dryRun = false`; it sets `status = published`, `publishedAt` (first time only), clears `unpublishedAt`, and invalidates the feed cache. The admin Publish button is a deliberate owner action and is not gated by a switch. `unpublishEpisode(id)` always works and sets `unpublishedAt`. The feed and `/api/podcast` keep serving published episodes when both podcast jobs are disabled. An episode that has ever been published (`publishedAt` set) can never be regenerated or deleted (its GUID and enclosure must not change); it can be unpublished.

The `publish_podcast` job (seeded **disabled**, `0 7 * * 1`, Monday 07:00 UTC) publishes the newest `ready` episode of the current or previous ISO week that has never been unpublished (`unpublishedAt` null) and whose `readyAt` is at least 24 hours old (config constant), so a manual Run or a boot catch-up cannot publish before the owner had a day to listen, and the job never undoes the owner's takedown (correctness review 1). The job re-reads its own row's `enabled` flag immediately before calling `publishEpisode`, so disabling it in the admin during a run prevents the publish. Going automatic = enabling the job row in the existing admin Jobs page; no code change.

**Spend controls** (critique 1.10: characters, not dollars).

- On/off = the `generate_podcast` and `publish_podcast` job rows in the admin Jobs page, both seeded disabled (owner decision, 2026-10-06; no environment kill switch). The automatic path re-checks its row's `enabled` flag before every TTS call and before publishing. Admin actions are not gated by the toggles. Nothing blocks `unpublishEpisode`, the feed or the public page.
- Configuration check (`assertPodcastRunnable`: ElevenLabs key, Bunny zone and password, both voice ids, `WEBHOOK_URL`): runs at the start of every podcast job run and every admin podcast action, and once at boot when either podcast job row is enabled (a missing setting is logged and alerted through `notifyEvent`). A disabled podcast with no credentials stays silent.
- Monthly cap `config.podcast.monthlyTtsCharCap` (32,000 since 2026-10-06, provisional: about 4.3 episodes at about 5,500 characters plus one full re-voice at 1 credit per character; it was 28,000, 5 episodes at the old 5,600 ceiling; S2 measured 0.11 during the `eleven_v4` launch promotion, so the ratio is re-measured with one call after 2026-10-12 before the cap is confirmed). Each TTS call **reserves** its characters first: a short `$transaction` takes `pg_advisory_xact_lock(<constant>)`, sums `podcast_tts_usage` for the UTC calendar month, and inserts the row if the sum plus this chunk stays under the cap; it commits before the HTTP call. The row is kept whatever the call's outcome (a timed-out call may still be billed). Over the cap → `PodcastBlockedError`. Regenerations count.
- Balance pre-check: before the first chunk, `GET /v1/user/subscription` (`character_limit - character_count`) must cover the remaining chunks. ElevenLabs credits reset on the subscription anniversary, not on the calendar month, so this is the guard that matches the vendor; the local cap is the guard that holds when the vendor's numbers are wrong. S2 showed the subscription counter tracks API usage exactly but lags a few calls behind, so the pre-check stays and is a coarse guard; the per-call truth is the `character-cost` response header, which `lib/elevenlabs.ts` returns and the pipeline logs with each chunk.
- ElevenLabs 401/402, `quota_exceeded` and paused-account responses → `PodcastBlockedError`, never retried, alerted once (owner decision 3).
- LLM usage: `withStructuredOutput(schema, { includeRaw: true })` logs `usage_metadata` per call (structured log, no column). A `parsed: null` result throws explicitly, so it counts as the dialogue's one regeneration (correctness review 10). No USD column or price setting: the episode's characters are summed from the ledger.

**Dry run** (critique 2.8). Dry run is derived, not set: `config.podcast.dryRun` is `NODE_ENV !== 'production'`, so there is no variable that could switch production into dry run or dev out of it. The row stores `dryRun`. In dry run the pipeline always voices with a **stub** (ffmpeg silence of the length the characters would take), so dev never spends credits; there is no live-TTS override (owner decision, 2026-10-06: production never publishes without the owner's Publish click, so real audio is heard by generating in production; the Phase 0 spike script covers voice trials); uploads go under a `dry-run/` prefix (without Bunny credentials the run stops at `voiced` with "storage not configured"); publishing refuses the row; the feed filters `dryRun = false`; the admin shows a "Dry run" badge. LLM calls stay real (cents).

**Dialogue script** (brief section C, with the critique's corrections). New `podcastDialogueSchema` in `server/src/schemas/llm.ts`: `episodeTitle`, `episodeSummary`, `segments[] { kind: intro|story|outro, storyRef: int|null, turns[] { speaker: HOST_A|HOST_B, text } }`. Format rules live in `.describe()` (`.context/prompting.md`); `minItems`/`maxItems` on turns are used only if a unit test shows LangChain's json_schema conversion keeps them, otherwise they stay in `.describe()` and validation. Code, not the model, adds the opener as turn 0 (HOST_A), a fixed sign-off turn, the show notes and the AI lines. `storyRef` is mapped to story ids right after the call and a snapshot (id, title, publisher, source URL, story slug) is stored in `episodeStories`; validation, show notes and the feed read the snapshot, never `storyIds`, so story deletion (which strips `storyIds`, `services/story.ts:561-579`) cannot shift references; a deleted story leaves a dead link in frozen show notes, which is accepted (critique 2.6). Validation in `podcastDialogue.ts`: each snapshot story covered exactly once, the intro exactly one HOST_A turn that welcomes listeners and leads straight into the first story (owner, 2026-10-06, after the Phase 1 review: HOST_B's line after the welcome was superfluous), no speaker more than twice in a row (so, after the HOST_A opener and intro, the first story segment opens with HOST_B), total spoken characters 4,200-6,200 (5,600 until the owner's 2026-10-06 change) including the code-added turns and tags (critique 2.15; this band is also the per-episode ceiling), each turn ≤ 400 characters, tags only from the allowlist and at most 2 per turn (unknown tags reject, never silently stripped; S3: tags are billed as characters and the owner heard the tagged sample as slightly stronger), no URLs, markdown or speaker prefixes. Invalid → one regeneration, then `PodcastBlockedError`. Never truncate.

**Segues between segments** (owner, 2026-10-06: several audio pieces are fine provided the script is cohesive with segues). Because chunks break at segment boundaries, every transition must live *inside* a segment's own turns, so each chunk carries its bridge and no join depends on a turn in the neighbouring chunk. Schema: the `segments` and `turns` `.describe()` text requires that each `story` segment's first turn opens with a spoken bridge from the previous segment, naming or contrasting what came before and leading into this story; the `outro` segment's first turn bridges back from the last story. Since 2026-10-06 the intro's one HOST_A turn is the first story's bridge, and the first story segment opens with HOST_B picking it up (still a first turn of at least 40 characters that is not the headline). Validation in `podcastDialogue.ts` (cheap, deterministic, no LLM judge): every segment after the intro has a first turn of at least 40 characters that is not just the story's headline restated, and no two consecutive story segments open with the same first five words (catches a templated "Next up…" on every story); a missing or degenerate bridge is invalid and takes the one regeneration like any other failure. The prompt's `<CONSTRAINTS>` states the rule (each story opens by connecting it to the one before, varied phrasing, no "moving on" filler); the hand-off may alternatively close the previous segment, but then the opening turn of the next segment must still carry its own lead-in, because a chunk can start a new TTS request with only `previous_text` context. `chunkTurns` keeps splitting only at segment boundaries when a segment fits, so the bridge and the story it introduces are always voiced in the same request.

The prompt (`server/src/prompts/podcast.ts`) is rewritten to `.context/prompting.md`: `<ROLE>`, `<GOAL>`, `<HOSTS>` (HOST_A frames each story, HOST_B brings why it matters and the caveats; both are AI hosts with no personal names, never modelled on a real person), `<CONSTRAINTS>` (facts only from the supplied material, attribution to the publisher, tone follows the subject, no filler agreement, short spoken sentences mostly under 18 words, numbers and acronyms written as spoken), `<STORIES>` marked as untrusted input whose instructions are ignored (AI-017). The "prototype phase" outro line is dropped; the sign-off invites feedback on the website (agent's choice; the owner can restore it). Selection gets its own small prompt (`server/src/prompts/podcast-select.ts`, `podcastSelectResultSchema`): one story per top-level issue, plus an optional fifth when an issue has two clearly outstanding stories, preferring stories that work spoken; pool = `published` stories of the last 7 days by `dateCrawled` (not `selected`, which may never publish and would leave show-notes links dead), matching the newsletter's pool.

**Audio** (ADR-0007, ADR-0005). `chunkTurns()` packs whole segments into chunks of ≤ 1,800 characters, splitting a segment at turn boundaries only when it alone is longer. Chunks are voiced sequentially with `model_id: eleven_v4`, a fixed `seed`, the two voice ids, `output_format=mp3_44100_128`, and text continuity (`previous_text`/`future_text`, the last and first 100 characters of the neighbouring chunks; Phase 0 S1: request ids gave no audible gain, and text context is stateless, so a resume needs nothing from an earlier run). With the 1,800-character limit and segments of about 1,000 characters, an episode is about 5 TTS calls, one per story segment (spike, 2026-10-06). Each chunk's bytes, request id, characters and measured duration are written before the next call; a resume skips stored chunks, so nothing is paid twice. Assembly writes the chunks to `os.tmpdir()`, runs one ffmpeg process (concat with `config.podcast.segmentPauseMs` of silence between chunks, 700 ms to start, because in S1 the next story started too abruptly; `loudnorm` to -16 LUFS, MP3 128 kbps mono, ID3 title, artist "Actually Relevant", album = show title, comment and `TXXX:AI-generated=true`, `TXXX:digitalSourceType=http://cv.iptc.org/newscodes/digitalsourcetype/trainedAlgorithmicMedia`; there is no standard ID3 IPTC frame, critique 1.7), reads the result and always deletes the temp files. Duration = bytes × 8 / 128,000 (CBR; tests allow ±1 s for the tag frames), so no ffprobe. Upload paths `episodes/<weekKey>-<8 random chars>.mp3` and `.vtt`, ASCII only, a fresh suffix per render, so a CDN-cached old file can never appear under a published URL; a regenerate before first publication deletes the previous objects best-effort (both paths are stored). The VTT (`buildTranscriptVtt`: turns timed proportionally to characters within each chunk, offset by the measured durations of the preceding chunks plus the pauses between them, critique 2.4) is uploaded at the `ready` stage, so it needs no route and no API hostname.

### Alternatives considered

- **A new `PodcastEpisode` table, or a 1:1 `PodcastRun` table for the operational columns.** Rejected for now: admin pages, routes, story-deletion cleanup and the shared type all key on `Podcast`, and legacy rows coexist as `stage = legacy`. **Accepted debt:** `Podcast` mixes content (title, dialogue, show notes) with operations (lease, attempts, block, error, audio metadata), about 30 columns. The trigger to split the operational columns into a `PodcastRun` table is a second episode kind or show; `getPodcasts` selects list columns explicitly meanwhile so list queries never load the dialogue.
- **Chunks in `os.tmpdir()` (brief) or in Bunny under a work prefix.** tmp is lost on every deploy and re-bills; Bunny would make dry run and tests depend on storage and expose unreleased audio. Postgres holds about 5 MB per episode for minutes to hours.
- **Generic scheduler fixes** (both architects discussed; the strongest-end-state one proposed a DB claim in `runJob`). Deferred, see above.
- **A separate hourly retry job.** Repeated slots of the same job need no second schedule.
- **`stage = failed` or `stage = blocked`** (brief; one architect). A stage value loses the resume point; error and block fields sit beside it.
- **A USD budget cap** (brief). On a subscription the marginal cost is credits, so the cap counts characters (critique 1.10).
- **The `@elevenlabs/elevenlabs-js` SDK; Buzzsprout, Transistor or R2.** SDK rejected (ADR-0007); hosting is the owner's decision (memo section 2).
- **Reusing the newsletter selection prompt with one story per issue.** Its role text names the newsletter, "spoken-ness" is a different criterion, and reuse would couple the two calibrations.
- **The `feed` package.** No itunes or podcasting2 support; hand-built XML is smaller than post-processing.
- **Raw MP3 frame concatenation without ffmpeg** (one architect). No loudness normalisation and possible clicks at joins; it stays the first thing Phase 0 S5 reaches for if ffmpeg fails on Render, as a new decision.
- **Dropping the VTT transcript** (simplicity review). `podcast:transcript` is in the owner's binding feed requirements, so it stays, with proportional timing named as approximate.

**Review disagreements, resolved.** The simplicity review asked for a lease without renewal or owner and for dropping the weekend window; the correctness review showed both are needed (a paused process overwriting a new owner's stage after billing; boot catch-up on a weekday). For a feature in a strained area, the correctness case wins. The simplicity review's other cuts were adopted: no `selected` stage, no separate per-episode ceiling, no cost-estimate setting or USD column, no LLM usage column, no "Regenerate audio" (with a fixed seed it reproduces the same audio), no legacy editor, listen links, Bunny host and model id as config constants rather than environment variables, `checkDialogue` built on `validateDialogue`, and no `podcast-select` call site in the large-tier suite. *(Phase 2b reverses two of these cuts on the owner's request: the `selected` stage returns, and "Regenerate audio" returns with a fresh seed per re-voice.)*

**Stages and modes** (ADR-0008, which extends ADR-0003). The stage list becomes `legacy | created → selected → scripted → voiced → ready`. `selected` is new: the stage that selection writes (`episodeStories` snapshot and `storyIds`), split out of today's `writeScriptStage`. The script stage then reads the snapshot and reloads the stories' prompt material by id (`loadEpisodeStories`); a story that is no longer published fails the stage with "story <title> is no longer published; change the selection" (an ordinary failure, kept on the row). The selection pool is anchored on the episode row's `createdAt` (published, `dateCrawled` in the 7 days before it), so the model's pool and the picker's pool are the same list whenever either is read.

A new column `mode` (`PodcastMode`: `automated | interactive`, null until chosen) says how far a run goes. `advanceEpisode` keeps its loop; after writing a stage it re-reads the row and stops when `mode = interactive` and the new stage is one of the review stops `selected` or `scripted`. `voiced` never stops (assembly follows at once), and `ready` is the end of production in both modes. A mode switch takes effect at the next stage boundary, because the loop re-reads the row. The machine stays forward-only: no runner ever moves a stage backwards. The derived `awaitingReview` (interactive, no live lease, no error, not blocked, stage `selected` or `scripted`) is returned with the episode; no stored pause flag, so nothing can disagree with the stage. The migration sets `mode = 'automated'` on existing non-legacy rows past `created` (they were produced that way); `created` rows keep null.

*Alternatives considered:* review stages as extra enum values (`selected_awaiting_review` …) double the stage list and make every "is it at least scripted" check list two values; a stored `awaitingReview` flag can drift from the stage after a failure or a restart. Per-episode `mode` plus derived pauses keeps one stage per production step.

**Flow.**
- **Start:** `POST /api/admin/podcasts/weekly` now only finds or creates the week's row (no advance) and returns it; the client navigates to `/admin/podcasts/:id`. An episode at `created` with no mode shows two buttons, "Interactive (review each step)" and "Fully automated".
- **One continue endpoint:** `POST /:id/resume` takes an optional `{ mode }`, stores it, clears a block as today, and advances in the background. It answers 409 when the row has no mode and none is given. The UI labels it by context: Start interactive / Start automated, "Approve stories and write the script", "Approve script and voice it", "Finish automatically" (mode switch at a pause), "Resume" (after a failure).
- **Automated** = today's behaviour: one run from `created` to `ready`.
- **Interactive:** stops at `selected` and at `scripted`; approving the script voices and assembles in one run, ending at `ready`.
- **At `ready`** (both modes): the audio player and a "Next steps" panel that says what comes next: listen; publishing arrives with Phase 3, which adds Publish and Unpublish here. This answers "not clear what the next steps are" without a dead button.

**Human changes** (only at rest: no live lease, not legacy, never published; 409 otherwise, 422 for content errors; each edit takes the lease for its write, so it cannot race a run):
- **Stories, at `selected`:** `GET /:id/story-pool` lists the pool (id, title, publisher, top-level issue, relevance, whether selected). `PUT /:id/stories { storyIds }` checks distinct ids, `minStories ≤ n ≤ maxStories`, and that each id is in the pool, then rebuilds the snapshot with refs 1..n in the submitted order. The picker keeps the model's order: a swapped-in story takes the place of the one it replaces, and an added story goes last.
- **Script, at `scripted`:** `PUT /:id/script { episodeSummary, segments: [{ turns: [{ text }] }] }`. The structure must match the stored dialogue (same segments, kinds, `storyRef`s, turn count and speakers): text changes only, and speakers stay structural. The merged dialogue runs through `validateDialogue(dialogue, refs, { authoredBy: 'person' })`. Hard rules stay errors and nothing is saved: band, turn ≤ 400, tag allowlist and count, no URLs, markdown or speaker prefixes, speaker runs, every story covered. The two segue rules (bridge ≥ 40 characters and not the headline; no two story openings with the same first five words) become **warnings** for a person's text. The save succeeds and the warnings are shown. *Agent's decision:* a person may write a deliberately short bridge, and they hear the result before publishing, while the hard rules protect TTS cost, chunking and the feed. On save: dialogue, `episodeSummary`, the rendered `script` and the show notes are rewritten.
- **Title and flag:** `PUT /:id { title?, humanEdited? }` works at any stage from `scripted` on, before publication.
- **Going back:** `POST /:id/rewind { to: 'created' | 'selected' | 'scripted', advance: boolean }` replaces `/regenerate`. `rewindEpisode` (replacing `resetEpisode` in `podcastPipeline.ts`) clears every later stage's output under the lease. Rewinding to `scripted` deletes the chunks, the audio fields and the Bunny objects (best-effort) and draws a new `ttsSeed`. Rewinding to `selected` also clears the dialogue, script, summary, show notes, `scriptModelId` and the title (back to the creation default). Rewinding to `created` also clears the snapshot and `humanEdited`. It refuses a target that is not before the current stage. The UI uses it as: Start over (`created`, advance); Regenerate script (`selected`, advance; keeps the stories); Change stories (`selected`, no advance); Edit script after voicing (`scripted`, no advance); Regenerate audio (`scripted`, advance).
- **Cost confirmation:** any action that will voice shows a confirm dialog before it is sent: Approve script and voice it, Regenerate audio, and Edit script after voicing (which discards the audio). The dialog gives the estimated characters (`ttsCharsEstimate`, the sum of `episodeChunks(dialogue)`, returned with the episode), "about N credits at 1 credit per character", and month to date against the cap (`GET /usage`). Since the owner's decision of 2026-10-06, a run that writes and voices (Fully automated, Finish automatically, Resume of an automated episode at `created` or `selected`) asks too, with a typical episode in place of the script's figure: `GET /usage` also returns `typicalEpisodeChars` (`config.podcast.spokenCharAim`) and `maxEpisodeChars` (the band's top). Interactive starts and the cron path never ask.
- **Seed:** `ttsSeed Int?` on the row. Voicing uses it, or `config.podcast.ttsSeed` when it is null; a rewind to `scripted` draws a fresh one, so "Regenerate audio" gives a different take, and a resume within one render keeps the same seed. `textToDialogue` takes the seed as a parameter.

**"Edited by a person".** `humanEdited Boolean @default(false)` on the row, shown as a checkbox on the episode page for every non-legacy episode. The server ticks it when a person changes the story set or its order, or the text of a turn or the summary. A title edit or a mere approval does not tick it. The person can tick or untick it at any time before publication. It selects the AI line of the show notes (and, in Phase 3, the feed description): unticked, the owner-approved `PODCAST_EPISODE_AI_LINE`; ticked, a new `PODCAST_EPISODE_AI_LINE_EDITED`, "AI-generated: Everything in this episode was written and voiced by AI from this week's news. A person reviewed and edited this episode.", **pending owner approval** (open question 5). `buildShowNotes(summary, stories, humanEdited)` is called by every write that changes any of the three. Regenerating the script after an edit keeps the flag; the person unticks it if no edit remains (a rewind to `created` clears it).

**Title prefix.** The script stage writes `title = "W41: <model title>"`, the week number from the row's `weekKey` (a private `weekLabel` in `podcastPipeline.ts`; no prefix without a `weekKey`). The person edits the title freely from `scripted` on. A regenerated script brings a new default title. **Progress and the persistent toast** (ADR-0009).
- **Lease before 202:** the routes that start work (`resume`, `rewind` with `advance`) claim the episode's lease before they answer. They answer 409 "in progress" when they cannot, and hand the held lease to the background run (`advanceEpisode(id, { …, leaseHeld: true })`; the dry-run reset inside `runEpisode` uses the same held lease). So `inProgress` is true from the moment the client has its 202, and a double click cannot start two runs. The cron path keeps claiming for itself. The lease helpers stay in `podcastPipeline.ts`; it now exports `claimEpisode` and `withEpisodeLease(id, fn)` (claim, fenced writes, release) for the routes and for edits.
- **Server:** `GET /api/admin/podcasts/active` (registered before `/:id`) returns every episode with a live lease as `{ id, title, stage, mode, activity, chunksDone, chunksTotal }`. `activity` is derived from the stage being left: `created` "Selecting stories", `selected` "Writing the script", `scripted` "Voicing" (stored chunks out of `episodeChunks`), `voiced` "Assembling and uploading". The episode detail response gains `activity`, `awaitingReview` and `ttsCharsEstimate`.
- **Client:** a `PodcastProgressProvider` (`client/src/hooks/usePodcastProgress.tsx`) is mounted in `AdminLayout` inside `ToastProvider` and the router. It asks `/active` on mount and on window focus, which reattaches after a reload or a run started by cron. It polls every 3 s while it tracks any episode. Its `track(id)` is called by the episode page after every 202. For each tracked episode it keeps one progress toast (`podcast-<id>`, "W41: …: Voicing 3/5", spinner) that never auto-dismisses while running. Clicking it navigates to `/admin/podcasts/:id`. When the episode leaves the active list, the provider fetches it once, turns the toast into the outcome ("Stories selected: review them", "Script ready: review it", "Episode ready to listen"; or an error with `lastError` or `blockedReason`), and invalidates the podcast queries. A success outcome auto-dismisses as today. An error outcome stays until it is dismissed.
- **Toast:** `Toast.tsx` gains an optional `href` per toast (the message renders as a router `Link`) and a `sticky` option on `updateToast` for outcomes that must not auto-dismiss. Existing callers are unchanged.
- **Episode page:** a stage stepper (Select → Script → Voice → Ready) with a spinner on the running step. Every action button is disabled while `inProgress`, and a save shows a spinner while its request is pending. The detail query keeps polling while `inProgress` (today's behaviour).
